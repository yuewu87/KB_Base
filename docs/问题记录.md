# 二、知识库定位

### Q5. 知识库主要装什么内容？

**A：** 内容很杂，包括个人学习笔记、专业领域资料库、项目/研究沉淀、通用第二大脑。允许**多分级**。

### Q6. 知识库主要给人用还是给 AI 用？

**A：** **人机共用**（路线 B）。不是纯 AI 检索库。

### Q7. Obsidian 是必要的吗？

**A：** 分对象看：
- **对 AI 不必要**——AI 直接读文件系统就够了。
- **对人必要**——在「人机共用」定位下，Obsidian 承担人的阅读、编辑、反链、搜索界面。自建同等能力的 GUI 是几个月的活。

### Q8. 知识库的本体是什么？

**A：** 是 `E:\KB_Library` 里的 **markdown 文件 + 目录结构 + frontmatter 字段**，不是 Obsidian。Obsidian 只是这些文件的一个视图，可随时卸载，文件仍在。这也是选本地 markdown 而非数据库的原因：AI 友好、可读、无锁定。

# 三、内容结构

### Q9. 分类用什么形态？

**A：** 人的大框架文件夹 + 项目子文件夹 + 独立知识区：

```
00_收件箱/          所有未定稿内容的统一入口
10_项目/
  <项目名>/
20_知识/            跨项目可复用知识（先建大分类，边用边长）
30_素材/            创作素材
40_索引/            MOC 主题地图 + Dataview 看板
90_附件/            图片等小文件
```

### Q10. 跨项目的「可复用知识」怎么处理？

**A：** **抽到独立知识区（`20_知识/`）**。项目文件夹只放项目专属档案（架构、决策、踩坑），从中提炼的通用知识进知识区，两边用双向链接互指。

理由：文件夹的物理位置只能有一个，但知识天然属于多个上下文。留在项目文件夹里会被项目边界锁死，下个项目启动时想不到去翻。

### Q11. 知识区内部怎么组织？

**A：** 先自动建几个大分类（后端/前端/工具链/方法论），之后**边用边长**。新建分类需报告，AI 不得自行发明分类。

### Q12. 课程知识归 `20_知识` 还是 `30_素材`？

**A：** 归 `20_知识`（2026-09-15 确认）。课程学到的东西就是典型的可复用知识，应与项目经验一起被检索到，而不是和绘画参考图放一起。`30_素材` 只放创作素材。

### Q13. 项目内笔记文件名要不要带项目前缀？

**A：** 要（2026-09-15 确认）。每个项目文件夹下都会有 `踩坑.md`，一旦出现同名文件，`[[踩坑]]` 双向链接就产生歧义。规则：`<项目名>-踩坑.md`。

### Q14. 「其他分类」是否改名为 `30_素材`？

**A：** 是（2026-09-15 确认）。原方案叫「其他分类」，注定变成垃圾桶——凡没明确归属的都往里塞。改为 `30_素材` 并限定语义为「创作素材」。

# 四、写入流程

### Q15. 「用大模型写入」具体指什么？

**A：** 分两层：
- **第一层**：在对话中总结（人的判断力介入，降噪）
- **第二层**：按规则写入库里（追求确定性、可重复、可校验）

### Q16. 两层之间怎么衔接？

**A：** 必须有一个**结构化接口**。第一层的产出不能是散文，得带固定字段（来源 / 一句话摘要 / 建议分类 / 关联笔记）。否则第二层没有判断依据，「按规则」无从谈起。

### Q17. 写入的节奏？

**A：** **随手记草稿 + 末尾转正**。会话中说「记一下」即落草稿，不打断思路；末尾统一转正。

### Q18. 要不要草稿区 / 收件箱？

**A：** 要。收件箱是**所有未定稿内容的统一入口**，agent 投递的和人手写的共用同一个 `00_收件箱/`，不分开——本质状态一致，分开只会让人每次纠结「该放哪」。收件箱**空的才是健康状态**。

### Q19. 转正前要不要逐条确认？

**A：** 不要。**报告是事后通知，不是事前审批单**。服务把活干完 → git commit → 给报告。用户扫一眼，不对再按 commit 回退。逐条拍板太麻烦。

### Q20. 归不了类的内容怎么办？

**A：** 不阻塞。**不进正式区**，留在 `00_收件箱/待归类/`，报告里列出。可当天处理，也可攒着集中看。AI 不得自行发明分类。

### Q21. 允许产生孤儿笔记吗？

**A：** 不允许。每条正式笔记至少链到一处已有笔记或 MOC 页。孤儿是检索不精准的根因。

### Q22. 投递后能不能反悔？

**A：** 能，且必须能。异步缓冲的意义就是留反悔窗口。收件箱条目在整理前必须**可编辑、可删除、可合并**。否则错的结论只是被延后固化。

# 五、字段与模板

### Q23. 「我的判断」字段是谁的判断？

**A：** **用户的判断**（字段名已由「我的判断」改为「用户的判断」）。内容须来自对话中用户说过的话。

**硬规则：用户未表达观点时该节留空，AI 不许代填。** 代填等于伪造用户观点，将来用户回看时分不清哪句是自己想的。

**怎么保证（2026-09-15 补充，Q58）：靠服务机械清空，不靠提示词。**

首次真实 LLM 运行就违反了这条：用户投递的只是一句事实陈述（「并发写入会锁表，用队列串行化解决」），模型却写了一整段「用户认为……」，还追加了两点用户没说过的补充。

加一条提示词硬规则后再试，**仍然被代填**——模型面对一个空标题的默认行为就是填满它，而「用户陈述的事实」与「用户的观点」这条界线对它太模糊。

最终定案：**服务在落盘前机械清空该节正文，只保留标题**（`planning.strip_user_judgment`），由用户自己在 Obsidian 里写。

- 机制上不可能伪造，不依赖模型自觉
- 代价：用户在对话里真说过的观点也不会被自动带过去——**刻意的取舍**，这一节的意义就在于它是用户亲手写的
- 提示词里仍保留一条（规则 8）说明「写了也会被丢掉」，避免模型浪费输出

### Q24. `类型` 字段的枚举？

**A：** `概念 | 踩坑 | 决策 | 经验 | 清单 | 日志 | 索引`。固定枚举，不许自由发挥——字段一旦失控，Dataview 查询和后续自动化全部失效。

其中 `日志`（Q50）和 `索引`（Q56）都属于**结构性文件**而非知识笔记；Dataview 查询知识时可按类型过滤掉。

- `日志` 于 2026-09-15 随 Q50 加入
- `索引` 于 2026-09-15 随 Q56 加入

后两者由**服务生成**，不由 LLM 产出——所以它们不在给模型的允许类型列表里。

### Q25. 检索主力是文件夹还是标签？

**A：** **`主题` 标签**。文件夹决定「物理放哪」，标签决定「属于哪些主题」。一篇笔记能挂多个标签，不能放多个文件夹。阶段一靠 Obsidian 搜索（`tag:#数据库`），阶段二作为 RAG 切片聚合依据。

### Q26. 模板文件放哪？

**A：** 先放**服务代码仓库里**，但以 **`.md` 形式**存在，代码读取。便于修改。

# 六、系统架构

### Q27. 谁来整理知识库？

**A：** **独立服务 + 自带 LLM（API key）**，专职整理，不占用各会话的额度与上下文。各会话 agent 只负责投递，不懂整理规则。

关键转变：把「整理」从**会话行为**变成**服务行为**，规则收拢到服务一处维护。

### Q28. 接口形式？

**A：** 三层，共用同一份逻辑：

| 层 | 谁用 | 通用性 |
|---|---|---|
| **CLI** | 任何能跑 shell 的 harness | **最通用** |
| **HTTP REST** | 任何能发请求的工具 | 底层，另两层都调它 |
| **MCP server** | 支持 MCP 的工具（Claude Code、Codex CLI） | 体验最好，覆盖有限 |

目标：接入市面上大多数工具（Claude Code、DeepSeek harness、Codex 等）。
**CLI 才是最通用的一层**，因为「能跑 shell」几乎是所有 agent harness 的底线能力。

### Q29. 写入如何保证一致性？

**A：** 所有写入**必须经过服务进程**，CLI 和 MCP 都走 HTTP，不直接碰文件。服务没启动时 CLI 报错并提示，而不是自己偷偷写。这样写入天然串行化，不会出现两份逻辑打架。

### Q30. 各 harness 怎么知道何时投递？

**A：** 定案（2026-09-15）。这个问题实际包含**两半**，阻塞性不同，分开处理。

#### ① 接口侧 —— 阻塞最小闭环

**命令形态：**

```bash
kb push --content "并发写入会锁表，最后用队列串行化解决" \
        --project "电商后台" --source 会话

# 长内容走 stdin，避免转义麻烦
echo "..." | kb push --project "电商后台"
```

- **一次投递 = 一条草稿**，多条就调多次。CLI 越简单，agent 越不容易用错。
- 返回：`已收，id=20260915-a3f2`。异步立刻返回，不阻塞会话。

**投递内容格式：agent 只交正文，其余服务推断。**

- 必填：正文
- 可选：`--project`、`--source`
- **禁止让 agent 填 `类型` / `主题` / 建议分类** —— 那等于把整理判断泄漏到每个会话，与服务收拢规则的设计相悖。

**项目名映射规则：**

- agent 报项目名，**默认取 git 仓库根的目录名**（`git rev-parse --show-toplevel` 的 basename），**不是 cwd 的 basename**——避免 agent 停在子目录（如 `src/kb/core/`）时取到 `core`。非 git 仓库时回退到 cwd basename。
- **允许没有项目**：`--project` 可选，留空则走 `20_知识/`。纯知识点、临时目录场景下没有项目才是正常的。
- **匹配前规范化**：统一转小写、`-` 与 `_` 视为等价，避免 `KN_Base` / `kn_base` / `KN-Base` 被当成三个项目。首次创建时按目录名原样保存。
- **服务按规范化名字在 `10_项目/` 下搜唯一匹配**：
  - 唯一匹配 → 挂到该项目
  - 找不到 / 找到多个 → 进 `00_收件箱/待归类/`，报告里列出
  - **从不自动新建项目文件夹**（与「AI 不得自行发明分类」同一原则）

#### ② 提示词侧 —— 不阻塞，且现在写太早

每个 harness 一份说明（Claude Code → skill；Codex → `AGENTS.md`；其他 → 通用说明），放 `docs/接入指南/`。

**但必须等接口稳定并跑通之后再写。** 接口没定稳就写说明书，必然是照着猜写的，接口一改全部过时。说明书应当是「描述既成事实」，不是「承诺未来行为」。

> 注：旧的「用户级 skill + 一行指针」方案是上一版架构（整理在会话内完成）的产物，**已作废**。新架构下 agent 只需会调 CLI。

#### 遗留

- 🔴 **项目目录改名后**（如 `KN_Base` → `KB_Engine`），vault 里已存在的项目文件夹是否跟改？涉及链接失效，低频，暂不处理。

### Q31. 管理界面？

**A：** **本地 Web UI**，一个 `.bat` 启动，模块化设计。首批功能：配置页、工作记录。其他功能后续再说。

内容侧界面（阅读、反链、工作记录看板、待归类看板）**由 Obsidian + Dataview 承接**，不重复造。

### Q32. 密钥与配置放哪？

**A：** **用 `.env` 存在工程根目录（`KN_Base/.env`）**（2026-09-15 确认）。不拆到用户目录，保证配置集中在一个文件夹里处理。

- `.env` **不入库**——`.gitignore` 已含 `.env` / `.env.*` 规则
- **`.env.example` 必须入库**（`.gitignore` 中已用 `!.env.example` 放行），列出全部配置项。**密钥留空待填，其余给出可用默认值**——换机器或重装时照着 example 填一份就够，不用翻代码找配置项，也不用猜默认值是什么
- **绝不能进 vault**。`E:\KB_Library` 是 git 仓库，写进配置会被提交进历史，删掉也还在

**配置项（初稿）：**

| 键 | 必填 | 说明 |
|---|---|---|
| `KB_LLM_API_KEY` | 是 | LLM 的 API key |
| `KB_LLM_BASE_URL` | 是 | API 地址 |
| `KB_LLM_MODEL` | 是 | 模型名（deepseek-flash 起步；具体 id 待接通知时确认） |
| `KB_VAULT_PATH` | 否 | vault 路径，默认 `E:\KB_Library` |
| `KB_PORT` | 否 | 指定端口；留空则自动寻找 |

> 原方案的 `~/.kb/config.toml` **已作废**——它把配置拆到了用户目录，与「配置集中在一个文件夹」冲突。

### Q49. 自动寻找到的端口，CLI 怎么知道？

**A：** 定案（2026-09-15）。服务启动后在工程目录写一个**运行时文件**：

```
KN_Base/runtime/service.json     # { "port": 51723, "pid": 12345, "started": "..." }
```

CLI 的流程：读 `runtime/service.json` → 拿端口去探测 → 通就直接投递；不通（或文件不存在）就后台拉起服务、等服务写好文件、再投递。

这个文件**不入库**（加入 `.gitignore`）。放在工程目录而非用户目录，同样是为了「配置集中在一个文件夹」。

### Q50. 工作日志（整理日志）怎么办？

**A：** 定案（2026-09-15）。

**位置与粒度**：`40_索引/整理日志/2026-09-15.md`，**按天聚合**——每次整理往当天那篇追加一节。

理由：调试期一天可能整理十几次，按次会产生一堆碎片文件；按天回看也顺。与「一次整理 = 一个 commit」不冲突，commit 里包含日志文件的那次追加。

**内容**（带 wiki 链接，Obsidian 里可点击跳转）：

```markdown
## 14:32 整理 3 条草稿

- 新建 [[并发写锁]]
- 合并入 [[XXX-踩坑]]
- 更新 [[40_索引/后端]]
- 待归类 1 条：……
```

**失败也记**。日志是审计记录，只记成功的话，回头看会不知道当时为什么有东西卡在收件箱。

**报告与工作日志同源**：服务产生一份「整理结果」结构，然后两个出口——渲染成文本给会话（报告），渲染成 markdown 进 vault（工作日志）。**不写两套逻辑**，否则会出现报告说「新建 3 篇」而日志写 4 篇这种对不上的情况。

**`类型` 字段取 `日志`**，因此枚举扩充为 6 个值（见 Q24）。

### Q51. 运行日志怎么办？

**A：** 定案（2026-09-15）。`KN_Base/logs/kb.log`，标准 Python logging，按大小轮转保留若干份，默认 INFO、可配 DEBUG。`logs/` 加入 `.gitignore`。

**核心约束：运行日志绝不能进 vault。** 一旦进去就成了笔记，会被检索、被 RAG 切片、被 AI 当作知识。技术日志是噪音，属于垃圾进垃圾出。

**两者不能混为一谈：**

| | **工作日志** | **运行日志** |
|---|---|---|
| 是什么 | 「什么时候整理了什么」，审计记录 | debug / info / error，技术排查用 |
| 谁看 | 用户 | 排查故障时 |
| 是不是知识 | 是，可被检索、阶段二可被 RAG 召回 | 不是 |
| 住哪 | vault 内（`40_索引/整理日志/`） | vault 外（`KN_Base/logs/`） |
| 保留 | 长期 | 轮转，保留 N 份 |

### Q52. 测试策略？

**A：** **全 mock LLM**（2026-09-15 确认）。LLM 调用全部替换为返回固定变更计划的假实现，在此基础上对校验层、落盘层写真实测试。

- 快、免费、稳定，可随时跑
- 真实 LLM 的效果靠手动端到端验证

**理由：** 真实 API 慢、花钱、结果不稳定，不适合作为自动化测试的基础。而整理逻辑的正确性（校验、落盘、回滚）本就不该依赖具体模型的输出——这正是 Q33 把 `llm/` 做成抽象层的原因。

### Q53. vault 的 `.obsidian/` 要不要入库？

**A：** **部分入库**（2026-09-15 确认）。

- **入库**：`app.json`、`community-plugins.json`、插件配置等——换机器时设置基本能跟着走
- **忽略**：`workspace.json`、`cache` 等频繁变动的文件

**理由：** `workspace.json` 记录「哪个面板开在哪」，每次开关 Obsidian 都会变。全部入库会让 git 历史被这种噪音淹没，真正的内容变更反而难找。

### Q54. LLM 怎么调？

**A：** **`openai` SDK + 兼容端点**（2026-09-15 确认）。`base_url` 指向 DeepSeek 的 OpenAI 兼容端点。

**理由：** Q35 要求「后续兼容其他模型」。openai SDK 已是事实标准，市面上多数供应商都提供兼容端点——将来换供应商只改 `base_url` 和模型名，`llm/providers/` 的代码几乎不动。

### Q55. 草稿文件的格式与流转？

**A：** 定案（2026-09-15）。

**文件名 = id**：`00_收件箱/20260915-a3f2.md`
id 规则：`YYYYMMDD-` + 4 位随机十六进制。用 id 而非「日期+摘要」作文件名——id 是对外接口（`kb organize <id>`），文件名与之一致最不容易出错；草稿生命周期短，可读性由 Dataview 看板提供。

**内容 = frontmatter + 正文原样：**

```markdown
---
状态: 待整理
id: 20260915-a3f2
来源: 会话
项目: 电商后台
投递时间: 2026-09-15 14:32
---

（agent 投递的正文，原样保存）
```

**正文绝不改写** —— 改写属于整理阶段。投递阶段服务只负责落盘，保证投递是纯粹的、无判断的，否则投递行为就不可预测了。

字段中没有 `类型` / `主题` —— 那些是整理阶段才产生的（见 Q30：agent 不许填，服务在整理时推断）。

**两种「卡住」的流转：**

| 情况 | 原因 | 去向 |
|---|---|---|
| 整理失败 | LLM 报错 / 格式不合规 | 原样留在 `00_收件箱/`，下次重试 |
| 归不了类 | LLM 正常但判断不了归属 | 移到 `00_收件箱/待归类/` |

**`kb organize` 扫描 `00_收件箱/` 及其 `待归类/` 子目录，且每次重新尝试。** 理由：库会长大——三个月前归不了类的笔记，可能因后来新增了相关笔记而变得可归类。不重试就永远卡着。重试失败的继续留在 `待归类/`，代价只是一次 LLM 调用。

### Q56. 索引页（MOC）从哪来？

**A：** 定案（2026-09-15）。**服务在需要时自动创建** `40_索引/<主题>.md`，内容是 Dataview 查询——零维护，永远自动列出该主题下的所有笔记，不需要人工往上加条目。

**为什么必须自动建：** Q21 定了「不允许孤儿笔记」，但**空库第一天没有任何笔记可链**，第一条笔记必然违反该约束。索引页自动生成后，第一条笔记就有东西可链，约束从第一天起成立。

**幂等：** 已存在的索引页原样返回，**不覆盖**——用户可能自己改过。

**`类型` 字段取 `索引`**，枚举扩充为 7 个值（见 Q24）。

索引页由**服务生成，不由 LLM 产出**——它不在给模型的允许类型列表里。是否需要新建索引页，由服务在落盘时按「frontmatter 的 `主题` 是否对应既有主题目录」决定。

### Q57. 依赖版本怎么管？

**A：** 定案（2026-09-15）。**顶层依赖写下界 + 关键包上界。**

`requirements.txt`：

```
fastapi>=0.141
uvicorn>=0.53
jinja2>=3.1
python-dotenv>=1.0
openai>=3.14,<4
python-frontmatter>=1.3
httpx>=0.28,<1
pytest>=9,<10
```

**背景：** 原计划 Step 2 写「版本先不锁，装完后用 `pip freeze` 回填」，Step 12 却把 freeze 产物 `requirements.lock.txt` 加进了 `.gitignore`。两条合起来的效果是**顶层依赖永远不锁**，「回填」这个动作没有归属。这是计划自身的矛盾，在 Task 1 的代码质量审查中被发现。

**为什么只给 `openai` 加上界：** 大版本破坏性变更最容易发生在 `openai` 这类快速演进的 SDK 上（当前 3.14，跨到 4.x 是迟早的事）。其余几个 API 相对稳定，加下界防「装到过老的版本」即可，加上界反而会挡住安全补丁。

**锁文件：** `requirements.lock.txt`（`pip freeze` 产物）继续不入库——它含平台相关包，跨平台没有意义。

### Q33. 为什么 `core/` 不许依赖 web/api？

**A：** 硬约束。整理是这套系统最容易出错的部分，必须能脱离界面单独跑测试。`core/`（领域逻辑）不 import `web/` 或 `api/`，`llm/` 是抽象层，`api/` 和 `web/` 都是只做协议转换的薄层。

### Q48. vault 里要不要放 CLAUDE.md？

**A：** **不放**（2026-09-15 确认）。vault 保持**纯数据**——只有 markdown 文件、目录结构和 `.obsidian/` 配置，**不含任何规则或说明**。

理由：

- **服务不读它**。服务的规则在代码和 `templates/` 里（见 Q26），与 vault 中的文件无关。
- **不产生会话**。整理走 API key，人通过 Obsidian 读写，不在 vault 目录开 Claude Code 会话，没有会话需要加载它。
- **两份约定会漂移**。vault 一份、服务代码一份，改了一边忘了另一边，就会留下**一份没人读又会说错话的文档**——比没有更危险。

边界因此变得清晰：**数据在 vault，规则全在服务侧。** 换库、重建库都不牵动规则。

> 原设计（Q1 阶段）的「vault 内 CLAUDE.md」是上一版架构的产物——那时整理发生在 vault 会话里。架构改为独立服务后，它失去存在理由，**已作废**。

# 七、本轮新增决策

### Q34. 分期范围？

**A：** **先最小闭环**：vault 骨架 + 服务核心 + CLI 投递 + 异步整理。先把「投递 → 整理 → 落盘」跑通。Web UI、MCP、撤回界面排在其后。

理由：整理质量是成败点，得先能跑起来看到真实效果，再包界面。

### Q35. LLM 选型？

**A：** **deepseek-flash**，API key 由用户自己填。**后续要兼容其他模型**，因此 `llm/` 必须是抽象层，换供应商不改上层。

### Q36. 查重怎么判？

**A：** **两段式**：
1. **预筛（便宜）**：`主题` 标签重叠 + 标题关键词，从全库捞候选（5-10 篇）
2. **判定（LLM）**：只把候选笔记的「一句话结论」和新内容一起给模型，判：完全重复 / 相关 / 全新

优点：**便宜**（只喂候选，非全库）、**可解释**（能说出为何判重）、**可演进**（阶段二把预筛换成向量召回，判定层不动）。

### Q37. 整理由谁触发？

**A：** **只能由用户触发**（2026-09-15 确认）。用户在会话中明确说「这条可以整理了」，agent 才调用工具触发整理。

与异步机制咬合：投递时先搁置（留反悔窗口），用户确认后才整理。

**硬约束：agent 不得自行判断某条总结「已经稳定了」就触发整理。** 否则与「用户决定」矛盾，异步缓冲也就失去意义。

### Q38. 整理是单条还是批量？

**A：** 两者都提供（2026-09-15 确认）——`kb organize` 整理全部待整理，`kb organize <id>` 只整理某条。

### Q39. 服务是常驻还是按需启动？

**A：** **按需自动拉起**（2026-09-15 确认）。

CLI 检测到端口无响应时，自动后台启动服务进程再投递。用户无需关心服务开没开，也不用开机常驻。

这样解决了「按需启动」与「各会话 agent 随时能投递」的矛盾：对用户是按需的，对调用方是无感的。

### Q40. 端口号？

**A：** 自动寻找未占用的端口。

### Q41. Web UI 用静态页面还是模板引擎？

**A：** **模板引擎打底 + 少量 JS 增强**（如 Jinja2）。

理由：配置页是表单、工作记录是列表，都是「读数据展示」型，模板引擎写起来快得多；**不需要引入前端构建链**（无 npm/vite），服务端单进程，符合「管理简单」。只有需要实时刷新的地方（如整理进度）才加 JS 轮询。

### Q42. Python 环境搭了吗？

**A：** 还没搭，可以用。环境名与版本见 Q2（已定：`kn_base` / Python 3.11）。

### Q45. 整理失败的兜底策略？

**A：** 定案（2026-09-15）。**核心手段：把 LLM 调用和文件写入彻底分开。**

整理拆成三段，前两段一个字节都不写：

**① 规划（只读）**——调 LLM 产出完整**变更计划**：哪些笔记新建、哪些改写、哪些链接要加、哪些 MOC 要更新。不碰 vault 文件。

**② 校验（只读，纯静态检查）**——不靠 LLM 自我保证，机器校验：
- `类型` 是合法枚举值吗
- 引用的笔记、分类真实存在吗
- 目标路径合法、无冲突吗
- 计划自相矛盾吗（同一条草稿被规划进两处）

校验不过就打回重来，**vault 一个字节没动**。这一步拦掉绝大多数幻觉类错误。

**③ 落盘（写入，不调 LLM）**——按计划执行纯文件操作。因为不调模型，是确定性的、快的、失败率极低的。「LLM 调到一半留半成品」不会发生，因为规划阶段根本不写。

**失败分级：**

| 失败类型 | 处理 |
|---|---|
| LLM 超时/限流/网络 | 指数退避重试 3 次 |
| 返回格式不合规 | 把错误信息喂回去让它自己修，重试 2 次 |
| 仍失败 | **按条隔离**——该条留在收件箱原样不动，其余条正常整理 |

按条隔离的意义：10 条草稿里 1 条判不了，不该拖垮另外 9 条。失败条目**什么也不写**（保持原样），所以下次重试天然幂等。

**回滚必须精确，不能用 `git checkout .`** ——那会把用户手动编辑、尚未提交的改动一起还原掉。

> 服务自己维护一份「本次操作的文件清单」：修改过的 `git checkout -- <文件>` 还原，新建过的直接删除。用户的未提交改动不受影响。

**崩溃残留：** 服务启动时检查 vault 工作区，若发现本次操作清单残留（= 上次落盘没跑完），**报告给用户决定**回滚还是保留，不自动处理——因为存在用户有未提交改动的可能，自动处理有风险。

### Q46. vault 的 git 提交策略？

**A：** 定案（2026-09-15）。**一次整理 = 一个 commit。**

理由：这直接支撑「报告是事后通知」的前提——收到报告后不满意，回退这一个 commit，整次整理干净撤销。若一篇笔记一个 commit，一次整理 20 篇就是 20 个 commit，历史全是噪音，回退还得挑。

Commit message 用中文，列出本次动了什么：

```
整理草稿 3 条

- 新建 20_知识/后端/并发写锁.md
- 合并入 10_项目/XXX/XXX-踩坑.md
- 更新 40_索引/后端.md
```

**配套三条规则：**

**① 服务只 `git add` 自己动过的文件，禁止 `git add -A`。**
否则会把用户正在编辑、尚未提交的笔记一起裹进这次「AI 整理」的 commit，历史就骗人了。

**② 服务使用独立的 git author（`kb-service`）。**
`git log --author=kb-service` 能一眼分出「AI 写的」和「我写的」，回顾和排查都用得上。

**③ 落盘前记录 HEAD，失败时按文件清单精确回滚**（见 Q45），不回滚清单之外的东西。

### Q47. 附件与媒体策略？

### Q60 的依据：Graphiti 的反面教材

调研查到 Graphiti（Zep）的双时态失效在生产上出过事故（[synapse 的事故报告](https://github.com/alexsh88/synapse/blob/main/docs/FINDING-silent-fact-loss.md)）：

> **被自动失效的事实里 70% 其实还是真的**（28/40，手工核对）。

根因是它的机制：挑「哪些旧事实该失效」时，候选集用**语义相似度**、**不要求候选与新事实共享同一个实体**，然后一次 LLM 调用返回一串**裸索引**（无理由、无置信度），系统照时间戳算术直接落。结果同项目内**只是用词相近**的两条互相误伤，常见形态是「更窄的新结论废掉更宽的真结论」。它还有个缺陷：失效判断**不留可复核的痕迹**。

**对我们的三条约束：**

1. 失效**显式指定**（`--revise`），不猜
2. 失效**留痕**（整理日志覆盖）
3. 链上每个 LLM 调用点都要有**确定性校验兜着** —— Q45 的三段式已经是这个形状，继续按它走

### Q64 的由来：提示词拦不住约束

**2026-09-16 首次端到端验证跑出来的。** 摊平改动做完后投了一条草稿，落盘结果是：

```
10_项目/KN_Base/KN_Base-项目目录摊平.md      ← 实际
10_项目/KN_Base/KN_Base-<类型>.md            ← Q13/README 定的
```

**根因：** 提示词规则 7 写的是「文件名必须**带**项目前缀，如 `项目名-踩坑.md`」，只要求「带前缀」。模型照做了——加了前缀，然后自己取了个内容标题。**代码里没有任何校验。**

**为什么这是致命的：** 这条规则的全部价值在于**路径可推导**（会话层说「改 KN_Base 的决策」不用先搜就能算出路径）。内容标题由模型定，推不出来——规则就白定了。

**处理：** 文件名改为由**代码强制**：

- `planning._project_note_name_error`：文件名必须是 `<项目名>-<类型>.md`，`rpartition("-")` 拆出项目名与后缀，两者都要对
- CREATE 分支再加一条：文件名后缀必须与 `类型` 字段一致（FOLD 不校验这条——fold 不写 frontmatter）
- 提示词规则 7 同步改写，并明说「不要拿内容标题做文件名」

**这是第三次撞上同一条：** Q23（`用户的判断` 不许代填）也是光靠提示词拦不住，最后改成落盘前机械清空。**凡是「必须如此」的约束，都要能落成代码检查**——提示词负责引导，机制负责保证。

**连带后果（已确认接受）：** 每个项目每种类型只能有一个文件。项目里第二条「决策」会走 fold 追加进 `KN_Base-决策.md`，越积越厚。
