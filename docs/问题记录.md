# 二、知识库定位

### Q5. 知识库主要装什么内容？

**A：** 内容很杂，包括个人学习笔记、专业领域资料库、项目/研究沉淀、通用第二大脑。允许**多分级**。

### Q6. 知识库主要给人用还是给 AI 用？

**A：** **人机共用**（路线 B）。不是纯 AI 检索库。

### Q7. Obsidian 是必要的吗？

**A：** 分对象看：
- **对 AI 不必要**——AI 直接读文件系统就够了。
- **对人必要**——在「人机共用」定位下，Obsidian 承担人的阅读、编辑、反链、搜索界面。自建同等能力的 GUI 是几个月的活。

### Q8. 知识库的本体是什么？

**A：** 是 `E:\KB_Library` 里的 **markdown 文件 + 目录结构 + frontmatter 字段**，不是 Obsidian。Obsidian 只是这些文件的一个视图，可随时卸载，文件仍在。这也是选本地 markdown 而非数据库的原因：AI 友好、可读、无锁定。

# 三、内容结构

### Q9. 分类用什么形态？

**A：** 人的大框架文件夹 + 项目子文件夹 + 独立知识区：

```
00_收件箱/          所有未定稿内容的统一入口
10_项目/
  个人/<项目名>/
  工作/<项目名>/
20_知识/            跨项目可复用知识（先建大分类，边用边长）
30_素材/            创作素材
40_索引/            MOC 主题地图 + Dataview 看板
90_附件/            图片等小文件
```

### Q10. 跨项目的「可复用知识」怎么处理？

**A：** **抽到独立知识区（`20_知识/`）**。项目文件夹只放项目专属档案（架构、决策、踩坑），从中提炼的通用知识进知识区，两边用双向链接互指。

理由：文件夹的物理位置只能有一个，但知识天然属于多个上下文。留在项目文件夹里会被项目边界锁死，下个项目启动时想不到去翻。

### Q11. 知识区内部怎么组织？

**A：** 先自动建几个大分类（后端/前端/工具链/方法论），之后**边用边长**。新建分类需报告，AI 不得自行发明分类。

### Q12. 🔴 课程知识归 `20_知识` 还是 `30_素材`？

**提议（未确认）：** 归 `20_知识`。课程学到的东西就是典型的可复用知识，应与项目经验一起被检索到，而不是和绘画参考图放一起。`30_素材` 只放创作素材。

### Q13. 🔴 项目内笔记文件名要不要带项目前缀？

**提议（未确认）：** 要。每个项目文件夹下都会有 `踩坑.md`，一旦出现同名文件，`[[踩坑]]` 双向链接就产生歧义。规则：`<项目名>-踩坑.md`。

### Q14. 🔴「其他分类」是否改名为 `30_素材`？

**提议（未确认）：** 是。原方案叫「其他分类」，注定变成垃圾桶——凡没明确归属的都往里塞。改为 `30_素材` 并限定语义为「创作素材」。

# 四、写入流程

### Q15. 「用大模型写入」具体指什么？

**A：** 分两层：
- **第一层**：在对话中总结（人的判断力介入，降噪）
- **第二层**：按规则写入库里（追求确定性、可重复、可校验）

### Q16. 两层之间怎么衔接？

**A：** 必须有一个**结构化接口**。第一层的产出不能是散文，得带固定字段（来源 / 一句话摘要 / 建议分类 / 关联笔记）。否则第二层没有判断依据，「按规则」无从谈起。

### Q17. 写入的节奏？

**A：** **随手记草稿 + 末尾转正**。会话中说「记一下」即落草稿，不打断思路；末尾统一转正。

### Q18. 要不要草稿区 / 收件箱？

**A：** 要。收件箱是**所有未定稿内容的统一入口**，agent 投递的和人手写的共用同一个 `00_收件箱/`，不分开——本质状态一致，分开只会让人每次纠结「该放哪」。收件箱**空的才是健康状态**。

### Q19. 转正前要不要逐条确认？

**A：** 不要。**报告是事后通知，不是事前审批单**。服务把活干完 → git commit → 给报告。用户扫一眼，不对再按 commit 回退。逐条拍板太麻烦。

### Q20. 归不了类的内容怎么办？

**A：** 不阻塞。**不进正式区**，留在 `00_收件箱/待归类/`，报告里列出。可当天处理，也可攒着集中看。AI 不得自行发明分类。

### Q21. 允许产生孤儿笔记吗？

**A：** 不允许。每条正式笔记至少链到一处已有笔记或 MOC 页。孤儿是检索不精准的根因。

### Q22. 投递后能不能反悔？

**A：** 能，且必须能。异步缓冲的意义就是留反悔窗口。收件箱条目在整理前必须**可编辑、可删除、可合并**。否则错的结论只是被延后固化。

# 五、字段与模板

### Q23. 「我的判断」字段是谁的判断？

**A：** **用户的判断**（字段名已由「我的判断」改为「用户的判断」）。内容须来自对话中用户说过的话。

**硬规则：用户未表达观点时该节留空，AI 不许代填。** 代填等于伪造用户观点，将来用户回看时分不清哪句是自己想的。

### Q24. `类型` 字段的枚举？

**A：** `概念 | 踩坑 | 决策 | 经验 | 清单`。固定枚举，不许自由发挥——字段一旦失控，Dataview 查询和后续自动化全部失效。

### Q25. 检索主力是文件夹还是标签？

**A：** **`主题` 标签**。文件夹决定「物理放哪」，标签决定「属于哪些主题」。一篇笔记能挂多个标签，不能放多个文件夹。阶段一靠 Obsidian 搜索（`tag:#数据库`），阶段二作为 RAG 切片聚合依据。

### Q26. 模板文件放哪？

**A：** 先放**服务代码仓库里**，但以 **`.md` 形式**存在，代码读取。便于修改。

# 六、系统架构

### Q27. 谁来整理知识库？

**A：** **独立服务 + 自带 LLM（API key）**，专职整理，不占用各会话的额度与上下文。各会话 agent 只负责投递，不懂整理规则。

关键转变：把「整理」从**会话行为**变成**服务行为**，规则收拢到服务一处维护。

### Q28. 接口形式？

**A：** 三层，共用同一份逻辑：

| 层 | 谁用 | 通用性 |
|---|---|---|
| **CLI** | 任何能跑 shell 的 harness | **最通用** |
| **HTTP REST** | 任何能发请求的工具 | 底层，另两层都调它 |
| **MCP server** | 支持 MCP 的工具（Claude Code、Codex CLI） | 体验最好，覆盖有限 |

目标：接入市面上大多数工具（Claude Code、DeepSeek harness、Codex 等）。
**CLI 才是最通用的一层**，因为「能跑 shell」几乎是所有 agent harness 的底线能力。

### Q29. 写入如何保证一致性？

**A：** 所有写入**必须经过服务进程**，CLI 和 MCP 都走 HTTP，不直接碰文件。服务没启动时 CLI 报错并提示，而不是自己偷偷写。这样写入天然串行化，不会出现两份逻辑打架。

### Q30. 各 harness 怎么知道何时投递？

**A：** 接入一个工具 = **代码 + 提示词**两件事。接口只是通道，agent 还得知道何时投递、投递什么格式。每个 harness 一份说明（Claude Code → skill；Codex → `AGENTS.md`；其他 → 通用说明），放 `docs/接入指南/`。

🔴 **待解决**：旧的「用户级 skill + 一行指针」方案是上一版架构的产物，需重新确定说明的载体与详细程度。

### Q31. 管理界面？

**A：** **本地 Web UI**，一个 `.bat` 启动，模块化设计。首批功能：配置页、工作记录。其他功能后续再说。

内容侧界面（阅读、反链、工作记录看板、待归类看板）**由 Obsidian + Dataview 承接**，不重复造。

### Q32. 密钥放哪？

**A：** **绝不能进 vault**。`E:\KB_Library` 是 git 仓库，写进配置会被提交进历史，删掉也还在。配置放 vault 外（如 `~/.kb/config.toml`），工程仓库 `.gitignore` 排除本地密钥。

### Q33. 为什么 `core/` 不许依赖 web/api？

**A：** 硬约束。整理是这套系统最容易出错的部分，必须能脱离界面单独跑测试。`core/`（领域逻辑）不 import `web/` 或 `api/`，`llm/` 是抽象层，`api/` 和 `web/` 都是只做协议转换的薄层。

# 七、本轮新增决策

### Q34. 分期范围？

**A：** **先最小闭环**：vault 骨架 + 服务核心 + CLI 投递 + 异步整理。先把「投递 → 整理 → 落盘」跑通。Web UI、MCP、撤回界面排在其后。

理由：整理质量是成败点，得先能跑起来看到真实效果，再包界面。

### Q35. LLM 选型？

**A：** **deepseek-flash**，API key 由用户自己填。**后续要兼容其他模型**，因此 `llm/` 必须是抽象层，换供应商不改上层。

### Q36. 查重怎么判？

**A：** **两段式**：
1. **预筛（便宜）**：`主题` 标签重叠 + 标题关键词，从全库捞候选（5-10 篇）
2. **判定（LLM）**：只把候选笔记的「一句话结论」和新内容一起给模型，判：完全重复 / 相关 / 全新

优点：**便宜**（只喂候选，非全库）、**可解释**（能说出为何判重）、**可演进**（阶段二把预筛换成向量召回，判定层不动）。

### Q37. 整理由谁触发？

**A：** **用户决定**。用户在会话中确认某条总结可以整理了，agent 调用工具触发整理。与异步机制咬合：投递时先搁置（留反悔窗口），用户确认后才整理。

🔴 **待解决**：需明确「谁判断可以整理了」必须是**用户**，不能是 agent 自行判断（否则与「用户决定」矛盾）。

### Q38. 🔴 整理是单条还是批量？

**提议（未确认）：** 两者都提供——`kb organize` 整理全部待整理，`kb organize <id>` 只整理某条。

### Q39. 🔴 服务是常驻还是按需启动？

**A：** 用户要求按需启动。

**待解决：** 与「各会话 agent 随时能投递」存在矛盾——服务没跑时 agent 调用会失败。

**提议：** **按需自动拉起**。CLI 检测到端口无响应，自动后台启动服务进程再投递，用户无感，也不用开机常驻。

### Q40. 端口号？

**A：** 自动寻找未占用的端口。

### Q41. Web UI 用静态页面还是模板引擎？

**A：** **模板引擎打底 + 少量 JS 增强**（如 Jinja2）。

理由：配置页是表单、工作记录是列表，都是「读数据展示」型，模板引擎写起来快得多；**不需要引入前端构建链**（无 npm/vite），服务端单进程，符合「管理简单」。只有需要实时刷新的地方（如整理进度）才加 JS 轮询。

### Q42. Python 环境搭了吗？

**A：** 还没搭，可以用。参见 Q2（环境名与版本待定）。
