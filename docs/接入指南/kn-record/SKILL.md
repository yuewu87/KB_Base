# 记到知识库（KN_Base）

KN_Base 是这个用户自己的知识库。**你是会话层，只负责投递和查询**——判断放哪、写成什么样、打什么标签，全是服务那边的事，不归你管。

你的全部职责是：**挑出值得沉淀的东西，原样投出去**。

---

## 命令

`kb` **不在 PATH 里**，用完整路径：

```bash
# 投递一条
"E:/Study_Projects/KN_Base/kb.bat" push --content "要记的内容" --source 会话

# 查
"E:/Study_Projects/KN_Base/kb.bat" search "关键词"

# 请求整理
"E:/Study_Projects/KN_Base/kb.bat" organize

# 撤回一条投错的草稿（还能一次给多个 id）
"E:/Study_Projects/KN_Base/kb.bat" drop 20260918-9e4f
```

### ⚠️ 必须加 `PYTHONIOENCODING=utf-8`

不加的话，**中文输出全是乱码**（`���գ�id=...`）——`kb.bat` 在 Windows 上按 GBK 输出，读回来就是坏的。所以每条命令都这么写：

```bash
PYTHONIOENCODING=utf-8 "E:/Study_Projects/KN_Base/kb.bat" push --content "..." --source 会话
```

### 投递只交正文

**只给 `--content`（内容）和 `--source 会话`**，别的什么都不填：

- ❌ **不要**填类型（概念/踩坑/决策……）
- ❌ **不要**填主题/标签
- ❌ **不要**建议放哪个目录
- ❌ **不要**自己给笔记起文件名

那全等于**把整理的判断泄漏到每个会话**——换个会话、换个工具，整理规则就不一样了，而这个知识库的价值恰恰在于「规则只在一处」。项目名不用你填，服务会自己取当前 git 仓库的目录名。

长内容走文件，避免转义麻烦：

```bash
PYTHONIOENCODING=utf-8 "E:/Study_Projects/KN_Base/kb.bat" push --file /tmp/note.md --source 会话
```

## 什么时候记

**记的是「以后还会再用到的东西」**，不是「刚才发生了什么」。

✅ **该记**：

- **踩过的坑** —— 一个错误排查了半天才找到原因，原因本身值得记
- **查出来的结论** —— 某个库/工具/协议的实际行为，跟文档写的不一样
- **做过的决策** —— 选了 A 不选 B，**以及为什么不选 B**（这个比结论本身值钱）
- **可复用的做法** —— 一段解决某类问题的套路
- **用户说过的判断** —— 用户自己表达的观点、偏好、取舍

❌ **不该记**：

- 一次性的操作过程（「我执行了 X 命令」）
- 临时的调试输出、报错堆栈本身（**除非**它的成因值得记）
- 会话里正在做的事的流水账
- 用户没说过、你自己推断出来的「用户偏好」——**那是伪造**
- 你现编的测试内容（哪怕它长得像一条真笔记）

**拿不准的时候问用户一句**，别自己塞进去。收件箱里堆垃圾，比漏记一条更糟。

## 什么时候请求整理

投出去的是**草稿**，会先在收件箱缓冲着。**由你判断什么时候让服务去整理**——三条触发条件，满足任一：

1. **攒够 10 条，且确认投递内容无误、没有需要改的结论**
   - 「10 条」是量；**「确认无误」是前提**——内容里还有想改的，先别触发
   - 攒的条数用 `PYTHONIOENCODING=utf-8 "E:/Study_Projects/KN_Base/kb.bat" inbox` 看
2. **用户提到「暂停开发」时** —— 一个阶段收尾，正是沉淀的时机
3. **用户直接要求整理时** —— 说「整理一下」「可以整理了」之类

```bash
PYTHONIOENCODING=utf-8 "E:/Study_Projects/KN_Base/kb.bat" organize
```

整理会**真改库里的文件**（移动、改名、合并）并**打一个 git commit**。跑完之后把结果讲给用户听——哪几条落了盘、哪几条归不了类留在待归类，**别只说「整理完了」**。

> **别机械地数到 10 就触发。** 那个数字是给你一个参考节奏，不是打卡。会话快结束了、用户要走了，哪怕只有 3 条也该问一句要不要整理。

## 改已有笔记

用户说「那条结论要改」「之前记的那个不对」时：

```bash
PYTHONIOENCODING=utf-8 "E:/Study_Projects/KN_Base/kb.bat" push --revise "文件名" --content "新的说法" --source 会话
```

- `--revise` 后面是**目标笔记的文件名**，**不含路径、不含 `.md`**（Obsidian 就是按文件名链接的）
- 服务会全库搜同名文件：**唯一命中才算数**，零个或多个都会让这条进待归类、不猜
- 结果是**新写一篇**、把旧的打上失效标记——**不是覆盖**。同一个文件名下永远只有一种说法

## 投错了：撤回来重投

**投出去的草稿不是定案**——它还在收件箱里缓冲，没整理就还能撤。

```bash
PYTHONIOENCODING=utf-8 "E:/Study_Projects/KN_Base/kb.bat" drop 20260918-9e4f
PYTHONIOENCODING=utf-8 "E:/Study_Projects/KN_Base/kb.bat" drop 20260918-9654 20260918-9e4f   # 一次几条
```

**什么时候用：**

- **项目名取错了** —— 默认取的是 **cwd 的 git 仓库根目录名**。你在临时目录、别的仓库、
  或一个刚 `git init` 的目录里推，就会记成那个目录名。**发现取错 → drop 掉 → 带 `--project` 重投**
- 投重复了、投完发现写歪了、投错库了

**规矩跟投递一样，一个字都不许绕：**

- **只走 `kb drop`，绝不手改 `E:\KB_Library` 里的文件** —— 绕过服务就没有串行化、没有校验，
  等于把「写入只此一路」开了口子。**哪怕只改一行 frontmatter 也不行**
- 删掉的草稿**不留痕迹**（不记日志、不打 commit），这是有意的——删等于「当没发生过」

**别怕撤。** 投错一条很正常，让它烂在库里才贵——它会跟着整理变成一篇字段错误的正式笔记。

> **`--project` 只在默认值不对时才写。** 正常情况下还是别填，服务自己取。

## 查

```bash
PYTHONIOENCODING=utf-8 "E:/Study_Projects/KN_Base/kb.bat" search "关键词"
```

拿到的是**笔记路径**，然后用 Read 工具去读它。检索主力是**标签**，所以换个说法可能查不到——查不到就**换个词再试**，别直接告诉用户「没有」。

---

## 你别做的事

- **别自己写笔记文件。** 一个字都不行——知识库的所有写入都必须经过服务，绕过它就没有串行化、没有校验、没有 commit。
- **别替用户总结观点。** 用户没说过的判断，不要写成「用户认为……」。这条有专门的机制在防（服务落盘前会机械清空那一节），你写了也是白写。
- **别把会话里的废话记进去。** 见上面「不该记」那一节。
- **别改 `E:\KB_Library` 里的任何文件。** 那是用户在 Obsidian 里的地盘。
- **别动 KN_Base 仓库的代码**（`E:\Study_Projects\KN_Base`）——你是来用这个知识库的，不是来改它的。除非用户明确要你改。

## 出问题的时候

| 现象 | 怎么办 |
|---|---|
| 输出是乱码 | 漏了 `PYTHONIOENCODING=utf-8` |
| `已收，id=...` 但用户问「怎么没进库」 | 正常——草稿在收件箱缓冲，**要 `organize` 才会落库** |
| 命令报连不上服务 | 服务没启动。`kb.bat` 会自己把它拉起来，稍等重试 |
| 归不了类 | 正常。草稿会留在 `_收件箱/待归类/`，报告里会写清楚为什么；**别硬塞**，也别为了让它归进去而重写内容 |
