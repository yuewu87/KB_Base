**这份文档记「踩过什么、学到了什么」，不记「做了什么」。** 做了什么看 [`03_问题记录.md`](03_问题记录.md)，目标形态看 [`01_架构.md`](01_架构.md)。

## 〇、一句话总结

**这个项目踩的坑八成是同一类：把「本该由代码保证的事」交给了模型或人的自觉。**

分了三条判据之后，方向就清楚了：

> **机械约束**（文件名格式、字段非空、路径必须存在）→ **代码必须管**
> **判断题**（这条可不可复用、该归哪个领域、这条算概念还是踩坑）→ **代码管不了，才交给模型**

分不清这两类，就会写出「提示词里写了但代码没查」的规则——**它们会静默失效**。

## 一、平台陷阱（Windows）

### 1. `subprocess` 调 git 必须显式写 `encoding="utf-8", errors="replace"`

**只写 `text=True` 会在 Windows 上按本地编码（GBK）解码**，而 git 的输出（中文 commit message、含中文的路径）是 UTF-8。

**最坑的地方是症状与原因隔了十万八千里**：解码异常抛在**子进程的读取线程**里，主流程只看到 `stdout=None`。你会以为是 git 没输出、或者命令写错了，实际是解码炸了。

**规则**：项目里每一处调 git 的地方都显式写这两个参数。

### 2. 解析 git 输出的路径，必须加 `-c core.quotepath=false`

否则 git 把中文路径转成八进制转义：

```
"20_\347\237\245\350\257\206/..."
```

按字面比对**全部对不上**——而且输出看起来「像是」正常路径，很难第一眼看出问题。

### 3. `git add` 传多个 pathspec，**一个不匹配就整体放弃**

不是「跳过不匹配的那个、把其余加进去」，而是**全有或全无**——`pathspec '...' did not match any files` 一报，一个文件都进不了暂存区。

**典型触发**：路径指向一个从未被跟踪、现在又已不存在的文件（刚删的临时产物、改名前的旧路径）。

**规则**：给 `git add` 传路径之前先过滤，只保留「磁盘上还存在」或「已被 git 跟踪」的。

**在脚本和自动化里尤其危险**：非零退出被吞掉，后续以为已经加进去了。

### 4. `.bat` 文件必须写成纯 ASCII

`cmd.exe` 按系统 OEM 代码页（中文 Windows 上是 GBK）**逐字节**读批处理文件。

UTF-8 的中文注释会被误解码、`REM` 行提前断裂，**后半截当成命令执行**。症状是「莫名其妙的报错」，比如中文被当成命令名。

**为什么不存成 GBK**：那样用 UTF-8 编辑器一改又坏。所以本项目一律 ASCII，中文说明放文档里。

### 5. `core.autocrlf=true` 会让 `git status` 撒谎

**现象**：7 个没动过的笔记显示「已修改」，`git diff` 却是**空的**。每次提交还刷几十行 `LF will be replaced by CRLF` 警告。

**根因**：Windows 上 git 默认 `core.autocrlf=true`——它期望工作区是 **CRLF**，而仓库里所有文件本来都是 **LF**（Python 写、Obsidian 也按 LF 存）。两边对不上，git 就认为文件被改过。

**危害不止是烦**：`git status` 一旦不可信，「服务只 `git add` 自己动过的文件」这条约定就守不住了——**你分不清哪些是真的改了**。

**修法**：加 `.gitattributes` 明确声明，不靠全局配置猜。

```
* text=auto eol=lf          # 默认 LF

*.bat text eol=crlf         # 批处理必须 CRLF——cmd.exe 对 LF 行尾的 .bat
*.cmd text eol=crlf         # 解析不可靠（尤其带 label/goto 时）
```

**注意**：属性只在**检出时**生效。改完要 `rm <文件> && git checkout -- <文件>` 让它重新落盘。

### 6. `conda run` 在本机报内部错误

不要用 `conda run`。直接用绝对路径：

```bash
"D:/Conda_base/envs/kn_base/python.exe" -m pytest -v
```

**另外**：默认的 `python`（`D:\EXE_CODES\Miniconda_exe`）**没装 pytest**。用错解释器会得到 `No module named pytest`，而那不是「没装依赖」的意思。

## 二、模型行为：提示词拦不住的约束

**这一节是全文最值钱的部分**——同一个坑踩了三次，第三次才总结出判据。

### 7. 一个空标题会自己长满 —— 提示词拦不住，只能别留空标题

**这条的机制部分已经随功能一起删了（2026-09-18），但观察到的模型行为是通用的，留着。**

**现象**：模板里有一节 `## 用户的判断`，提示词明明白白写着「用户未表达观点时该节留空」——
模型还是填了。首次真实运行就违反：投递的只是一句事实陈述（「并发写入会锁表」），
模型却写了一整段「用户认为……」，还追加了用户没说过的补充。**加了提示词硬规则后再试，仍然被代填。**

**根因**：**模型面对一个空标题，默认行为就是把它填满。** 而「用户陈述的事实」与
「用户的观点」这条界线对它太模糊——所以这不是它不听指令，是指令本身要求它做一件
它分不清的事。

**当时的修法**：落盘前**机械清空**该节正文（`planning.strip_user_judgment`），只保留标题。

**后来的结局**：2026-09-18 整节删掉了——全库 48 篇**一次都没被填过**，净产出只有噪音。

**教训（对后来更有用的一条）**：**别在模板里留一个「等人来填」的空标题。**
要么有东西自动填它，要么它不该存在。留着它，就要同时准备一条对抗模型默认行为的机制——
而那条机制的存在理由，会在「其实没人填」的事实暴露之后一起消失。

> **代价（当时刻意接受的）**：用户在对话里真说过的观点也不会被自动带过去——
> 这一节的意义就在于它是用户亲手写的。

> **背景**：第 8、9 条记的是 `10_项目/` 时代的两条规则。**规则本身已随结构重订取消**（项目降为 frontmatter 字段、投递直接归领域），但它们是下面第 10 条判据的来源——**规则死了，判据还活着**，所以留在这里。
>
> 引用旧编号的地方在 2026-09-17 清掉了：`03_问题记录.md` 改为**作废即删**，那几个编号已不存在。

### 8. 文件名格式 → 提示词只说了「带前缀」

**现象**：提示词规则 7 写的是「文件名必须**带**项目前缀，如 `项目名-踩坑.md`」。模型照做了——**加了前缀，然后自己取了个内容标题**，落成 `KN_Base-项目目录摊平.md`，而不是原先定的 `KN_Base-决策.md`。**代码里没有任何校验。**

**为什么是致命的**：这条规则的全部价值在于**路径可推导**（会话层说「改 KN_Base 的决策」不用先搜）。内容标题由模型定，**推不出来**——规则就白定了。

**修法**：改用**代码强制**（当时是 `planning` 里的一个文件名校验函数，已随结构重订移除），并加「文件名后缀 == 类型字段」的一致性校验。今天的对应物是 `planning.validate_plan` 里的 `clean_title` 校验（Q72）。

### 9. 「可不可复用」→ 这条只能归提示词

**现象**：9 条硬规则只说了「路径必须落在 `10_项目/` 或 `20_知识/` 下」，**没说什么时候用哪个**。模型只能靠常识猜。

**当时的修法**：加一条判断规则——「换个项目还用得上吗？」（该规则随结构重订取消，现在只有领域一个去处）

**这条不能落成代码检查**：可不可复用是**判断题**，代码判不了。和上面两条正好相反。

### 10. 判据（从 7/8/9 总结）

| | 例子 | 归谁管 |
|---|---|---|
| **机械约束** | 文件名格式对不对、字段非空、路径存不存在 | **代码** |
| **判断题** | 可不可复用、该归哪类、算概念还是踩坑 | **模型** |

**提示词负责引导，机制负责保证。**

三次踩坑都是把机械约束当判断题交给了模型。**写规则之前先问一句：这条能不能落成一行 `if`？** 能，就别写在提示词里。

### 11. 失效判断不能靠相似度猜（调研结论）

查 Graphiti（Zep）的双时态失效时，找到一份生产事故报告（[synapse](https://github.com/alexsh88/synapse/blob/main/docs/FINDING-silent-fact-loss.md)）：

> **被自动失效的事实里 70% 其实还是真的**（28/40 人工核对）。

**根因**：它挑「哪些旧事实该失效」时用**语义相似度**、**不要求候选和新事实共享同一个实体**，然后一次 LLM 调用返回一串**裸索引**（无理由、无置信度），系统照时间戳算术直接落。结果只是用词相近的两条互相误伤，常见形态是**「更窄的新结论废掉更宽的真结论」**。它还有个缺陷：失效判断**不留可复核的痕迹**。

**对我们的约束**：失效必须**显式指定**（`--revise`），不由服务猜；失效要**留痕**（整理日志覆盖）；链上每个 LLM 调用点都要有**确定性校验兜着**。

## 三、测试与验证

### 12. 测试全绿 ≠ 功能对

**`--revise` 的整条链是空转的，而测试全绿。**

**根因**：`write_draft` 只写 `状态/id/投递时间/来源/项目` 五个键，`read_draft` 也只读这五个——`revise_target` 在 push 时被丢掉，整理时 `plan.revise_target` 恒为 `None`，标记失效的代码**永远进不去**。

**为什么测试发现不了**：那批测试只覆盖 `vault` 层的三个函数，**恰好绕过整条链**。

**更糟的是它静默**：用户以为生效了，没有任何告警。

**教训**：单元测试覆盖的是**函数**，不是**链**。凡是「A 写入 → B 读出 → C 使用」这种跨层传递，**必须有一条端到端的往返测试**。

### 13. 只有真实模型跑才走得到的分支

修完上一条之后又发现：**`--revise` 会自我失效。**

模型看到新内容跟原文相似，选了 `fold`（追加进原笔记）；随后 revise 逻辑去找「被取代的那篇」——找到的正是**刚被 fold 的同一篇**，落成：

```
失效: true
被取代于: <它自己>
```

**为什么之前的测试发现不了**：真实路径是「**模型自己决定 create 还是 fold**」，而 mock 里的 LLM 返回的是固定计划——**永远走不到那个分支**。

**修法**：`validate_plan` 拦住「目标路径 == 被取代的那一篇」，报错并说明「新内容必须另起一篇」。**重试循环会把这段理由喂回模型**，它下一次就改成 `create`。

**教训**：mock 测试保证「给定计划，落盘是对的」；**真实模型测试保证「模型产出的计划是合法的」**。两者不可替代。

### 14. 端到端要用真实内容，不要编

第一轮验证时我**现编了两条内容**（「pytest 长路径坑」「dataclass 哈希」）投进库里——不是用户的经验，也跟项目无关。它们长得跟真笔记一模一样，混在库里**看不出来**。

后来改用 `04_RPA_restart` 项目的真实踩坑档案，效果完全不同：

- 它的 `docs/` 里有**成篇的编号问题档案**（现象/根因/修法/核实/回归用例五段式）
- 而且**自带脏数据**（一条「记反了」的说明、两条被更正的旧结论）——正好测冲突消解

**教训**：真实素材自带「边界情况」，编的素材只带你想得到的那些。

### 15. 测试数目不是指标

项目里这个数字的变化：258 → 249（删项目层）→ 258 → 261 → 279 → 281 → 295。

**删掉 26 个测试的那次是进步，不是退步。** 被测的东西不存在了，测试就该跟着走——留着才是负担。

## 四、写计划与执行

### 16. 计划里「预期的失败原因」最容易写错

一份 12 个任务的实施计划，执行时被抓出 **10 处**与计划不符。多数是两类：

- **「这一刻测试该失败成什么样」写错了**。比如 Task 3 说「仍有失败，原因是 X」，实际 22 个失败里只有 1 个是 X 那个原因，另外 21 个是另一个过渡态。
- **改动的文件面估小了**。比如「`KNOWLEDGE` 常量只影响 planning.py」——实际它被 6 个测试文件引用约 55 处，常量一删全部 ImportError。

**教训**：计划里凡是写「应该是这样」的地方，**执行时会变成噪音**——执行者要么停下来确认，要么自己猜。**写不准就不写**，让执行者自己观察。

### 17. 「对不上就停下来报告」是唯一有效的护栏

那份计划里反复写着一句话：

> **跑出来的东西跟期望不符就停下来报告，不要自己判断「大概是这个意思」继续往下走。**

**10 处偏差全部是被这句话逼出来的。** 如果执行者「看着差不多就过了」，这些会全部静默滑过去——**包括那个 `--revise` 空转的 bug**。

**反过来说，计划本身不必完美**：只要执行者诚实报告偏差，错的计划也能安全落地。**「不许自己发挥」比「计划写得对」更重要。**

### 18. 并行代理的收益与代价

把 12 个任务按**文件重叠情况**排成 4 波并行，比 12 次串行快得多。

**但代价是：计划里「每个任务一次提交」的设计没了。** 并行代理共享工作区，同时 `git commit` 会抢索引锁。改成「代理只改、主会话统一提交」，倒是得到了更清楚的历史，但**失去了任务级的回滚点**。

**教训**：并行前先看**文件重叠**——不重叠才能真并行。本轮 `planning.py` 被 4 个任务碰到，所以那几波只能串行。

### 19. 计划文件本身要留「执行记录」

计划执行完，**把「计划错了什么」写回计划文件**。

理由：「计划写了什么」复盘时没用（代码才是事实）；**「当时哪里没想清楚」才有用**——它说明这类问题下次该怎么想。

## 五、运维与配置

### 20. 端口：自动寻找 vs 固定，是两个用户要的东西

**踩到的实例**：`.env` 里 `KB_PORT=` 是空值 → 每次重启自动换端口。CLI 侧完全无感（靠 `runtime/service.json` 自动发现），**但人这边书签就废了**——改代码让服务重启，端口从 `56294` → `54852` → `52447` 一路换，而给用户报的还是旧地址，**连报两次**。

**根因**：Q40 定的「自动寻找未占用端口」对 **CLI** 是对的（agent 不该关心服务开没开），对 **Web UI** 是错的（人要一个能收藏的地址）。

**修法**：部署时在 `.env` 里把 `KB_PORT` 钉死。两个用户要的东西不一样，不该用同一个策略。

### 21. 改了 `src/` 下的代码必须 `kb stop`

服务是**常驻进程**——改了代码不重启，它**仍执行旧逻辑**，而且看起来一切正常。

`kb status` 会检测并告警（比对代码 mtime 与进程启动时间），但**告警是你主动去查才看得到的**。

**规则**：改代码 → `kb stop` → 下次调用自动用新代码拉起。

**⚠️ 这道护栏自己在 2026-09-20 瞎过一次，两个原因叠在一起，都值得记。**

**① 一条测试删掉了真实的运行时状态（这是主因，也是我自己写的）。**

`tests/test_proc.py` 为了验 taskkill 那条 `creationflags`，调了**真的**
`runtime.stop_service()`——它结尾那句 `clear_service_info()` 删的是
**开发机上正跑着的那个服务的 `data/runtime/service.json`**。
补丁只打了 `subprocess.run`、`running_port`、`read_service_info`，
**没人想到「这个函数还会写文件」**。

症状全在测试之外：**571 条全绿，而机器上的服务记录没了。** 接着：

| 你以为 | 实际 |
|---|---|
| `kb stop` 报「本来就没在运行」 | 它在跑，只是**记录没了**；这次调用还把它仅剩的线索删了 |
| `kb status` 说代码是最新的 | `is_stale()` 在文件缺失时返回 `False`——**假的全绿** |
| 改了代码，重启验证过了 | 用的还是**改动前那个进程**，`ensure_service` 只是把旧端口还给你 |

**这次就是这么被骗的**：跑了整整一轮验证，`?new=1` 死活不生效、看着像功能写坏了，
实际是 08:14 起的老进程在服务请求，而 `router.py` 是 08:29 改的。

**修法（机制，不是自觉）**：`tests/conftest.py` 里一个 **autouse** 夹具，把
`runtime.SERVICE_FILE` 重定向到 `tmp_path`。**不靠每个人记得给这条打补丁**——
第三个人写「顺手调一下 `stop_service`」时不会再踩一遍。
（两个方向都验过：有夹具时哨兵文件活着；把 `autouse=True` 去掉，**4 条测试照样全绿地
把哨兵删了**。）

`kb status` 的告警和 `kb stop` 的能力，**都建立在那个文件存在**之上——
和第 30 条「文档里的能力」一样：**一个中间层丢了，上层的能力就静默失效。**

**教训一**：**测试调用带副作用的函数时，副作用也得被夹具罩住**，不能只罩住它的返回值。
`subprocess.run` 打了桩 ≠ 这个函数不会碰文件系统。而且**这类 bug 一声不响**——
测试全绿，出事的地方在开发机上。

**教训二**：**「探活失败」和「没在跑」不是一回事；护栏沉默时要当它没检查过，
不能当它通过了。** 以后再看见「改完没生效但测试是绿的」，**先去看监听那个端口的
是哪个 pid、它几点起的**（`netstat -ano | grep <端口>` +
`Get-Process -Id <pid> | Select StartTime`），别急着怀疑代码——
这次的时序一眼就能看出进程比代码老 15 分钟。

**还没改的设计洞（记在 [`03_问题记录.md`](03_问题记录.md) 待解决第 5 条）**：
`stop_service()` 在探活返回 `None` 时会**顺手 `clear_service_info()`**，
把 pid 一起删掉。探活瞬时失败（0.5 秒连接超时、服务正在启动）和服务真没在跑，
在它眼里是同一件事——**一旦文件先没了，那个进程就再也不好停了**。

## 六、文档与设计

### 22. 文档从 A 跳到 B，中间那一步没人写

早先的设计写着：「可复用知识**抽到** `20_知识/`，两边用双向链接**互指**」（`10_项目/` + `20_知识/` 时代，该结构已取消）。

**问题**：它从「抽到」直接跳到了「互指」，中间那一步没写——**项目那一侧留什么？** 要让「两边」互指，两边就得都有文件。「精简」这个词在全部文档里**一次都没出现过**。

**为什么没人发现**：因为两边看起来都自洽。

**教训**：这类「A 到 B 之间的动作没写」的漏洞，**只能靠一次端到端实跑才暴露**。写流程时每一步都要问「这一步的输入是什么、输出是什么」。

### 23. 万能兜底分类注定变垃圾桶

原方案的目录里有个「其他分类」——**凡没明确归属的都往里塞**。

**修法**：改名 `30_素材` 并限定语义为「创作素材」。

**这条在结构重订后依然适用**：不允许出现「其他」「杂项」这类领域。

### 24. 两份约定会漂移

**vault 里不放任何规则文件**（没有 `CLAUDE.md`，没有使用说明）。

理由：vault 一份、服务代码一份，**改了一边忘了另一边**，就会留下一份**没人读又会说错话的文档**——比没有更危险。

**边界因此清晰**：数据在 vault，规则全在服务侧。换库、重建库都不牵动规则。

### 25. 作废的条目：先保留，后改成删

结构重订时一大批旧决定作废了（`10_项目/`、项目笔记命名、抽离……）。当时的做法是**标 `【作废 YYYY-MM-DD】` + 一行原因，内容保留不删**，理由是「当初为什么那么想」比结论本身有用。

**2026-09-17 反过来了：作废的条目直接删。**

理由：攒了一批之后，文档变成**一半还算数、一半不算数**——人和读文档的 AI 都得先逐条判断哪条有效，**判断成本超过了存根的价值**。而真正值得留的**跨越规则存废的洞察**（比如上面第 10 条的判据），本来就该单独拎出来，不该指望读者从作废条目里自己捞。

**只保留一条**：编号空缺不补——免得旧讨论、commit message、其它文档里的引用全部对不上。

## 七、前端

### 26. `async` 函数不能直接喂给 `onsubmit="return ..."`

**踩到的**：设置窗的保存写成 `onsubmit="return saveSettings(this)"`，而 `saveSettings`
是 `async`。**`async` 函数返回的是 Promise——对象，truthy**，`onsubmit` 拿到它判断不出
「要不要取消默认动作」，于是**表单按原生 GET 提交，整页跳走**，函数体里那句
`return false` 根本没被用到。

**症状极有迷惑性**：保存**是生效的**（`fetch` 也发了、服务端回了 200），只是页面一跳、
什么反馈都没有。**很容易被误判成「保存没反应」而去查后端。**

**更要命的是连带泄露**：表单里那个密码输入框带 `name`，原生 GET 提交会把它塞进
URL 查询串——**用户刚填的 API Key 明文进了浏览器历史、地址栏补全、以及任何记
访问日志的一层**。

**修法**：`onsubmit="saveSettings(this); return false"`（分号，不是 `return` 那个函数）。
或用 `event.preventDefault()`。**别改成 `type="button"` + `onclick`**——那样回车提交就没了。

**为什么自检没抓到**：程序化 `form.submit()` **会绕过 `onsubmit`**，`.click()` 与真鼠标
点击在导航行为上也不等价。**「页面没刷新」这种断言，只能用真鼠标事件（如 CDP 的
`Input.dispatchMouseEvent`）配 `frameNavigated` 监听来验。**

**教训**：`onsubmit="return f()"` 里那个 `f` **必须是同步的**。它是唯一能取消默认动作的
时机，一旦 `f` 变成 `async`，取消就静默失效——而**代码看起来一点问题都没有**。

### 33. 「只有人眼看得见」的东西，多半能用无头 Chrome 看

第 26 条最后留了一句：页面跳没跳、窗口闪没闪，「只能用真鼠标事件配 `frameNavigated` 去验」。
第 32 条也留了一句：「窗口真的不闪了只能靠人在真网页上点一次」。**两句都对，但当时都停在了
「测不了」——其实只是没去找那一步。**

2026-09-20 改「思考中…」「整理中…」两个 JS 和 `.new-chat` 的边框时补上了。**不用装
playwright/selenium**（这个项目没那两条依赖），本机 Chrome + Node 25 自带的 `WebSocket` 就够：

```bash
# ① 截屏：一眼看版式对不对
chrome --headless=new --disable-gpu --hide-scrollbars \
       --user-data-dir=<临时目录> --window-size=1280,760 \
       --screenshot=out.png http://127.0.0.1:51823/?new=1

# ② 驱动：加 --remote-debugging-port=9222，再用 CDP
#    Runtime.evaluate 里 dispatchEvent(...)，读回 DOM 状态即为断言
```

`--user-data-dir` **必须给个临时目录**，否则会拿你正在用的 Chrome 配置起来，可能弹窗、
也可能和已开的窗口打架。

**这次真验出来了三条**，其中一条是只有跑起来才会想到的：

| 验的 | 结果 |
|---|---|
| 点发送 → 追加「你那句 + 思考中…」、按钮禁用、空状态被移除 | ✅ |
| 点投递 → 提示变「整理中…」、按钮禁用 | ✅ |
| **空正文点投递 → 什么都不该变** | ✅ 按钮没禁用、提示没动 |

最后那条是重点：**空提交服务端会回 400，但画面上先说「整理中…」就是骗人**。
只读代码不会想到去问「空的时候呢」。

**一个顺手的好性质**：`dispatchEvent(new Event('submit'))` 是**不可信事件**——
处理器照跑，但**浏览器不会真的提交**。既能验处理器，页面又不会跳走，
正好卡在「想看处理器干了什么」这个位置上。（要验**真提交**（跳转、URL 里带什么），
那还是得第 26 条那条 `Input.dispatchMouseEvent`。）

**最值钱的一条**：**有具体的像素怀疑时，先截图看一眼。** 用户说「开始新会话加个框啊，
它是个按钮」，而代码里 `.new-chat` **明明写着 `border: 1px solid #cfdeee`**——
看着一点问题都没有。截图才看清：`#cfdeee` 边框配 `--blue-tint` 底（`#f7fafd`）
摆在 `--paper`（`#fbfcfe`）上，**差 4 个色阶，等于没有框**，画面上就是一行蓝字。
那套淡皮只在**白底卡片**里成立（设置窗、巡检页就是这么用的），**别往 `--paper` 上放**。

**再补一刀（同一天稍后）**：改成「实蓝边 + **白底** + 蓝字」（抄的是 `button.primary`）——
框**看得见**了，无头截图里清清楚楚一根蓝线。用户还是说「**还是一个链接的样子**」。
这才想明白：**「像按钮」靠的是底色，不是边框。** 对照左栏的「记一条」和右下的「发送」，
**能按的东西都铺着底**；白底 + 一根细线，在近白的页面上永远读成「描了个框的链接」。
最后铺上 `--blue-soft`，一次就对了。

所以这同一个东西踩了两遍：第一遍错在**对比度**，第二遍错在**把「有边框」当成了
「像按钮」的充分条件**。

**教训**：**「人眼才看得见」通常只是「还没找到无头浏览器里对应的那一步」。**
真剩下来非人不可的才是例外（比如第 32 条那个**窗口闪不闪**——它要一个真实的桌面，
无头浏览器里不产生窗口）。**能查的别交给别人查。**

> ⚠️ **但无头截图会拍到入场动画的第 0 帧。** `.card` 挂着
> `animation: card-in 260ms var(--ease) both`，而 `card-in` 是 `from { opacity: 0 }`
> ——`both` 意味着**动画跑完前它一直停在全透明**。`--screenshot` 在 load 事件一结束就拍，
> 于是卡片一个都看不见。2026-09-20 我据此差点报一个「整理日志主区是空的」的假 bug：
> 其实 DOM 里卡片好好的，`getBoundingClientRect()` 有高度、`getComputedStyle` 也取得到
> 背景色——**只有像素是空的**。
>
> **截图要加 `--virtual-time-budget=2000`**，把虚拟时间推过去再拍。
> 同理，**「截图里没有」不等于「没画出来」**——两者都要再往下证一层。

### 34. 静态资源不发 `cache-control`——改了 CSS，刷新看不到

**踩到的**：`.new-chat` 的样式改了两轮，用户两轮都说「没变」。而服务端发的 HTML 和 CSS
都是新的，全新 profile 的无头浏览器截出来的也是新样式——**两边都对，他那边的屏幕还是旧的**。

Starlette 的 `StaticFiles` **只发 `etag` 和 `last-modified`，不发 `cache-control`**
（`curl -I` 一看就明白；testclient 里更直接——`r.headers["cache-control"]` 抛 `KeyError`，
**这个键压根不存在**）。而**没有 `Cache-Control` 的响应，浏览器会启用「启发式缓存」**：
按距 `Last-Modified` 的时长自己推算一个有效期，**期间根本不问服务端**，`etag` 也就无从校验。

**修法**：一个小中间件，给 `/static/` 一律回 `Cache-Control: no-cache`。
`no-cache` **不是**「不缓存」，是「用之前先问一句」——本地服务，一个 304 不要钱，
换来的是**改完刷一下就是新的**。

**教训**：**「我改了、他看不见」时，先把「我以为发出去的那份」和「他实际拿到的那份」分开。**
服务端 `curl` 验过、无头浏览器（全新 profile）截图也验过，**那两环都硬**——
可用户屏幕上是**第三份：浏览器自己存的那份**，我一次都没查过。
**验证链上少一环，前面几环再硬也白搭。**

> ⚠️ 说清楚：**「就是缓存害的」我没能证实**——他清除缓存前看到的到底是哪一版，无从回溯。
> 但「没有 `cache-control` 就一定有启发式缓存」是查得实的，这个缺口本来也该补。
>
> 这类坑对**样式**尤其毒：样式错了，页面上表现出来只会像「**功能没做**」，
> 而代码、模板、接口、测试全是对的——和 `docs/03` 第 5 条那个**旧服务**是同一种形状。

## 八、配置

### 27. 重读配置不能用 `load_dotenv`——它是 `override=False` 的

**踩到的**：设置页保存后要重载配置，第一版想当然地又调了一次 `load_dotenv`——**改了文件也读不到新值**。

**根因**：`load_dotenv` 默认 `override=False`——**已经设过的环境变量它不覆盖**。第一次加载把值写进了 `os.environ`，第二次就什么也不做，重载成了空转。

**修法**：用 `dotenv_values(env_file)`——直接解析文件、**返回 dict、不碰 `os.environ`**。顺带还避免了重载污染进程环境。

**教训**：「读配置」和「重新读配置」不是同一个动作。库函数的默认行为是按「只读一次」设计的，第二次调它得先问一句「**它会不会真的再读一遍**」。这条有测试钉着（把 `reload_config` 改回走 `load_dotenv`，那条用例会红）。

## 十一、Windows 平台

### 29. `.bat` 结尾的 `endlocal` 会把退出码抹成 0

**踩到的**：加 `kb drop` 时，删一个不存在的 id 该返回 1。CLI 里 `main()` 明明
`return 1`，直接调 Python 也确实是 1——**但从 `kb.bat` 走一道，回来永远是 0**。

**根因**：`endlocal` 会把 `ERRORLEVEL` 重置成 0。而三个 bat 的骨架都是
`setlocal` … `endlocal` 结尾，于是**它们从来没有把失败传出去过**。

**这不是 drop 引入的**——它一直如此。受影响的早就不止一条：

| 命令 | 本来该返回 | 实际返回 |
|---|---|---|
| `push` 正文为空 | 2 | 0 |
| `organize` 全失败 | 1 | 0 |
| `drop` 有 id 找不到 | 1 | 0 |

**在任何按退出码判成败的脚本里，`kb.bat` 都在报假成功。**

**修法**：**在 `endlocal` 之前**把码存进变量，然后一行里 `endlocal` 和 `exit /b` 一起走：

```bat
set "KN_RC=%ERRORLEVEL%"
endlocal & exit /b %KN_RC%
```

**为什么 `&` 能保证顺序**：cmd 是**先展开整行、再逐条执行**。`%KN_RC%` 在
`endlocal` 清掉它之前就已经展开成值了。这是 cmd 里的固定写法，不是碰巧。

**教训**：「没报错」和「报的是成功」是两回事。**一个只会返回 0 的包装层，
比一个会崩的包装层更难发现**——它把下面所有命令的失败都伪装成成功。
验证退出码时**必须走真实入口**（`kb.bat`），不能只测 `main()` 的返回值：
那中间隔着一层平台,**测试全绿和线上正确之间正好差着这一层**。

### 30. 文档里写着的能力，不等于实现了

**踩到的**：`01_架构.md` 的写入流程图里一直写着，收件箱「**留反悔窗口：可编辑、可删除、可合并**」。
而实际上 `kb` 只有 `push / organize / inbox / search / web / sweep / status / stop` 八条——
**一条都撤不回来**。这份文档我反复读过好几遍，从没觉得不对。

**这不是笔误**：那句话写的是**设计意图**，意图本身没错。错的是它和已实现的能力
**长得一样**——读的人分不出「打算这么做」和「已经这么做」。

**教训**：**文档里写下的每一项能力，都要能指到一段代码或一条 `#编号`**。
指不到的，要么标上「未实现」，要么删掉。设计意图可以写，
但**写完就得有人负责把它变成代码，或者明确承认它是空的**——
否则它会安安静静地骗过每一个读它的人，包括写它的人。

**同一个坑的第二种形态（2026-09-18，Q101）：提示词里让模型填的字段，代码根本不接。**

提示词的 JSON 契约里有一个 `target_tags`，规则 7 整条在讲怎么填它。模型老老实实算了
路径派生标签加语义标签——而 **`OrganizePlan` 根本没有这个属性**，`parse_plan` 不读，
全项目零消费者。**模型的生产被静静丢进垃圾桶。**

比文档那种更隐蔽：文档写了没人读，你翻一眼就知道；**模型填了没人接，没有任何东西会报错**，
只会表现为「标签怎么老是缺」。而且它还骗走了模型的注意力——同一件事让它填了两遍，
一遍有效、一遍作废。

**教训**：**给模型定契约时，每个字段都要能指到一个消费者。** 指不到的删掉——
留着它不只浪费，还会掩盖真正的字段为什么是空的。

### 31. 脚本里「读进来再写回去」，顺手改掉的不止你想改的那一个词

**踩到的**：做变异验证（改掉提示词里一句话、看测试变不变红）时，图省事用了
`p.write_text(p.read_text().replace(...))`。测试如期变红，改回来，一切正常——
**直到 `git diff` 冒出一行警告**：

```
warning: in the working copy of 'src/kb/core/planning.py',
         CRLF will be replaced by LF the next time Git touches it
```

一查，**整个文件 391 行全成了 CRLF**，而库里其它 `.py` 全是 LF。

**根因**：`Path.write_text` 在 Windows 上按文本模式打开、`newline=None`，
写出去的 `\n` 会**逐行翻成 `\r\n`**。我只想改 6 个字，实际重写了整个文件的换行。

**这次没出事，纯属侥幸**：`core.autocrlf=true` 会在提交时把 CRLF 归一成 LF，
所以 `git diff` 里干干净净，只有那行警告。**换台机器（`autocrlf=false`）
或者换个文件类型，就是一次 391 行的伪改动**——review 时根本看不出真正改了什么。

**教训**：**「改一个词」和「重写整个文件」是两回事，别用后者的手段干前者。**
用脚本改文件时，读写的 `newline`（还有 BOM、编码）都要显式写死，
或者干脆用 `Edit` 工具做精确替换。**尤其别在验证性脚本里这么干**——
那种脚本的产物本来就该原样还原，多出来的副作用最容易蒙混过关。

### 32. 后台服务每调一次 `git`，就闪一个黑窗口

**踩到的**：用户报「投递之后会闪出好几个终端窗口，虽然都是一闪而过」。

**根因是一条链，缺一环都推不出来：**

1. 服务是 `kb web` 拉起来的，`spawn_service` 用 **`DETACHED_PROCESS`** 起它——
   这个标志的语义是「**不要控制台**」，服务进程没有 console。
2. 一次投递要调**好几次** `subprocess.run`：`git rev-parse`（猜项目名）、
   `git ls-files` + `git add` + `git commit`（落盘）。**全都是控制台程序**。
   （`taskkill` 那条在停服务时，同一个毛病。）
3. Windows 的规矩：**一个没有 console 的进程去起一个控制台程序，系统会给它新分一个
   console**——那个新 console 就是一个真的窗口，起来、闪一下、随着子进程退出而消失。

于是「一次投递」= 好几个黑窗口此起彼伏。**平时看着像灵异现象，其实每一步都合乎规矩。**

**修法**：给这些子进程加 `creationflags=CREATE_NO_WINDOW`，集中放在 `kb/proc.py` 的
`proc.NO_CONSOLE`（非 Windows 上是 `0`），三个调用点各自引用——**不是一个地方写死常量**，
免得下次新增 `subprocess.run` 时又漏一个。

**教训**：**在 Windows 上「没有控制台」是要主动声明的，不是默认状态。**
`DETACHED_PROCESS` 只保证了服务自己不长窗口，**对它起的每个子进程都无效**——
反而正是「服务没有 console」这件事，把子进程从「共享父进程的 console（无窗口）」
推成了「另分一个（有窗口）」。

**顺带一条**：这个坑**测试永远测不出来**——测试进程有 console，窗口压根不会出现。
所以 `tests/test_proc.py` 能验的只有「`creationflags` 有没有传下去」（monkeypatch
`subprocess.run` 看 kwargs），**「窗口真的不闪了」只能靠人在真网页上点一次投递**。
分不清这两类断言，就会拿「测试全绿」去担保一件它根本没管的事。

（**别把这条推得太广**：无头浏览器看不见窗口，但**别的「人眼才看得见」多半能验**——
版式、点了之后 DOM 变没变、提示文字对不对，都能用无头 Chrome 看。见第 33 条。）
