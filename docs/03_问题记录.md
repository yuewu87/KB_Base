# 二、知识库定位

### Q5. 知识库主要装什么内容？

**A：** 内容很杂，包括个人学习笔记、专业领域资料库、项目/研究沉淀、通用第二大脑。允许**多分级**。

### Q6. 知识库主要给人用还是给 AI 用？

**A：** **人机共用**（路线 B）。不是纯 AI 检索库。

### Q7. Obsidian 是必要的吗？

**A：** 分对象看：
- **对 AI 不必要**——AI 直接读文件系统就够了。
- **对人必要**——在「人机共用」定位下，Obsidian 承担人的阅读、编辑、反链、搜索界面。自建同等能力的 GUI 是几个月的活。

### Q8. 知识库的本体是什么？

**A：** 是 `E:\KB_Library` 里的 **markdown 文件 + 目录结构 + frontmatter 字段**，不是 Obsidian。Obsidian 只是这些文件的一个视图，可随时卸载，文件仍在。这也是选本地 markdown 而非数据库的原因：AI 友好、可读、无锁定。

# 三、写入流程

### Q15. 「用大模型写入」具体指什么？

**A：** 分两层：
- **第一层**：在对话中总结（人的判断力介入，降噪）
- **第二层**：按规则写入库里（追求确定性、可重复、可校验）

### Q16. 两层之间怎么衔接？

**A：** 必须有一个**结构化接口**。第一层的产出不能是散文，得带固定字段（来源 / 一句话摘要 / 建议分类 / 关联笔记）。否则第二层没有判断依据，「按规则」无从谈起。

### Q17. 写入的节奏？

**A：** **随手记草稿 + 末尾转正**。会话中说「记一下」即落草稿，不打断思路；末尾统一转正。

### Q18. 要不要草稿区 / 收件箱？

**A：** 要。收件箱是**所有未定稿内容的统一入口**，agent 投递的和人手写的共用同一个 `_收件箱/`，不分开——本质状态一致，分开只会让人每次纠结「该放哪」。收件箱**空的才是健康状态**。

### Q19. 转正前要不要逐条确认？

**A：** 不要。**报告是事后通知，不是事前审批单**。服务把活干完 → git commit → 给报告。用户扫一眼，不对再按 commit 回退。逐条拍板太麻烦。

### Q20. 归不了类的内容怎么办？

**A：** 不阻塞。**不进正式区**，留在 `_收件箱/待归类/`，报告里列出。可当天处理，也可攒着集中看。AI 不得自行发明分类。

### Q21. 允许产生孤儿笔记吗？

**A：** 不允许。每条正式笔记至少链到一处已有笔记或 MOC 页。孤儿是检索不精准的根因。

### Q22. 投递后能不能反悔？

**A：** 能，且必须能。异步缓冲的意义就是留反悔窗口。收件箱条目在整理前必须**可编辑、可删除、可合并**。否则错的结论只是被延后固化。

# 四、字段与模板

### Q23. 「我的判断」字段是谁的判断？

**A：这一节已于 2026-09-18 删除——它没被用起来。**

**原来的设计。**（字段名已由「我的判断」改为「用户的判断」。）这一节记录**用户本人的立场**，内容须来自对话中用户说过的话，**AI 不许代填**。代填等于伪造用户观点，将来回看时分不清哪句是自己想的。

首次真实 LLM 运行就违反了这条：用户投递的只是一句事实陈述（「并发写入会锁表，用队列串行化解决」），模型却写了一整段「用户认为……」，还追加了两点用户没说过的话。

加一条提示词硬规则后再试，**仍然被代填**——模型面对一个空标题的默认行为就是填满它，而「用户陈述的事实」与「用户的观点」这条界线对它太模糊。

最终定案（2026-09-15 补充，Q58）：**服务在落盘前机械清空该节正文，只保留标题**（`planning.strip_user_judgment`），由用户自己在 Obsidian 里写。机制上不可能伪造，不依赖模型自觉；提示词里仍留一条（规则 8）说明「写了也会被丢掉」，避免模型浪费输出。

**2026-09-18 删除。** 理由是**它从来没被填过**：全库 48 篇笔记，这一节**一次都没写过内容**，每篇都只挂着一个空标题。设计前提是「用户会自己在 Obsidian 里写」——实际没发生，它净产出的只有噪音。

> 用户的话：「用户判断还是删了吧，基本不怎么看」。

**删掉的东西**：5 份模板里的 `## 用户的判断`、`planning.strip_user_judgment` 及其调用、提示词规则 8、相关测试。

> **防代填的机制一并不需要了**——没有那一节，就没有一个「等着被填满的空标题」在诱导模型伪造。当初那条提示词规则之所以失败，正是因为它在一个空标题上跟模型的默认行为对抗；标题没了，对抗的对象也没了。

### Q24. `类型` 字段的枚举？

**A：** `概念 | 踩坑 | 决策 | 经验 | 清单 | 日志 | 索引`。固定枚举，不许自由发挥——字段一旦失控，Dataview 查询和后续自动化全部失效。

其中 `日志`（Q50）和 `索引`（Q56）都属于**结构性文件**而非知识笔记；Dataview 查询知识时可按类型过滤掉。

- `日志` 于 2026-09-15 随 Q50 加入
- `索引` 于 2026-09-15 随 Q56 加入

后两者由**服务生成**，不由 LLM 产出——所以它们不在给模型的允许类型列表里。

### Q25. 检索主力是文件夹还是标签？

**A：** **`主题` 标签**。文件夹决定「物理放哪」，标签决定「属于哪些主题」。一篇笔记能挂多个标签，不能放多个文件夹。阶段一靠 Obsidian 搜索（`tag:#数据库`），阶段二作为 RAG 切片聚合依据。

> **2026-09-16 补注：结论不变，而且更重要了。** 新结构（[Q67](#q67-目录结构重订)）以领域为一级目录、领域内分类由 LLM 自建，**文件夹会自己长**——正因为如此，「检索不靠文件夹」这条成了容错的前提：文件夹放错了只影响人翻目录，不影响检索。
>
> **连带问题已定（2026-09-17）：** 领域化之后标签从哪来——**路径派生与 AI 另提，两者都要**。见 [Q76](#q76-主题标签从哪来)。

### Q26. 模板文件放哪？

**A：** 先放**服务代码仓库里**，但以 **`.md` 形式**存在，代码读取。便于修改。

# 五、系统架构

### Q27. 谁来整理知识库？

**A：** **独立服务 + 自带 LLM（API key）**，专职整理，不占用各会话的额度与上下文。各会话 agent 只负责投递，不懂整理规则。

关键转变：把「整理」从**会话行为**变成**服务行为**，规则收拢到服务一处维护。

### Q28. 接口形式？

**A：** 三层，共用同一份逻辑：

| 层 | 谁用 | 通用性 |
|---|---|---|
| **CLI** | 任何能跑 shell 的 harness | **最通用** |
| **HTTP REST** | 任何能发请求的工具 | 底层，另两层都调它 |
| **MCP server** | 支持 MCP 的工具（Claude Code、Codex CLI） | 体验最好，覆盖有限 |

目标：接入市面上大多数工具（Claude Code、DeepSeek harness、Codex 等）。
**CLI 才是最通用的一层**，因为「能跑 shell」几乎是所有 agent harness 的底线能力。

### Q29. 写入如何保证一致性？

**A：** 所有写入**必须经过服务进程**，CLI 和 MCP 都走 HTTP，不直接碰文件。服务没启动时 CLI 报错并提示，而不是自己偷偷写。这样写入天然串行化，不会出现两份逻辑打架。

### Q30. 各 harness 怎么知道何时投递？

**A：** 定案（2026-09-15）。这个问题实际包含**两半**，阻塞性不同，分开处理。

#### ① 接口侧 —— 阻塞最小闭环

**命令形态：**

```bash
kb push --content "并发写入会锁表，最后用队列串行化解决" \
        --project "电商后台" --source 会话

# 长内容走 stdin，避免转义麻烦
echo "..." | kb push --project "电商后台"
```

- **一次投递 = 一条草稿**，多条就调多次。CLI 越简单，agent 越不容易用错。
- 返回：`已收，id=20260915-a3f2`。异步立刻返回，不阻塞会话。

**投递内容格式：agent 只交正文，其余服务推断。**

- 必填：正文
- 可选：`--project`、`--source`
- **禁止让 agent 填 `类型` / `主题` / 建议分类** —— 那等于把整理判断泄漏到每个会话，与服务收拢规则的设计相悖。

**项目名映射规则：**

- agent 报项目名，**默认取 git 仓库根的目录名**（`git rev-parse --show-toplevel` 的 basename），**不是 cwd 的 basename**——避免 agent 停在子目录（如 `src/kb/core/`）时取到 `core`。非 git 仓库时回退到 cwd basename。
- **项目名可选**：`--project` 不给也能投，一律按内容归领域。
- **匹配前规范化**：统一转小写、`-` 与 `_` 视为等价，避免 `KN_Base` / `kn_base` / `KN-Base` 被当成三个项目。规范化后**只用于标签去重**——`项目` 只是 frontmatter 字段和标签，**不影响笔记的物理位置**（[Q68](#q68-项目降为标签)）。
- 归不了类的落 `_收件箱/待归类/`（[Q70](#q70-功能目录去编号)）。

#### ② 提示词侧 —— 不阻塞，且现在写太早

每个 harness 一份说明（Claude Code → skill；Codex → `AGENTS.md`；其他 → 通用说明），放 `docs/接入指南/`。

**但必须等接口稳定并跑通之后再写。** 接口没定稳就写说明书，必然是照着猜写的，接口一改全部过时。说明书应当是「描述既成事实」，不是「承诺未来行为」。

### Q31. 管理界面？

**A：** **本地 Web UI**，一个 `.bat` 启动，模块化设计。首批功能：配置页、工作记录。其他功能后续再说。

内容侧界面（阅读、反链、工作记录看板、待归类看板）**由 Obsidian + Dataview 承接**，不重复造。

### Q32. 密钥与配置放哪？

### Q49. 自动寻找到的端口，CLI 怎么知道？

**A：** 定案（2026-09-15）。服务启动后在工程目录写一个**运行时文件**：

```
KN_Base/runtime/service.json     # { "port": 51723, "pid": 12345, "started": "..." }
```

CLI 的流程：读 `runtime/service.json` → 拿端口去探测 → 通就直接投递；不通（或文件不存在）就后台拉起服务、等服务写好文件、再投递。

这个文件**不入库**（加入 `.gitignore`）。放在工程目录而非用户目录，同样是为了「配置集中在一个文件夹」。

### Q50. 工作日志（整理日志）怎么办？

**A：** 定案（2026-09-15）。

**位置与粒度**：`_索引/整理日志/2026-09-15.md`，**按天聚合**——每次整理往当天那篇追加一节。

理由：调试期一天可能整理十几次，按次会产生一堆碎片文件；按天回看也顺。与「一次整理 = 一个 commit」不冲突，commit 里包含日志文件的那次追加。

**内容**（带 wiki 链接，Obsidian 里可点击跳转）：

```markdown
## 14:32 整理 3 条草稿

- 新建 [[并发写锁]]
- 合并入 [[XXX-踩坑]]
- 更新 [[_索引/计算机]]
- 待归类 1 条：……
```

**失败也记**。日志是审计记录，只记成功的话，回头看会不知道当时为什么有东西卡在收件箱。

**报告与工作日志同源**：服务产生一份「整理结果」结构，然后两个出口——渲染成文本给会话（报告），渲染成 markdown 进 vault（工作日志）。**不写两套逻辑**，否则会出现报告说「新建 3 篇」而日志写 4 篇这种对不上的情况。

**`类型` 字段取 `日志`**，因此枚举扩充为 6 个值（见 Q24）。

### Q51. 运行日志怎么办？

**A：** 定案（2026-09-15）。`KN_Base/logs/kb.log`，标准 Python logging，按大小轮转保留若干份，默认 INFO、可配 DEBUG。`logs/` 加入 `.gitignore`。

**核心约束：运行日志绝不能进 vault。** 一旦进去就成了笔记，会被检索、被 RAG 切片、被 AI 当作知识。技术日志是噪音，属于垃圾进垃圾出。

**两者不能混为一谈：**

| | **工作日志** | **运行日志** |
|---|---|---|
| 是什么 | 「什么时候整理了什么」，审计记录 | debug / info / error，技术排查用 |
| 谁看 | 用户 | 排查故障时 |
| 是不是知识 | 是，可被检索、阶段二可被 RAG 召回 | 不是 |
| 住哪 | vault 内（`_索引/整理日志/`） | vault 外（`KN_Base/logs/`） |
| 保留 | 长期 | 轮转，保留 N 份 |

> **2026-09-16 扩展：日志从两层变三层。** 新增**流程日志**（每一个流转：谁发了什么命令、分给谁、谁做了什么、怎么返回），落在服务侧存储，**同样不进 vault**。整理日志与流程日志在 Web UI 上同一页展示（卡片颜色区分），但**存储必须分开**。见 [`01_架构.md`](01_架构.md) 第十节。

### Q52. 测试策略？

**A：** **全 mock LLM**（2026-09-15 确认）。LLM 调用全部替换为返回固定变更计划的假实现，在此基础上对校验层、落盘层写真实测试。

- 快、免费、稳定，可随时跑
- 真实 LLM 的效果靠手动端到端验证

**理由：** 真实 API 慢、花钱、结果不稳定，不适合作为自动化测试的基础。而整理逻辑的正确性（校验、落盘、回滚）本就不该依赖具体模型的输出——这正是 Q33 把 `llm/` 做成抽象层的原因。

### Q53. vault 的 `.obsidian/` 要不要入库？

**A：** **部分入库**（2026-09-15 确认）。

- **入库**：`app.json`、`community-plugins.json`、插件配置等——换机器时设置基本能跟着走
- **忽略**：`workspace.json`、`cache` 等频繁变动的文件

**理由：** `workspace.json` 记录「哪个面板开在哪」，每次开关 Obsidian 都会变。全部入库会让 git 历史被这种噪音淹没，真正的内容变更反而难找。

### Q54. LLM 怎么调？

**A：** **`openai` SDK + 兼容端点**（2026-09-15 确认）。`base_url` 指向 DeepSeek 的 OpenAI 兼容端点。

**理由：** Q35 要求「后续兼容其他模型」。openai SDK 已是事实标准，市面上多数供应商都提供兼容端点——将来换供应商只改 `base_url` 和模型名，`llm/providers/` 的代码几乎不动。

### Q55. 草稿文件的格式与流转？

**A：** 定案（2026-09-15）。

**文件名 = id**：`_收件箱/20260915-a3f2.md`
id 规则：`YYYYMMDD-` + 4 位随机十六进制。用 id 而非「日期+摘要」作文件名——id 是对外接口（`kb organize <id>`），文件名与之一致最不容易出错；草稿生命周期短，可读性由 Dataview 看板提供。

**内容 = frontmatter + 正文原样：**

```markdown
---
状态: 待整理
id: 20260915-a3f2
来源: 会话
项目: 电商后台
投递时间: 2026-09-15 14:32
---

（agent 投递的正文，原样保存）
```

**正文绝不改写** —— 改写属于整理阶段。投递阶段服务只负责落盘，保证投递是纯粹的、无判断的，否则投递行为就不可预测了。

字段中没有 `类型` / `主题` —— 那些是整理阶段才产生的（见 Q30：agent 不许填，服务在整理时推断）。

**两种「卡住」的流转：**

| 情况 | 原因 | 去向 |
|---|---|---|
| 整理失败 | LLM 报错 / 格式不合规 | 原样留在 `_收件箱/`，下次重试 |
| 归不了类 | LLM 正常但判断不了归属 | 移到 `_收件箱/待归类/` |

**`kb organize` 扫描 `_收件箱/` 及其 `待归类/` 子目录，且每次重新尝试。** 理由：库会长大——三个月前归不了类的笔记，可能因后来新增了相关笔记而变得可归类。不重试就永远卡着。重试失败的继续留在 `待归类/`，代价只是一次 LLM 调用。

### Q56. 索引页（MOC）从哪来？

**A：** 定案（2026-09-15）。**服务在需要时自动创建** `_索引/<主题>.md`，内容是 Dataview 查询——零维护，永远自动列出该主题下的所有笔记，不需要人工往上加条目。

> **2026-09-17：已定。** 索引页**按现有目录分**（一个目录一个），巡检时顺手更新。见 [Q79](#q79-_索引-索引页按什么出)。

**为什么必须自动建：** Q21 定了「不允许孤儿笔记」，但**空库第一天没有任何笔记可链**，第一条笔记必然违反该约束。索引页自动生成后，第一条笔记就有东西可链，约束从第一天起成立。

**幂等：** 已存在的索引页原样返回，**不覆盖**——用户可能自己改过。

**`类型` 字段取 `索引`**，枚举扩充为 7 个值（见 Q24）。

索引页由**服务生成，不由 LLM 产出**——它不在给模型的允许类型列表里。是否需要新建索引页，由服务在落盘时按「frontmatter 的 `主题` 是否对应既有主题目录」决定。

### Q57. 依赖版本怎么管？

**A：** 定案（2026-09-15）。**顶层依赖写下界 + 关键包上界。**

`requirements.txt`：

```
fastapi>=0.141
uvicorn>=0.53
jinja2>=3.1
python-dotenv>=1.0
openai>=3.14,<4
python-frontmatter>=1.3
httpx>=0.28,<1
pytest>=9,<10
```

**背景：** 原计划 Step 2 写「版本先不锁，装完后用 `pip freeze` 回填」，Step 12 却把 freeze 产物 `requirements.lock.txt` 加进了 `.gitignore`。两条合起来的效果是**顶层依赖永远不锁**，「回填」这个动作没有归属。这是计划自身的矛盾，在 Task 1 的代码质量审查中被发现。

**为什么只给 `openai` 加上界：** 大版本破坏性变更最容易发生在 `openai` 这类快速演进的 SDK 上（当前 3.14，跨到 4.x 是迟早的事）。其余几个 API 相对稳定，加下界防「装到过老的版本」即可，加上界反而会挡住安全补丁。

**锁文件：** `requirements.lock.txt`（`pip freeze` 产物）继续不入库——它含平台相关包，跨平台没有意义。

### Q33. 为什么 `core/` 不许依赖 web/api？

**A：** 硬约束。整理是这套系统最容易出错的部分，必须能脱离界面单独跑测试。`core/`（领域逻辑）不 import `web/` 或 `api/`，`llm/` 是抽象层，`api/` 和 `web/` 都是只做协议转换的薄层。

### Q48. vault 里要不要放 CLAUDE.md？

**A：** **不放**（2026-09-15 确认）。vault 保持**纯数据**——只有 markdown 文件、目录结构和 `.obsidian/` 配置，**不含任何规则或说明**。

理由：

- **服务不读它**。服务的规则在代码和 `templates/` 里（见 Q26），与 vault 中的文件无关。
- **不产生会话**。整理走 API key，人通过 Obsidian 读写，不在 vault 目录开 Claude Code 会话，没有会话需要加载它。
- **两份约定会漂移**。vault 一份、服务代码一份，改了一边忘了另一边，就会留下**一份没人读又会说错话的文档**——比没有更危险。

边界因此变得清晰：**数据在 vault，规则全在服务侧。** 换库、重建库都不牵动规则。

# 六、本轮新增决策

### Q34. 分期范围？

**A：** **先最小闭环**：vault 骨架 + 服务核心 + CLI 投递 + 异步整理。先把「投递 → 整理 → 落盘」跑通。Web UI、MCP、撤回界面排在其后。

理由：整理质量是成败点，得先能跑起来看到真实效果，再包界面。

### Q35. LLM 选型？

**A：** **deepseek-flash**，API key 由用户自己填。**后续要兼容其他模型**，因此 `llm/` 必须是抽象层，换供应商不改上层。

### Q36. 查重怎么判？

**A：** **两段式**：
1. **预筛（便宜）**：`主题` 标签重叠 + 标题关键词，从全库捞候选（5-10 篇）
2. **判定（LLM）**：只把候选笔记的「一句话结论」和新内容一起给模型，判：完全重复 / 相关 / 全新

优点：**便宜**（只喂候选，非全库）、**可解释**（能说出为何判重）、**可演进**（阶段二把预筛换成向量召回，判定层不动）。

### Q37. 整理由谁触发？

**A：** **只能由用户触发**（2026-09-15 确认）。用户在会话中明确说「这条可以整理了」，agent 才调用工具触发整理。

与异步机制咬合：投递时先搁置（留反悔窗口），用户确认后才整理。

**硬约束：agent 不得自行判断某条总结「已经稳定了」就触发整理。** 否则与「用户决定」矛盾，异步缓冲也就失去意义。

> **2026-09-16 修订：本条的结论已被推翻。** 现定为**整理触发权归会话 AI**——时机由会话 AI 判断（暂停项目时、半天未整理等），用户也可主动发起；**发请求前必须先确认没有需要推翻的结论**。理由：这条最初防的是「把还没想清楚的东西固化」，而那个风险现在由那道前置确认承担，交给会话 AI 判断更省事。**触发条件写进会话层接入说明（见 [Q62](#十一架构扩张决议2026-09-15-第二轮)）。** 原文保留，供回看当初的顾虑。

### Q38. 整理是单条还是批量？

**A：** 两者都提供（2026-09-15 确认）——`kb organize` 整理全部待整理，`kb organize <id>` 只整理某条。

### Q39. 服务是常驻还是按需启动？

**A：** **按需自动拉起**（2026-09-15 确认）。

CLI 检测到端口无响应时，自动后台启动服务进程再投递。用户无需关心服务开没开，也不用开机常驻。

这样解决了「按需启动」与「各会话 agent 随时能投递」的矛盾：对用户是按需的，对调用方是无感的。

### Q40. 端口号？

**A：** 自动寻找未占用的端口。

### Q41. Web UI 用静态页面还是模板引擎？

**A：** **模板引擎打底 + 少量 JS 增强**（如 Jinja2）。

理由：配置页是表单、工作记录是列表，都是「读数据展示」型，模板引擎写起来快得多；**不需要引入前端构建链**（无 npm/vite），服务端单进程，符合「管理简单」。只有需要实时刷新的地方（如整理进度）才加 JS 轮询。

### Q42. Python 环境搭了吗？

**A：** 还没搭，可以用。环境名与版本见 Q2（已定：`kn_base` / Python 3.11）。

### Q45. 整理失败的兜底策略？

**A：** 定案（2026-09-15）。**核心手段：把 LLM 调用和文件写入彻底分开。**

整理拆成三段，前两段一个字节都不写：

**① 规划（只读）**——调 LLM 产出完整**变更计划**：哪些笔记新建、哪些改写、哪些链接要加、哪些 MOC 要更新。不碰 vault 文件。

**② 校验（只读，纯静态检查）**——不靠 LLM 自我保证，机器校验：
- `类型` 是合法枚举值吗
- 引用的笔记、分类真实存在吗
- 目标路径合法、无冲突吗
- 计划自相矛盾吗（同一条草稿被规划进两处）

校验不过就打回重来，**vault 一个字节没动**。这一步拦掉绝大多数幻觉类错误。

**③ 落盘（写入，不调 LLM）**——按计划执行纯文件操作。因为不调模型，是确定性的、快的、失败率极低的。「LLM 调到一半留半成品」不会发生，因为规划阶段根本不写。

**失败分级：**

| 失败类型 | 处理 |
|---|---|
| LLM 超时/限流/网络 | 指数退避重试 3 次 |
| 返回格式不合规 | 把错误信息喂回去让它自己修，重试 2 次 |
| 仍失败 | **按条隔离**——该条留在收件箱原样不动，其余条正常整理 |

按条隔离的意义：10 条草稿里 1 条判不了，不该拖垮另外 9 条。失败条目**什么也不写**（保持原样），所以下次重试天然幂等。

**回滚必须精确，不能用 `git checkout .`** ——那会把用户手动编辑、尚未提交的改动一起还原掉。

> 服务自己维护一份「本次操作的文件清单」：修改过的 `git checkout -- <文件>` 还原，新建过的直接删除。用户的未提交改动不受影响。

**崩溃残留：** 服务启动时检查 vault 工作区，若发现本次操作清单残留（= 上次落盘没跑完），**报告给用户决定**回滚还是保留，不自动处理——因为存在用户有未提交改动的可能，自动处理有风险。

### Q46. vault 的 git 提交策略？

**A：** 定案（2026-09-15）。**一次整理 = 一个 commit。**

理由：这直接支撑「报告是事后通知」的前提——收到报告后不满意，回退这一个 commit，整次整理干净撤销。若一篇笔记一个 commit，一次整理 20 篇就是 20 个 commit，历史全是噪音，回退还得挑。

Commit message 用中文，列出本次动了什么：

```
整理草稿 3 条

- 新建 计算机/git/暂存区是全有或全无.md
- 新建 艺术/透视/一点透视.md
- 更新 _索引/计算机.md
```

**配套三条规则：**

**① 服务只 `git add` 自己动过的文件，禁止 `git add -A`。**
否则会把用户正在编辑、尚未提交的笔记一起裹进这次「AI 整理」的 commit，历史就骗人了。

**② 服务使用独立的 git author（`kb-service`）。**
`git log --author=kb-service` 能一眼分出「AI 写的」和「我写的」，回顾和排查都用得上。

**③ 落盘前记录 HEAD，失败时按文件清单精确回滚**（见 Q45），不回滚清单之外的东西。

### Q47. 附件与媒体策略？

### 一条跨越了规则存废的判断标准

> **机械约束（文件名格式对不对、字段非空）→ 代码必须管；判断题（可不可复用、这条算概念还是踩坑）→ 代码管不了，只能写提示词。**

**这条跨越了具体规则的存废，是本轮最有价值的产出。** 项目里反复撞上：笔记文件名格式、内容可不可复用、`用户的判断` 代填（见 [`04_踩坑与经验.md`](04_踩坑与经验.md) 第 7–10 条），每一次都是因为没分清这两类，把机械约束当成判断题交给了模型。

**后来还在继续撞（2026-09-18，Q101）**：`主题` 与 `项目` 两个字段，明明是派生和搬运、一个字的判断都没有，却一直靠模型自觉填——`项目` 实测丢了 4 篇。判据没变，只是又一条规则被挪到了正确的一侧。

### Q60 的依据：Graphiti 的反面教材

调研查到 Graphiti（Zep）的双时态失效在生产上出过事故（[synapse 的事故报告](https://github.com/alexsh88/synapse/blob/main/docs/FINDING-silent-fact-loss.md)）：

> **被自动失效的事实里 70% 其实还是真的**（28/40，手工核对）。

根因是它的机制：挑「哪些旧事实该失效」时，候选集用**语义相似度**、**不要求候选与新事实共享同一个实体**，然后一次 LLM 调用返回一串**裸索引**（无理由、无置信度），系统照时间戳算术直接落。结果同项目内**只是用词相近**的两条互相误伤，常见形态是「更窄的新结论废掉更宽的真结论」。它还有个缺陷：失效判断**不留可复核的痕迹**。

**对我们的三条约束：**

1. 失效**显式指定**（`--revise`），不猜
2. 失效**留痕**（整理日志覆盖）
3. 链上每个 LLM 调用点都要有**确定性校验兜着** —— Q45 的三段式已经是这个形状，继续按它走

### Q91. 兜底分类名要不要拦？

**A：** **要，而且归代码。**

`validate_plan` 里加一条：`target_path` 的**目录**部分不许叫 `其他` / `其它` / `杂项` / `临时` / `未分类` / `misc` / `other` / `tmp` / `todo` 这些。

**文件名不查**——「其他语言怎么处理」是一篇正经笔记，不是兜底分类。

**为什么归代码不归提示词：** 名字里带这些词就是兜底，跟内容是什么无关，**是一眼可判的机械约束**。而模型看到一条装不下的内容时，最省事的做法就是往「其他」里一塞——**闸门要卡在它迈不过去的地方**。

### Q92. LLM 到底能不能自主新建目录？

**A：** **能，而且已经建过。**

2026-09-17 核查（此前一直以为不能）：

- `allowed_prefixes` 只要求「在某个**领域**下」，**领域内的子分类不做任何存在性检查**
- 目录由 `atomic_write` 的 `mkdir(parents=True)` 建出来
- Q30 那条「项目目录不存在就拒」**随项目层一起删了**
- 实证：`计算机/RPA/` 是模型自己建的（那次 commit 是「整理草稿 1 条」）

**被闸住的只有一层**：

| 层 | 谁定 |
|---|---|
| **领域**（一级） | **人**——`SEED_DOMAINS`，新增要改脚本或手工建 |
| **领域内分类** | **模型**——自建，审核按「近义归旧」复核 |

**所以旧阶段二那条「建目录申请 → 审核 → 建立」实质上是做了的。** 此前把它报成「没做」，是因为脑子里那条路还停在 Q30——**而 Q30 已经不在了，当时没跟上。**

## 定案

### Q93. 三个日志页各带一列「箱子」

**A：** 每个日志页有自己的、按天落盘的「箱子」；右侧栏两个竖排页签（整理日志页 = 报告|历史，工作日志页 = 流程图|历史，运行日志页只有箱子）；巡检单开一页。

**「报告」与「流程图」固定显示最近一次，与箱子无关。**

**设计全文见 [`superpowers/specs/2026-09-17-log-boxes-design.md`](superpowers/specs/2026-09-17-log-boxes-design.md)。**

**顺带结掉悬案：整理日志与流程日志是「两页」**（Q50 那条延伸注释写的「同一页、卡片颜色区分」作废）。当时的纠结是拿两个不能并列的东西做二选一——整理日志是**知识**（进 vault、可检索、回头会翻），流程日志是**排查工具**（只在出事那一次看）。Q80 的「是不是知识」这条分界本来就分开了它们。

### Q94. 层级上限 = 4 层

**A：** 目录嵌套**最多 4 层**（`planning.MAX_DIR_LEVELS`）。**领域算第一层**，文件名不算——`计算机/Python/x.md` 是两层，`计算机/a/b/c/x.md` 是四层（上限）。

问卷原话是「顶多三四层的样子吧」——定在 4。

**这条和 Q91 的兜底分类名是同一类**：机械约束，归代码不归模型。已落：`validate_plan` 数一遍相对路径的目录层数，超了直接拒；提示词里也写明，省得模型每次撞校验白跑一轮。

### Q95. 检索方案：先按几千条设计

**A：** **不选型。** 现在这套「标签 + 全文匹配」在**几千条**这个量级够用，就按这个量级设计。

到几千条以上再回头看要不要上向量。省下的选型成本换现在的简单。

### Q97. 会话 AI 什么时候触发整理

**A：** 三条触发条件，满足任一即触发：

1. **攒够 10 条**，**且**确认投递内容无误、没有需要更改的结论
2. **用户提到「暂停开发」**时
3. **用户直接要求整理**时

第 1 条里的「确认无误」是**前置条件**，不是独立触发条件——攒够 10 条但内容有要改的，先别触发。

**这条是 Q62「触发条件写什么」的答案内容**，它落在哪儿也定了（Q30②）：写进会话层接入说明。
**那份已经写了**——[`docs/接入指南/kn-record/`](接入指南/kn-record/SKILL.md)，装在用户级
`~/.claude/skills/`，任何项目的会话都读得到。这几条不再是「只有人知道」。

### Q98. Web 上改配置，改完怎么生效？

**A：** **保存即生效**——写回 `.env`，当场重载。

重载要做的三件事：模型三件套**重建 LLM 客户端**（换模型不用重启，这是最常改的一项）、
日志级别**当场调 `logging`**、其余的下次用到时现读。

**有两类要等下次启动服务**：巡检间隔与日志保留（服务启动那一刻才判/才清）、
以及 vault 路径与端口（路径是一切的前提、端口就是地址本身）。后两个在界面上
是**只读**的，要改得动 `.env`。

**重读配置不能用 `load_dotenv`**——它是 `override=False` 的，改过的值读不回来，
重载会变成空转。用 `dotenv_values`（见 [`04_踩坑与经验.md`](04_踩坑与经验.md) 第 27 条）。

**退出按钮**：「退出」= 停服务 → 弹提示窗。**标签页关不掉**（浏览器只让 JS 关
自己开的窗口），所以只给提示。侧栏那两个按钮（设置 / 退出）见布局设想的补充一节。

### Q99. 收件箱能进不能出

**A：加 `kb drop`（2026-09-18），删草稿。不留记录、不打 commit。**

**怎么发现的。** 用户在另一个项目里用 [`kn-record`](接入指南/kn-record/SKILL.md)
投了一天（十来条），其中两条的项目名记成了 `kb_push`——投递时 cwd 是临时目录，
`--project` 的默认值取了那个临时目录的 git 根名。

**会话层这边的反应值得记：**它**拒绝手改**那两行 frontmatter，理由是「别改
`E:\KB_Library` 里的任何文件」+「知识库的所有写入必须经过服务」。**它是对的。**
手改一次，串行化、校验、commit 就全开了口子。但它合规的那条路（`--project` 重推）
会**多出两条内容重复的草稿**——而收件箱**没有任何命令能撤**。

**于是缺口不是「项目名会取错」，是「投出去就收不回来」。** 前者无解也无需解：
`--project` 的默认值本来就是猜的（取 git 仓库根名），猜错很正常，**只要有一条退路**。

**定下的三条：**

1. **也只走服务**——`kb drop` 打 `/drop`，不碰文件。跟投递同一条规矩
2. **不留记录、不打 commit**——删是「当没发生过」。流程日志上不该多一笔，
   也不该为它单打一个提交。**这不是审计场景**；要审计就不该删，该作废
3. **只删草稿**，碰不到笔记；找不到的 id 报出来 + 退出码 1，但**其余几条照删**

**没做「改草稿」**（改项目名、改正文）：改的需求可以用「删了重投」满足，
而多一条「改」的路径就多一套校验。真需要了再说。

**「跳过」和「没走到」仍然没做**——那是另一件事，见下面待解决第 1 条。

### Q100. `[[双向链接]]` 的质量

**A：提示词加一条「链接要说得出共性」，`## 相关` 里的用 `——` 写。不加机械校验。**

**怎么发现的。** 用户看了 Obsidian 的关系图，问「被连接的双方共性怎么样」。查了全库
45 篇笔记的 116 条链接：

| 检查 | 结果 |
|---|---|
| 坏链 | **0** |
| 靠索引页凑数 | **几乎没有**（`计算机` 只被链 1 次） |
| 剔掉领域标签后两边仍有共同标签 | **82%** |

**结构是健康的，问题出在「理由」上：**

| 位置 | 条数 | 带理由 |
|---|---|---|
| 正文里 | 17 | 52% |
| **`## 相关` 章节** | **99** | **15%** |

**根因是「模板 + 硬规则」的组合，不是模型偷懒。** `templates/笔记/*.md` 每份末尾都有
一节 `## 相关`，硬规则 4 又要求「content 至少一个 `[[链接]]`」——**模型看到一个叫「相关」
的空章节，最省力的做法就是往里丢链接，不用说为什么**。入链冠军（11 条入链）只有 2 条
写了理由，而它自己的 `## 相关` 里就一行 `- [[计算机]]`，索引页凑数。

**为什么没加机械校验**（「`## 相关` 里的链接行必须含 `——`」——**这确实能落成一行 `if`**）：

> **格式卡住了不等于想清楚了。** 模型写「——同属常见坑」照样过检，
> 于是拿一次重试探来一个**合规的空话**，比不给理由更糟——它看起来像有理由。

这跟「兜底分类名」（Q91）不是一类：那条是**名字在不在禁用表里**，客观可判；
这条判的是**共性真不真**，只能归模型。**先只改提示词，看它自己能不能收敛。**

**这不是新增能力，是补上一条一直没提的要求。** 链接方向本来就对（横向关联同类坑，
正是知识库该做的），缺的只是「凭什么算相关」没变成规则。

**端到端验证（改了提示词之后）。** 推两条对照草稿跑 `kb organize`：

| 草稿 | 与已有笔记的关系 | 结果 |
|---|---|---|
| `open()` 不指定 encoding | **真有共性** | 3 条链接，3 条带具体理由 |
| Obsidian 图谱按 path 过滤 | **跟谁都不像** | 1 条链接，理由牵强 |

真有共性时效果超出预期——模型写出了「批处理文件本身**反而**必须用 GBK，
方向相反但都是『编码不匹配就全乱』」，这句指出了方向相反，是从前的链接里
读不出来的信息。

**但「跟谁都不像」那一篇暴露了一个矛盾：两条规则打架。**

> 硬规则 4：「**必须**至少包含一个 `[[双向链接]]`」
> 新加的话：「**说不出来共性就别链**」

当一篇笔记真的跟谁都不像时，「别链」和「必须链」冲突，模型选择**编一个理由**，
而不是放弃链接。它写的是：

> ——同属知识库工具的使用经验，都是想要的行为必须显式写出来，不能指望工具自己猜

这话把两篇换成**任何**别的工具笔记都成立，等于没说。

**所以补了第二句：给「共性」一个可检验的判据。**

> **共性要具体到能被检验**：同一个工具、同一层机制、同一类失败模式。
> 「都是坑」「都要显式写」「同属知识管理」这种说了等于没说的不算——
> 那只是在讲「两篇都是好笔记」，换个标题也成立。

手法同规则 1 的「『编码』和『字符集』不算重复」——**给反例比给正例管用**，
模型分得清「具体」和「泛泛」的边界在哪。

**「至少一条链接」没松动。** 孤儿笔记在 Obsidian 里是孤岛，代价比一条牵强的
链接大；而且理由现在写在明面上，读到牵强的一眼能看出来——**从「看不见质量」
变成「质量可见」本身就已经是收益。**

### Q101. `主题` 和 `项目` 为什么会静默丢？

**A：这两个字段本来就没有判断成分，不该交给模型——改由代码算（2026-09-18）。**

**怎么发现的。** 用户问「投递的内容质量怎么样」，顺手查了字段：

| 检查 | 结果 |
|---|---|
| 48 篇笔记的 `主题` | 全都填了——**纯靠模型自觉，代码一行没兜** |
| 48 篇笔记的 `项目` | **4 篇没有**，其中 3 篇本该有 |
| 提示词里的 `target_tags` | **幽灵字段** |

最后一条最荒唐：`target_tags` 是提示词专门让模型填的（JSON schema 里有，规则 7 整条在讲怎么填），
但 **`OrganizePlan` 根本没有这个属性**，`parse_plan` 不读，全项目零消费者——
**模型认真算了路径派生标签加语义标签，服务静静丢掉**。而真正入库的 `主题`，要它**再填一遍**。

两条规则打架的结果是：`主题` 空不空，取决于模型记不记得填。

**根因还是那条分界线**（「机械约束归代码，判断题归模型」）：

| 字段 | 归谁 | 为什么 |
|---|---|---|
| `类型` | 模型 | 判断题——这条算概念还是踩坑 |
| `主题` | **代码** | 路径在手边 + 大小写/分隔符/长度都是字符串操作 |
| `项目` | **代码** | 从草稿**原样搬**，一个字的判断都没有 |

**改法。** `planning.derive_tags` 从 `target_path` 拆出每一级目录名（领域排最前），
合并模型给的 `semantic_tags`（0-3 个，**只放路径上看不出来的**），统一规范化（小写、
空白折 `-`、截 20 字）后写进 `主题`；`resolve_frontmatter` 把草稿的 `project` 原样写进
`项目`——草稿没有（Web 投递）就把模型自己编的删掉，**草稿是唯一真源**。

> **`主题` 从此不可能为空**——路径至少有一级目录。这条比「加个校验报错」彻底：
> 报错只是拦住坏的，派生是让它坏不了。

**顺带修掉两个：**

- **fold 的内容怼在 `## 相关` 后面**。模板里 `相关` 是收尾节，但落盘是
  `body + 新内容` 直接拼在文件末尾，把它挤到文章中间、后面还挂着新章节。
  实测 2 篇已经这样。改成插到 `## 相关` 之前；找不到那一节（用户自己改过的笔记）
  照旧追加到末尾，不猜。
- **同一条洞见拆成多篇**。48 篇里有三篇讲的是同一条「机械约束 vs 判断题」的分界线，
  第一篇的「原因」直接引用第二篇的表格。提示词加一条：**候选笔记里已讲过同一条洞见的
  就 fold，别另起一篇**，只有新的成因/场景才 create。

**没做的**：`semantic_tags` 的**质量**（是不是真跨领域）不加校验——那是判断题。
只卡数量（>3 报错），因为数字是机械约束。

**端到端验证（2026-09-18）。** 两条对照草稿：

| 草稿 | 期望 | 实际 |
|---|---|---|
| Windows 命令行参数传不了换行（全新） | create，标签由路径派生 | `计算机/Windows/…`，`主题: [计算机, windows, 命令行]` ✓ |
| 文本模式写 bat 换行是 LF（已有笔记讲过） | fold 进那一篇 | `[folded] Windows 批处理文件必须用 GBK 编码` ✓ |

新建那篇的 `项目: KN_Base` 由代码写入（推的时候没给 `--project`，是服务自己从 cwd 取的），
**模板里也没有「用户的判断」了**。

### Q102. 候选召回排不准、链接理由没落地——为什么都先不改？

**A：两个都量了，都真实存在，但都有更便宜的修法；动代码的账暂时不划算（2026-09-18）。**

顺着 Q101 的审计往下量，撞上两个：

| 现象 | 实测 |
|---|---|
| 候选列表的**排序不携带信息** | 打分是 `similarity(草稿正文, 标题+标签)`，两侧长度差一个量级，分数全挤在 **0.04–0.11**（top1 中位数 0.059）。拿一篇笔记**自己的正文**去查，**只有 14/49 排第一**（20 篇第二、11 篇第三），排前面的大多不相关 |
| `## 相关` 的链接**大多没有理由** | 全库 102 条链接里 **83 条是裸链**。同一批（vault `52dfb88`）里 `import 期求值` 3 条全带理由、`Path 不展开环境变量` 3 条全裸——**同一份提示词，一次做到一次没做到** |

**为什么先不改：**

- **排序那条**：recall@8 是 **49/49**——真的要的那篇总在清单里，只是被 7 条噪声裹着、不带位置信息。
  它没有直接的用户可见症状；改它的价值是**让「候选正文也喂给模型」变便宜**，而那件事
  要等「篇内重复」真的再发生（见待解决第 2 条）。
- **链接理由那条**：「**有没有**理由」是机械检查，本该落进 `validate_plan`——那里已经有
  「必须有链接」「链接目标必须存在」两条机械检查了。但硬校验会让没写理由的打回重试、
  可能耗到进待归类，**这个代价值不值没结论**。

两个都留在待解决里，等真卡住再说。**别再重挖一遍**——数字都在上面，下次直接谈「要不要动手」。

### Q103. 检索只回索引，拿不到正文

**A：`search_notes` 连正文一起返回，三处调用点都放出来（2026-09-18）。**

**现象。** 用户问「软件版本怎么命名」，会话层答：库里有 1 篇《软件版本命名规范》，**要我把调出来读给你听吗**？
用户说「可以」，它答：**不过这次检索只返回了这条索引记录，没有带回正文内容，我这边暂时拿不到里面的具体条目。**

**根因。** `search_notes` 返回 `list[Path]`——纯路径。三处调用方（`kb search`、`GET /search`、
Web 对话的 `search` 动作）各自再把文件读一遍取 frontmatter，拼出「标题｜标签｜路径」，
**正文一次性丢掉**。

**而全文匹配本来就要把 `body` 读进来**（`_matches` 正是拿它比关键词）——读都读了，
却只拿它做判断、不往下传。**纯粹是漏掉，不是设计取舍。**

**改法。** `search_notes` 返回 `list[Hit]`，`Hit` 带 `path/title/tags/body`；标题走
`vault.note_title`（正文一级标题优先，文件名兜底）——`first_heading` 顺手从 `classify`
搬到 `vault`，检索也要用它，不该再从「查重预筛」那个模块里借。

| 调用点 | 以前 | 现在 |
|---|---|---|
| `kb search`（CLI） | 路径 + 标题 + 标签 | 后面直接跟正文 |
| `GET /search` | 同上 | 多一个 `body` 字段 |
| Web 对话的 `search` 动作 | 一行一条索引 | 每条一段 `## 标题` + 正文 |

**Web 对话那条最要紧**：`run_action` 的返回值**就是模型能看到的全部**（`chat.run_turn`
把它当工具结果塞回上下文），而 `search` 是它唯一的查库动作。只给索引，它除了
「我不知道」和编内容，**没有第三条路可走**。

skill 也补了一句：正文就在结果里，**查到就直接讲，不要问「要我把调出来读给你听吗」**——
那次失败里用户已经说了「可以」，而它没有第二个动作可做，只能回头说「我拿不到」。

### Q104. 首次配置没人写、点了按钮像没反应——四件小事

**A：README 补「第一次用」一节；两个「等待」画出来；一个「开始新会话」入口（2026-09-18）。**

四条一起提的，共同点是**都不是功能缺失，是「已经在跑但人看不出来」**。

**① 首次配置。** `README` 的「配置」表列了键，却从没说**第一次该干什么**——
而这里有两个坑，各自都是「照文档做还是跑不起来」：

- `KB_LLM_API_KEY` **没有默认值**，空着不是降级、是任何一条 `kb` 命令都当场停
  （`ConfigError` → 退出码 2）。原来的 README 一个字没提。
- `KB_VAULT_PATH` 的默认值是 `E:\KB_Library`——**作者本机的绝对路径**。别人克隆下来
  要么跑不起来，要么**真的写进那个目录**。

顺带发现 `scripts/init_vault.py`（建 vault 骨架那把脚本，**vault 结构的唯一真源**）
在 README 和 `docs/` 里**一次都没被提到过**——不知道它存在的人只会手工建目录，
而手工建的目录不是真源。补了一节，写明「照默认来」和「放别处」两条路。

**② 「思考中」/「整理中」。** 投递和对话都是**同步的一整页 POST**：点了之后页面从头到尾
一动不动，直到把模型调完、文件写完、git commit 打完。**看起来就是没反应**，
于是人会再点一次——同一条消息投两遍、同一句话发两遍。

**没有改成 fetch 异步**，虽然那样「真」是异步的：整页 POST 更简单，而且网络断了的时候
浏览器自带的错误页比手写的「网络错误，请重试」说得清。**要的只是把等待画出来**，
所以 JS 只做一件事：点下去先把「你自己那句话 + 思考中…」追加进消息流、把按钮禁用掉。
页面马上就会被 POST 的结果换掉，这两条临时元素不用管回收。

**③ 「开始新会话」。** 难点不在按钮，在**空白会话没法表达**：`cid` 传空和压根不传
长得一模一样，都会回落到「最近一次会话」——点了按钮的人会发现自己**又回到上一轮对话里**。
所以加的是 `/?new=1` 这个显式信号（不传 `cid`），不是靠空串。

### Q105. 「查一下 X」到底查库还是上网？

**A：先查库、不判断，库里没有再上网；来源要说在明面上（2026-09-20）。**

起因是用户问的一句：「我在会话里说『查一下 xxx』，模型会先查知识库还是上网查？」
当时的答案是**都不会去查库**——`kb search` 这个机制是好的（Q103），但**触发不归机制管，
归 skill 的 `description`**，而那份描述里只有「知识库里有没有讲过 X」「之前那条结论是什么」
这类**明确指向库**的说法。「查一下 X」不在其中，会被当成上网查或翻代码。
README 第三行那句「你要查的时候，**让会话里的 AI 代你查**」，于是成了一句没兑现的承诺。

两条路摆出来：**放宽触发词**，或者**加一条优先级**。用户选了「**还是查吧，不判断了，
先用试试**」——即**不判断**，连「查一下 asyncio 用法」这种明显该上网的也先搜一次库。
理由是：查库是本地调用、一次不到一秒，而**判断错的代价是他自己的结论被漏掉**。
**判断这一步不值得做。**

第二条规则是用户当场纠出来的。我原来写的是「别让用户以为下面那段是从他自己库里念的」，
他的反驳是「**不说是库里的那怎么体现库的价值**」——这句是对的，而且指向**反方向**：
真正要让用户看见的是**命中库的时候**。所以规则定成「**来源写在明面上**」：

- 从库里来的 → 「**库里记过**」，并点出标题/路径
- 库里没有 → 「**库里没有这条，我上网查一下**」

关键在于前半条。这不是免得用户误会，是**让库的价值看得见**——他看不见库在干活，
就不会信它，也不会往里投。

落点在 [`docs/接入指南/kn-record/SKILL.md`](接入指南/kn-record/SKILL.md)：
`description` 补了「查一下 X」这类触发词，「查」一节开头加了库优先 + 标来源两条。
`~/.claude/skills/` 那份同步。

### Q106. 六套皮肤怎么落地？

**A：`<html data-skin>` + CSS 变量重定义；配色由 6 个锚点推导，不手挑（2026-09-20）。**

需求是「布局一行不动，只换配色」，一共六套：四套来自用户给的撞色参考，
一套保留现有蓝，一套是现有皮肤的白换黑。

**方案**。备选是「每套皮肤一个 `<link>`，切换时换 `href`」。选了
`data-skin` + 变量重定义，决定性的理由是 `color-scheme`：深色皮里滚动条、
`<select>` 下拉、`<input readonly>` 这些**浏览器原生画的东西**，只有认了
`color-scheme: dark` 才会跟着变暗，否则四套深色皮边上漏一圈白。顺带还白拿
首屏无闪烁（服务端渲染就是对的颜色）、零额外请求、不写属性正好回落现有蓝。

**变量层**。`style.css` 里原来有 43 处写死的十六进制散在正文里，不全提到
`:root` 就会漏色。`--blue*` / `--pink*` 改名成 `--accent*` / `--journal*`——
按颜色起的名一换皮就是谎话（粉色皮里的 `--blue-soft`）。每套 32 个变量：
6 个锚点 + 26 个推导。

**为什么是「推导」不是「手挑」**。192 个数字手挑，等于埋 192 个将来会对不上
的地方：调一次「② 的紫再深一点」要跟着改二十个配套值，改漏一个画面上看不出来。
所以除锚点外全部按固定比例算。规则落在
[`src/kb/web/skins.py`](../src/kb/web/skins.py)，`scripts/derive_skins.py` 写进
`style.css`，测试断言两边逐字相等——**CSS 里那六块不许手改**。

**推导中发现两个真问题，都记在案**：

1. **② 的紫、⑥ 的蓝当文字读不清**（2.85 / 2.60:1）。没有动用户定的锚点，而是
   多出一档 `--accent-ink`（强调色**当文字用**时自动推到 4.5:1），填充仍用原
   锚点，调色板样子不变。
2. **`--divider` 的比例一开始写反了**（`mix(surface, ink, .22)`，实际该是 `.84`）。
   现有蓝那根 `#3d4753` 正是 `.84` 反推出来的。之所以没暴露：**现有蓝是硬编码的、
   不走这条推导**，只有另外五套受影响，而它们本来就没有「应该长什么样」可对照。

**可读性由测试守着，不是靠注释承诺**：六套逐套参数化断言正文、`--accent-ink`、
按钮文字三处对比度 ≥4.5。`_pick_ink`（白黑二选一）有个理论死角——底色亮度落在
0.183–0.233 那段窄带里黑白都够不着（黑最高 4.40）——现有六套没踩进去，
换锚点可能踩进去，到时候是测试红而不是用户眯着眼看。

**现有蓝「原样保留」有代价**：收变量时 `--line-strong` / `--accent-line` 各合并了
2-3 个手挑的近色，所以 5 个选择器的 1px 边框动了 1-2 个色阶（最明显的是
`.tab.active` 的边框变淡）。差异都在 1px 边框上，用户已确认接受。

**切换**。`KB_SKIN` 是 `choice`，走现有的 `/settings` 落盘链路，改完立刻生效
（`get_cfg()` 每请求现读，不用重启）。左栏底部的「外观」面板**先改 DOM 再发请求**，
所以是零延迟变色；存失败会把面板重新打开并报一句，不静默吞掉。

**扫漏色用的是计算色审计，不是肉眼**：无头浏览器把六个页面在六套皮肤下、每个
元素的**最终计算色**全报出来，逐条核对是否那 32 个变量解释得了。36 个组合全清。
它当场揪出一处 CSS 扫描够不到的漏色——`flow.html` 里流程链的勾写死了
`stroke="#fff"`，而它是画在 `--accent` 实心圆上的，切到 ④ 荧光绿就是白勾压绿底
（≈1.2:1，基本看不见）。改成 `var(--on-accent)`，并把防回潮测试扩到模板目录。

> 那几张参考截图（bilibili 的）**没有进仓库**——仓库是 public 的，看完就删。

**2026-09-20 补：②③ 的角色分工定死了。** 用户看过真页面之后，连着否了两版，
最后给的是**一句话就够用**的规格：

> 页面底色极光紫，点缀的用蜜柚黄，**跟极光紫荧光绿页面仅仅是绿和黄的区别**；
> 红粉那个**以红为底、粉为点缀**。注意色号，不要弄错了。

**② = ④ 换一个点缀色。** 锚点里 `paper` / `surface` / `ink` / `line` /
`accent_soft` 五条**逐字照搬 ④**（`#241c3a` / `#2e2549` / `#efeafb` /
`#3e3462` / `#3a3457`），**只有 `--accent` 不同**：④ 是荧光绿 `#bcfe1a`，
② 是蜜柚黄 `#fbea03`。有测试盯着这条对照关系不算多余——它正是用户的原话。

**③ 是深底 + 亮点缀**：底按 ④ 压极光紫的同一个深度压石榴红
（相对亮度都落在 0.014 上下）→ `--paper #410d14`、`--surface #4f0f19`，
点缀 `--accent #f1dddf`（雾粉桃原色）。

### Q107. 日志页的「一条一张卡片」，一条是指什么？

**A：整理日志一条 = 一条草稿的整理结果。** 工作日志还没动（见下）。

**问题是怎么冒出来的。** 2026-09-22 用户看过真页面：
「整理日志和工作日志的每一条用一个卡片这个设计怎么没了」。

**查下来：不是没了，是从来就没按条分过。** 需求 [`02_需求.md`](02_需求.md)
第五节的原话是「一张一张的**长条形卡片**装载，**每一条日志一张卡片**。打开这个界面时
**按顺序弹出**」，而实现是：

| | 谁决定卡片边界 | 一节/一轮几张卡 |
|---|---|---|
| 整理日志 | `parse_journal` 按 `## ` 切节，`journal.html` 一节一张卡 | 1 |
| 工作日志 | `group_flow` 按 `run` 分组，`flow.html` 一组一张卡 | 1 |

`git log` 追两个模板：从最早的实现 `a43dccf` 就是这两个循环，六套皮肤那几版
（`16e5eb6`…`cd5b8a0`）只动了颜色变量，结构一行没碰。

**为什么一直没被发现**：测试期每一轮整理只有 1-3 条草稿，一轮一张卡跟一条一张卡
**长得一模一样**。2026-09-22 头一回一轮 34 条，就露馅了——`## 08:13 整理 34 条草稿`
不再是「一张卡」，而是 34 条挤在一起的一面墙；工作日志那边一个 run 101 行同理。

**还有一个同页不一致**：右栏「报告」页签**本来就是按条渲染的**
（`journal.html` 里 `{% for r in latest %}` 一条一个 `.bubble.assistant`）。
同一页两种粒度，主区是漏的那个。

**为什么选「一条草稿一张卡」而不是「一行一张卡」**（当时给用户的二选一）：

- 一行一张卡 → 工作日志当天就是 **383 张卡**，一张卡一行字，卡片这个形状没有意义了
- 草稿一张卡 → 对得上 [Q89](#q89-工作日志流程日志长什么样) 给的例子
  （`14:32 你在网页上投递了一条草稿 / 14:33 模型决定放进…` 本来就是按草稿成组的），
  也解决了「规划/校验/落盘 三步分家、读者得自己在 100 行里配对」这个真问题

**落成什么样**：`## 08:13 整理 34 条草稿` 那行**退成分组标签**（`.group`，
比箱子名 `.day` 轻一档），卡片标题的位置让给条目本身。所以
`.card.journal` 现在是一张只有一行字、**没有 `<h3>` 的卡**——
`.card li` 那套正文色/字号得搬进 `.card.journal` 里，不然卡里没别的规则管它。

**顺带改的**：`journal.html` 的页面说明从「一次整理一张卡片」改成
「一条草稿一张卡片」——**旧文案是错的**，它把退化后的行为写成了设计。

**⚠️ 工作日志还没改，而且不是纯模板活。** `group_flow` 的行只有
`at / run / step / text` 四个字段，**没有草稿 id**，按草稿切块得靠
「规划→校验→落盘」的循环去猜——切得出来但脆，日志格式一改就散。
干净的做法是记日志时把草稿 id 写进行里，那是 `core/` 的改动。用户当时说
「第一个」，先只改了整理日志。

### Q108. 知识库的生命周期：初始化 / 迁移 / 移除

**问题**（用户的原话）：如果给别人使用，那有几个问题——知识库路径要能填；
刚开始使用时会自动生成领域级的文件夹吗；初始化按钮，需填好模型配置、知识库路径，
然后初始化知识库文件夹；不想要知识库之后怎么处理。后续补：不想要的话就是全部删除，
一点痕迹都不留的那种，另外知识库目录可迁移也实现一下；领域名让用户选，在设置窗口里
加一个初始化按钮，直接一条龙。

**结论**：设计文档在 `docs/superpowers/specs/2026-09-22-知识库生命周期-design.md`。
几条值得单独记的：

- **`config.py` 的 `DEFAULT_VAULT_PATH` 是颗雷，已拆。** `KB_VAULT_PATH` 留空会
  回落到 `Path(r"E:\KB_Library")`——作者本机的路径。别人的服务会安安静静写进
  作者的库，而且看起来一切正常（`list_drafts` / `list_domains` 在目录不存在时
  都返回 `[]`）。**「未初始化」这个状态要能被表示，跟这个回落直接冲突**，
  所以空值现在表示「没有」（`Path | None`），不是「用默认的」。
- **「有没有库」不存标志位**，由磁盘 + `.env` 推出来：`cfg.vault_path is None`
  或路径下没有 `.git` = 未初始化。判据用 `.git` 而不是「目录存在」——用后者的话，
  用户填一个现成的空文件夹就会被当成已初始化，投递进去后 `atomic_write` 自己
  `mkdir(parents=True)`，**在一个不是库的地方长出半个库**：收件箱有草稿、领域是空的、
  每条都掉进待归类。
- **领域清单不进 `.env`，设置里也没有这一栏。** 领域的唯一真源始终是磁盘
  （`list_domains` 直接读目录），初始化时勾选的作用只是**建出目录**，建完就不再
  被读第二次。要加领域 = 建文件夹——这也正是「名称不能随便起」能成立的原因
  （勾选保证起点干净，人工建目录留着当后路）。
- **`init_vault` 从 `scripts/` 搬到 `core/vault_setup.py`。** 服务要调它，而 `src/`
  与 `scripts/` 之间没有桥（`pythonpath` 只有 `src`）。服务进程「恰好」能 import
  是**巧合不是设计**——`spawn_service` 用 `-m kb.api.http` 且 `cwd=PROJECT_ROOT`，
  `python -m` 把 cwd 放进了 `sys.path[0]`，换个人从别的 cwd 起就断。
- **迁移拒绝非空目标，半路迁移必须挡。** 后者失败的样子是「看起来一切正常」：
  一轮整理会多次读库，迁移插中间就把它劈成两半，而最后那个 `commit_changes`
  只在新库里提交——**旧库那半永远不进 git 却躺在磁盘上**。挡住它的机制就是个
  带锁的 `Busy`，很便宜。
  > **2026-09-22 补：这把锁只罩「动文件」那一段。** 巡检原先是从规划（一次 LLM
  > 调用）就占住锁、一直占到 commit——它是整个流程里最长的一段，而且**只读**。
  > 冷启动那轮后台巡检因此会把**所有写入口冻住几十秒到几分钟**：用户在「记一条」
  > 写完点投递 → 409，而那条路是个纯 HTML 表单，浏览器把 `{"detail": …}` 直接
  > 渲染成一页，**刚写的正文既没落草稿也没进 vault**。现在 `run_sweep` 只在
  > `apply_plan` + `_commit_sweep` 那一段占锁（窗口从分钟级压到秒级），
  > 拿到锁之后**再验一次库还在不在**——规划那几十秒里库完全可能被搬走或删掉
  > （迁移是先拷后删源），拿一份过期计划去 apply 会写到不存在的地方。
  > 调用方只做一次**只读**的「忙不忙」预检（省一次白花的 LLM 调用），
  > 真正的互斥在 `run_sweep` 里面。用户按暂停时给的失败也不再是「巡检自己坏了」
  > ——新增 `lifecycle.BusyError`，「被挡住」映成 409 / 一份「这次没跑成，等它
  > 跑完再来」的报告，和「巡检炸了」分开（后者才该去看运行日志）。
- **「一点痕迹都不留」物理上做不到**：`data/logs/` 今天那两个文件正被服务自己
  打开着，Windows 上删不掉。界面上如实说明，不假装清干净了。
- **`data/runtime/service.json` 绝不能删**——那是 `kb stop` 唯一的线索，删了就是
  「停不掉的孤儿进程」，而那个 bug 的症状是测试全绿、开发机上服务失控。**有两条测试
  真咬着这条**：`tests/core/test_lifecycle.py::test_remove_leaves_the_rest_of_data_alone`
  与 `tests/web/test_setup.py::test_remove_keeps_service_json`。它们不止断言
  `service.json` 还在，还各造了一个无关文件一起验——因为 `remove_vault` 压根不碰
  `data/runtime`，只断言 `service.json` 的话是**恒真**的，守不住任何东西。
  删除清单只有 `data/chats`、`data/logs`、`data/state.json` 三项。
- **向导那层壳是 `<div>`，不是 `<form>`。** 设置面板`_settings.html` 整个包在一个
  大 `<form id="settings-form">` 里，而向导是它的子节点。**HTML 解析器遇到嵌套
  `<form>` 会把内层直接丢掉**（不动声色，不报错）——结果 `getElementById('wizard-form')`
  拿到 `null`，向导的 `onsubmit` 整个消失，「初始化」按钮一按变成提交外层的保存设置。
  另外**在输入框里敲回车会触发表单的隐式提交**（外层那个 `<button type="submit">保存</button>`），
  所以向导根节点上挂了一句 `onkeydown` 把 Enter 吞掉。两条都落成了测试。
- **未初始化时侧栏只置灰「记一条」和「巡检」。** 这两个是动作，按下去必然写库；
  其余的入口（整理日志 / 工作日志 / 运行日志）是只读的，空库下看到的是空列表，
  这恰恰是告诉用户「还没东西」的正确方式——一起灰掉等于把信息也藏了。
  判据是 `vault_ready(cfg.vault_path)`（同 `.git` 那条），不是另起一套。
- **分组要有稳定键，不能拿显示名当标识。** `Group` 上加了一个 `key`
  （`model` / `vault` / `service` / `skin` / `about`）：模板用它认组
  （`{% if g.key == 'vault' %}`）、JS 用它定位导航按钮（`data-group-key` + 一
  个 `showGroupByKey`）。原先三处都在比「知识库」这三个字——模板一处、JS 一处、
  测试一处——改一次显示名就会有一处悄悄失灵，而故障长成「这一组不见了」或者
  「初始化完停在『模型配置』那一栏」。同一个道理下面还收了两份**键名清单**：
  一条龙的段①现在由 `settings.GROUPS` 渲染（`data-model-key` 带着键名给 JS），
  往「模型配置」加字段只改一处。
- **`KB_VAULT_PATH` 的输入框回来了。** 用户当初的原话就是「知识库路径要能填」，
  而「知识库」那一组改成自绘之后那个框整个没了——`settings.py` 里它还写着
  `text`、`editable_keys()` 也还说它能改，契约和界面各说各话。现在它摆在已初始
  化那张卡下面，走 `saveSettings` 那条路，保存时 `settings.validate` 照旧验
  「那儿到底是不是一个已建好的库」。和「迁移到别处」的分工写在卡上：
  迁移是**搬**（当前这个库整个搬过去、源删掉），改这里是**换指向**
  （当前这个库留在原地，服务改看另一个）。
- **迁移接受「已经存在的空目录」。** 用户手动 `mkdir` 一个再选它，是很自然的操作，
  没有任何理由拒绝。危险的是**非空**目标：`copytree(dirs_exist_ok=True)` 会静默合并，
  而合进一个已有的库是灾难。所以拦的是「目标里有东西」，**这道闸必须在回滚的 `try` 之外**——
  它拦的是「调用方用错了」，不是「拷贝出错」；放进 `try` 里，回滚会把目标里原有的
  文件一起删掉，**把用户的数据弄没**。代价是空目录这层壳在回滚时会被一起收走，
  属于已知边界，写在代码注释里。

- **「删源失败」不回滚目标——回滚的方向跟着「哪份是完整的」走，不跟着「谁是旧的」走。**
  迁移的最后一步是删掉旧库。这一步在 Windows 上会失败（文件被 Obsidian 或杀软占着），
  而走到那里时**旧库已经删掉一半、新库才是唯一完整的一份**。所以「失败就回滚」在这
  一步是**反的**——回滚会把好的那份也毁掉。原来的实现更糟：`_rmtree(source)` 在
  `try` 之外抛的是裸 `OSError`，端点的 `except LifecycleError` 接不住，用户拿到 500，
  而 `.env` 没改、旧库残着、重试又撞「目标非空」400——**死胡同**。
  现在的做法：**保住目标，把「旧库没删干净」如实报出来**（走 `/setup/migrate` 的
  `notes`，语义和 `/setup/remove` 的 `notes` 一致），`.env` 照常指向新库，用户的书房
  是好的，脏东西留在旧路径上可以回头再清。
  > 那条「失败时回滚目标，源库一根汗毛不动」的铁律**只管拷贝阶段**。
  > 一句话记法：**拷贝失败时旧的是完整的，删源失败时新的是完整的**——同一个函数里，
  > 两段的回滚方向相反。
- **破坏性端点必须自己验「这儿到底是不是库」。** `require_vault` 只判
  `vault_path is None`、**不判 `.git`**，所以「路径配了但那儿没库」这个状态在
  `/setup/remove` 与 `/setup/migrate` 上没有任何闸——`KB_VAULT_PATH` 填错时，
  一句 `POST /setup/remove` 会把那个目录连同里面的文件整个删掉。界面上的「检查」
  和确认框都是**界面礼貌**，绕过界面的 `curl` 与会话层 AI 一路畅通，所以闸要设在
  `remove_vault` / `_check_migration` 的入口上，判据用 `vault_ready`。
  > **2026-09-22 评审后又收了一轮：只判 `.git` 不够。** `KB_VAULT_PATH` 写成
  > 相对路径时，`.` 会按**服务进程的 cwd**（`spawn_service` 用
  > `cwd=PROJECT_ROOT`）探到 KN_Base 仓库自己的 `.git`——于是整个仓库被当成库
  > 拷到目标、紧接着 `_rmtree(source)` 把它删掉，响应还是一句轻描淡写的「旧库
  > 没删干净」。同一个 `.` 打到移除那条路上抛的是 `Path(".").with_name("")` 的
  > 裸 `ValueError` → 500。现在判据收在 `lifecycle.vault_path_problem` **一处**
  > （`migrate_vault` / `remove_vault` / `router._check_migration` 共用），
  > `vault_ready` 也补上「必须绝对路径」——它是状态接口与 `/setup/init` 那道闸
  > 共用的判据，只拦破坏性操作的话，界面照样报「已初始化」、投递照样往项目仓库
  > 里写草稿。失败文案按「相对路径 / 那儿不是库」**分开**：用户下一步该干的事
  > 不一样，而且路径写法那种如果只说「不是一个知识库」，那儿明明有 `.git`，
  > 会把人引到错方向。
  >
  > **2026-09-22 又补了一条出口。** 那道闸带来一个死角：用户自己 `rm -rf .git`
  > （或库被挪走、盘符没挂）之后，`KB_VAULT_PATH` 指着一个还装着笔记、却没有
  > `.git` 的目录——「移除知识库」被闸拒掉，而设置窗提交空值那句文案又让人
  > 「用『移除知识库』」，**循环指回同一个端点**。解法**不是把闸拆了**（确认框
  > 拦不住 `curl`，填错一个字母就得能兜住），而是**在未初始化态给一句话**：
  > 填同一个路径点「初始化」，`init_vault` 幂等、已有的笔记一律不碰，收编之后
  > 「移除知识库」自然就出现了。**先收编、再移除**——两步，但每一步都安全。

- **评审记档里还剩的**（2026-09-22。Task 5–10 四轮代码评审一共报了 40 条，
