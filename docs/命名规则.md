# 命名规则

**用途：让会话层和服务层用同一套规则算出同一个名字。** 会话层不背目录结构，只按这里的规则推导；服务层按同一套规则解析和校验；审核按同一套规则审。

---

## 总原则

**能确定性推导的名字，两边各算各的也必须一样；不能推导的，靠检索定位。**

哪些能推导、哪些不能，下面每条都标了。**标「可推导」的，会话层可以自己算出完整路径；标「不可推导」的，会话层只能给线索，由服务层去搜。**

---

## 一、项目名

**来源：** `git rev-parse --show-toplevel` 的目录名。非 git 仓库时取当前目录名。

**规范化：** 转小写；`-`、`_`、空格一律视为 `-`。

| 原始 | 规范化 |
|---|---|
| `KN_Base` | `kn-base` |
| `kn_base` | `kn-base` |
| `KN-Base` | `kn-base` |
| `yuewu bachong` | `yuewu-bachong` |

**存储用原样，匹配用规范化。** 首次创建时按目录名原样保存；此后比对一律用规范化值。所以 `KN_Base` 和 `kn_base` 会被认成同一个项目。

**匹配不到，或匹配到多个 → 进 `00_收件箱/待归类/`，不猜。**

---

## 二、目录

```
00_收件箱/
00_收件箱/待归类/
10_项目/<项目名>/
20_知识/<主题>/
30_素材/
40_索引/
40_索引/整理日志/
90_附件/
```

**`10_项目/` 下直接是项目文件夹，不再分「个人 / 工作」。**

---

## 三、项目笔记 ★ 可推导

```
10_项目/<项目名>/<项目名>-<类型>.md
```

- `<项目名>` 用目录里**实际的那个写法**，不是规范化值
- `<类型>` ∈ `概念` `踩坑` `决策` `经验` `清单`（这五个是允许 LLM 使用的类型；`日志` `索引` 由服务生成）
- **每个项目每种类型至多一个文件**

例：`10_项目/KN_Base/KN_Base-踩坑.md`

**为什么这条重要：** 给定「项目名 + 类型」，路径唯一确定，**不含任何内容信息**。所以会话层说「改 KN_Base 的踩坑」，它自己就能算出完整路径，不需要先查。

**这条由代码强制，不只写在提示词里**（`planning._project_note_name_error`，另加 CREATE 分支里「文件名后缀 == `类型` 字段」的一致性校验）。

> **2026-09-16 补的校验。** 首次端到端验证时发现：提示词里只写了「文件名必须**带**项目前缀，如 `项目名-踩坑.md`」，模型照做了——加了前缀，然后自己取了个内容标题，落成 `KN_Base-项目目录摊平.md`。
>
> 差别是致命的：规则本来的价值在于**路径可推导**，而内容标题由模型定，推不出来。所以补了代码校验。
>
> 这是第三次撞上同一条：Q23（`用户的判断` 不许代填）也是靠提示词拦不住、最后改成机械清空。**凡是「必须如此」的约束，都要能落成代码检查。**

---

## 四、知识笔记 ★ 不可推导

```
20_知识/<主题>/<标题>.md
```

- `<主题>` 是已存在的主题目录；不存在就申请新建（走审核）
- `<标题>` 由 LLM 从内容提炼

**标题清洗规则：**

1. 去掉文件系统非法字符：`\ / : * ? " < > |`
2. 去掉首尾空白和结尾的点
3. 长度上限 **60 个字符**，超出截断
4. 保留中文，不做大小写转换

**为什么不可推导：** 标题来自内容，会话层算不出来。所以修改知识笔记时，会话层只能给线索（关键词或标题），由服务层检索定位。

---

## 五、索引页

```
40_索引/<主题>.md
```

服务自动生成，内容是 Dataview 查询。**已存在的不覆盖**——你可能自己改过。

---

## 六、整理日志

```
40_索引/整理日志/<YYYY-MM-DD>.md
```

按天聚合，每次整理往当天那篇追加一节。

**注意：这是唯一进 vault 的日志。** 流程日志和运行日志都不进——它们不是知识，进去会污染检索。

---

## 七、草稿

```
00_收件箱/<YYYYMMDD>-<4 位十六进制>.md
```

例：`20260915-a3f2.md`

用 id 而非「日期 + 摘要」作文件名——id 是对外接口（`kb organize <id>`），文件名与之一致最不容易出错。

**归不了类的草稿移到 `00_收件箱/待归类/`，文件名不变。**

---

## 八、修改请求的定位 ★

会话层要改一条已有笔记时，**给出目标文件名（不含路径、不含 `.md`）**，服务层全库搜同名文件：

| 搜索结果 | 处理 |
|---|---|
| 唯一命中 | 定位成功 |
| 零命中 | 进 `待归类`，报告里列出 |
| 多个命中 | 进 `待归类`，报告里列出——**不猜是哪一个** |

例：

```
kb push --content "队列串行化不是最优解，应该用乐观锁重试" --revise "KN_Base-踩坑"
kb push --content "这条结论要改……" --revise "向量检索的取舍"
```

**为什么用文件名而不是路径：** Obsidian 本身就是按文件名链接的，用文件名定位和它一致。而且会话层不需要知道目录结构。

**为什么改项目笔记很容易：** 项目笔记名可推导（第三节），会话层直接给就行。
**为什么改知识笔记要搜：** 知识笔记名不可推导（第四节），只能搜。

---

## 九、审核按什么审

上面每一条都是审核的检查项。审核拿到「提议 + 本规则」，逐条对照：

- 项目笔记的路径，是不是 `<项目名>/<项目名>-<类型>.md` 的形状？
- 类型在枚举里吗？
- 要新建的主题目录，是不是和已有主题高度重叠？
- 要改的目标文件，搜到的结果是唯一的吗？
- 标题清洗规则走了吗？

**审核不判断「内容该不该这么归类」——那是整理的事。审核只判断「名字和路径合不合规则」。**

---

## 十、已定：用 `--revise`，不用 frontmatter

**修改请求走 `--revise <文件名>` 参数**（即第八节例子里的样子），不在草稿 frontmatter 里加字段。

**理由：** `--revise` 是会话层**明确说**「这条取代那条」；写 frontmatter 等于让 LLM 自己填一个判断字段，和 Q30「agent 只交正文，不填类型/主题/分类」相冲。

**这条还避开了 Graphiti 的坑。** 调研查到它的失效机制在生产上出过事故——被自动失效的事实里 70% 其实还是真的，因为它挑「哪些该失效」时靠语义相似度、没有约束。**失效判断越显式，越不容易误伤。** 详见 `规划总纲.md` 第二节第 7 条。

**失效后旧内容不删**，打失效标记保留，**默认排除出检索结果**（点时间查仍可得历史）。
