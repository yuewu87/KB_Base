## 二、架构（你描述的）

### 两层

| | 是谁 | 干什么 |
|---|---|---|
| **第一层** | 会话 AI（Claude Code、DeepSeek Harness 等） | **只**投递、发请求、接收 |
| **第二层** | 知识库服务 | 处理请求、分发任务、检索、返回 |

### 第二层里的 agent

| agent | 职责 | 你的原话要点 |
|---|---|---|
| **审核** | **必须独立**，不参与其他事务 | 「仅仅作为有智能的能根据规则自动审核的独立程序」 |
| **管理** | 与用户对接、与会话层 AI 对接、分发任务 | 与用户走 Web 对话；与会话层「怎么方便怎么来，甚至可以不用」 |
| **整理** | 归类、查重、补链接 | 现有能力 |
| **检索** | 代会话层查 | 新增 |

**你说「其他事务多少个无所谓」**——除了审核必须独立，其余的分法你不在意。

### 审核的定位（这块你说得最具体）

> 「当整理时发现没有这个分类需要新建文件夹时，就发送明确的请求（比如请求新建 `E:/KB_Library/项目/kb_base`）给审核 AI，审核就判断是不是乱建的、文件夹下是否已经有该文件，**这里就需要强制一套文件命名规则，按规则审，按规则建立**」

**审核是「按规则审」，不是「凭判断审」。** 这是这套设计里最像机制、最不像提示词的一环。

### 建立文件夹的两种触发

1. **项目启动时** —— 用户提出「新建知识库」需求，第一层 AI 启动服务、发送建立需求
2. **整理时** —— 整理过程中发现有概率触发，**多发生在前期**

### 第二层需要的新能力

- **修改**：项目后续发现结论不对 → 会话层发更改请求 → 第二层要能改
- **检索**：返回文档给会话层
- **分发**：把请求派给对应的 agent

### 可替换性

> 「管理层这个 AI 可以像插件一样更换成其他程序的 AI，例如角色扮演系统的 AI，接入 QQ bot 等更便捷、更联通的方式」

## 八、我的判断：需要几个 agent

你问「需要分几个，还是一个就够」。**我认为按你说的分就够，不必更多：**

| agent | 为什么必须单独 |
|---|---|
| **审核** | 你要求它「独立、不参与其他事务」。独立的价值在于**它只对规则负责**——如果它还兼着整理，就会出现「自己审自己」 |
| **整理** | 现有能力，单独一个 |
| **管理/分发** | 它是对外的那一张脸，会话层和 Web 都找它。它是**路由器**，可以很简单 |
| **检索** | 可以并进整理，也可以单独。倾向单独——它的负载特征和整理完全不同（检索要快、频繁；整理慢、偶尔） |

**不建议再多。** 每多一个 agent 就多一处「谁说了算」的模糊地带。你现在列的四类正好对应四种不同的职责边界，再拆就是拆职责而不是拆功能了。

### 4 的注意点：页面合并了，**存储必须分开**

- **整理日志 = 知识**，进 vault（`40_索引/整理日志/`），可被检索、阶段二可被 RAG 召回
- **流程日志 = 运行记录**，**绝不能进 vault** —— Q51 已定：进去就成了笔记，会被检索、被当知识。技术日志是噪音

**UI 上一页两种来源，存储上分开。** 视觉合并不改变存储边界。

### 5 的注意点：建议「失效」而非「覆盖」

「对比文件然后修改」如果实现成直接覆盖正文，会丢掉「当初为什么那么想」——而那往往比结论本身有用。

建议 frontmatter 加 `superseded_by` / `valid_until`，旧内容保留但标记失效。这是调研结论之一（Zep/Graphiti 的双时态），也是纯 markdown + git 最擅长的事。
