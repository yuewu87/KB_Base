## 一、定位

**人机共用的知识库，但更倾向于 AI。**

- 人查看就用 Obsidian：**只是查看、检索、随手改**
- AI 直接查找

**不是「放对位置」本身。** 放错位置可以接受——原话：「可以接受，主要的功能还是为知识的关联性和检索能力服务」。

> 这句出自问卷**第 14 题**（「能接受它偶尔放错位置吗」），是**「为什么放错可以忍」的理由，不是一条独立需求**。用户 2026-09-17 的口径：**关联性是为检索服务的**——所以「关联」这件事做没做到，看的是检索够不够用。

---

## 二、使用场景

### 写

- **项目类**：有准备的会话层投递（项目里踩的坑、经验、决策）
- **随手记**：琐碎的知识点，几句话的事，**走 Web UI，不开会话**。两种形态都要：
  - **对话式**：说给 AI 听，它投递
  - **模板式**：点「＋ 记一条」→ 选模板 → 写 → 投递

> 模板是**脚手架型**——问几个大白话问题帮人把话说清，**不逼人先想清楚这是什么类型**。整理阶段负责重组。

### 与用户对接的 AI

> **这一节 2026-09-16 从原问卷里补回。** 合并文档时它一度被当成「做法」删掉了——**但它是需求**。

**原话：**

> 「管理层的 ai，它需要与用户或会话层 ai 对接，**与用户就是 web 里对话式**」
>
> 「我有想过管理层这个 ai 可以**像插件一样更换**成其他程序的 ai，例如角色扮演系统的 ai，接入 qqbot 等更便捷、更联通的方式」
>
> 「如果**分发路由能做到处理命令、返回数据给会话层 ai，那其实 web 的 agent 和会话层的 ai 没有区别**」

**要点：**

- **它是「另一个入口」，不是一层、不是管理 agent**——能力和会话层 AI 相同，只是走 Web 不走 CLI
- **可替换性发生在入口层**：CLI / Web / 以后的 qqbot 是平级的入口，换的是入口，不是内核
- 会话层 AI 的对接「怎么方便怎么来」——甚至可以不经过它，直接发请求走流程

### 查

线索是**「关键词或一段描述」**。

由会话层 AI 代查，拿到文档后融合回复用户，或自己直接用。

### 整理

时机由会话 AI 判断（如暂停项目时、长时间未整理），或用户主动说明。

> 「需要给 AI 明确写清触发条件」（原话）——所以触发条件要写成会话层能读到的规则，不能只在我们脑子里。

## 三、边界

| | |
|---|---|
| **人数** | 个人使用，**没有协作打算** |
| **内容敏感度** | 不介意外发。原话：「如果给其他人用的话，介意就用本地 LLM 就行」 |
| **数据归属** | 原话：「数据库就是数据库，什么都不沾」——**实现代码、数据、相关文件全放在本项目里** |
| **可移植** | 要能**打包成可移植的项目** |
| **不要什么** | 明确不要「其他分类」这类兜底目录——注定变垃圾桶 |

---

## 四、规模

原话：「我现在有多个项目，还有一堆课程笔记，累积的素材，挺多」。

**课程知识按内容归领域**（编程课 → `计算机/`，绘画课 → `艺术/`）——课程学到的东西就是典型的可复用知识，应与项目经验一起被检索到。

## 五、Web UI 布局设想

原话整理：

- **整体**：想做得有设计感些，但**先简单搭建一版**
- **主界面**：一定有个**可折叠的左侧栏**，里面放按钮 `[ai对话] [整理日志] [工作日志] [运行日志]`，后续需要再添加。**主区宽度跟随侧栏展开关闭而变**
- **[ai对话] 页**：需要个**右侧栏**放会话历史。基本可以直接借鉴 DeepSeek 的网页布局，**只是把左边的会话历史放到右边**
- **[整理日志] 页**：一张一张的**长条形卡片**装载，每一条日志一张卡片。打开这个界面时**按顺序弹出**。报告也加一个右侧栏，做成**手机聊天界面样式**，像发消息一样一条一条发送出来
- **[工作日志] 页**：同理，和整理日志一样
- **[运行日志] 页**：**终端样式**，日志原本输出什么样，这里就输出什么样
- **配色**：白色 + 蓝色，**不要太亮的**。整理日志卡片**淡蓝色**，工作日志卡片**淡粉色**

> 「工作日志」在这里指的是**流程日志**（每一个流转的记录）。命名以 [`03_问题记录.md`](03_问题记录.md) Q80 为准。

### 2026-09-17 补充：箱子、页签、巡检页

**上面这段是最初的设想，以下是后续定案，冲突处以这里为准。** 设计全文见 [`superpowers/specs/2026-09-17-log-boxes-design.md`](superpowers/specs/2026-09-17-log-boxes-design.md)。

- **左侧栏多一项**：`[巡检]` 单开一页（放巡检报告与巡检按钮），与 ai对话、三个日志并列。原来挂在左侧栏的「巡检一次」按钮挪进那一页
- **每个日志页带一列「箱子」**：箱子 = 那一天；**按天落盘**，那天没产生日志就不建箱子。箱子名（如 `26_9_17箱子`）**只是界面叫法**，文件沿用各自命名
- **右侧栏加两个竖排页签**（贴着侧栏左边缘），内容跟着页面走：
  - 整理日志页：`报告 | 历史`（报告 = 最近一次整理的文字记录）
  - 工作日志页：`流程图 | 历史`（流程图 = 最近一次操作那六个步骤的 ✓/○ 竖排）
  - 运行日志页：**没有页签**，只有箱子

> **「报告」「流程图」固定显示最近一次，与箱子无关**——选中的箱子只决定主区看哪一天。

### 2026-09-17 补充：设置与退出

- **侧栏加两项**：「设置」归在导航那一组（跟 ai对话、日志并列），「退出」（红底）
  单独在最底，上面一条分隔线——一个是功能，一个是关机
- **设置窗是模态、双栏**（左列分类、右列内容），四组：模型配置 / 知识库 / 服务 / 关于
- **保存即生效**——模型三件套与日志级别当场换。**巡检间隔与日志保留要下次启动服务**
  （它们只在服务启动那一刻用一次）。端口与 vault 路径**只读**（换错了整个服务当场废、改了书签作废）
- **退出 = 停服务 → 弹提示窗**。标签页关不掉（浏览器只让 JS 关自己开的窗口），所以只给提示

## 六、成功与失败的标准

**这项没答。** 原话是反问「你问的这个『东西』是什么」。

换个问法仍在等答案：**三个月后，从哪一件具体的事上你能判断出「这套东西有用」？**

已知的是失败模式（原话：「就像你写的那样」）——大致是「三个月后我不用了」「里面有重复内容我怎么清」「AI 放的东西我从不看」。

## 八、落实情况（2026-09-17 核）

**逐条对着上面的需求核一遍。** 设计上还没答案的见 [`03_问题记录.md`](03_问题记录.md) 的待解决清单。

| 需求 | 落在哪 |

| 人机共用、偏 AI | Obsidian 看/查/写判断；会话里的 AI 直接查 |

| 事 | 来由 / 现状 |
|---|---|
