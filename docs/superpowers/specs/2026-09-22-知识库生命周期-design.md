# 知识库生命周期（初始化 / 迁移 / 移除）设计

> 2026-09-22。用户的原话：「如果给别人使用，那有几个问题」——
> 10. 知识库路径要能填；11. 刚开始使用时会自动生成领域级的文件夹吗；
> 12. 初始化按钮，需填好模型配置、知识库路径，然后初始化知识库文件夹；
> 13. 不想要知识库之后怎么处理。
>
> 以及后续补的：「不想要的话就是全部删除，一点痕迹都不留的那种，另外，知识库目录
> 可迁移也实现一下」「领域名让用户选，在设置窗口里加一个初始化按钮，直接一条龙」。

---

## 一、这份文档解决什么

让**别人**能把 KN_Base 跑起来、用下去、再干净地扔掉。

现在这套东西只对作者成立：`.env.example` 里 `KB_VAULT_PATH=E:\KB_Library` 是作者
本机的路径，而且**留空也会回落到同一个路径**（`config.py:27` 的 `DEFAULT_VAULT_PATH`）。
别人克隆下来照着 README 填 `.env`、跑 `python scripts/init_vault.py`，中途任何一步
没做对，**服务照样起得来、照样不报错、安安静静地写进一个不对的地方**
（`list_drafts` / `list_domains` 在目录不存在时都静默返回 `[]`，见 `vault.py:128`、`vault.py:211`）。

本设计把「有没有库、库在哪、怎么建、怎么搬、怎么扔」变成四个**显式**状态，
每一步都在界面上看得见。

## 三、四个状态

「有没有知识库」不是一个布尔值，是四个。全部由**磁盘 + `.env`** 推出来，不额外存标志位。

| 状态 | 判据 | 界面 |
|---|---|---|
| **未初始化** | `cfg.vault_path is None`，**或** 那个路径下没有 `.git` | 首屏引导卡；设置里显示「还没有知识库」+ 一条龙入口 |
| **已初始化** | 路径有值 且 `<路径>/.git` 存在 | 正常界面；设置里显示「已初始化」+ 迁移/打开/移除 |
| **正在整理** | 后端 busy 标志为 `"organize"` | 迁移按钮置灰；投递/整理端点返回 409 |
| **正在迁移** | 后端 busy 标志为 `"migrate"` | 投递/整理/移除按钮置灰；迁移按钮自轮询 |

**别把这四个状态和 9.2 那条校验看成矛盾。** 两者的作用面不同：

- `vault_path` 有值但没 `.git` —— 这是**启动时读出来的状态**（老 `.env` 里留着
  `E:\KB_Library` 而那个目录不是库、或者用户手工改过 `.env`）。界面显示「未初始化」，
  **一条龙可以直接用**，`init_vault` 幂等，不会破坏目录里已有的东西。
- 9.2 拦的是**在设置窗里改路径这个动作**——那时库已经活着，凭空换指向会把它换废。

**为什么用 `.git` 而不是「目录存在」当判据**：`init_vault` 必然建 `.git`（`init_vault.py:94`），
而用户随便填一个空目录不会有。用「目录存在」判，用户填了个现成的空文件夹就会被当成
「已初始化」，然后投递进去——`atomic_write` 会自己 `mkdir(parents=True)`（`vault.py:53`），
于是**在一个不是库的地方长出半个库**，收件箱有草稿、领域是空的、每条都掉进待归类。
这正是要防的「看起来一切正常」。用 `.git` 判，这种情况会显示「未初始化」，用户可以
直接点初始化（`init_vault` 幂等，不会破坏目录里已有的东西）。

### 🔴 必须先拆的雷：`DEFAULT_VAULT_PATH`

`config.py:117` 现在是：

```python
vault_path=Path(vault_raw) if vault_raw else DEFAULT_VAULT_PATH
```

`DEFAULT_VAULT_PATH` 是 `Path(r"E:\KB_Library")`（`config.py:27`）——**作者本机的路径**。
只要 `.env` 里留空，别人的服务就会往作者的库写。第 1 条决定（「未初始化」要能被表示）
和这个回落是直接冲突的：**空值必须表示「没有」，不能表示「用作者的」**。

**拆法**：`Config.vault_path` 的类型从 `Path` 改成 `Path | None`，空值就是 `None`，
`DEFAULT_VAULT_PATH` 整个删掉。所有用到 `cfg.vault_path` 的地方都要显式处理 `None`：

- CLI（`kb push` / `kb organize` / `kb search` 等）：报
  `还没有知识库。请在网页上点「初始化知识库」，或手工把 .env 的 KB_VAULT_PATH 填好、再跑 python scripts/init_vault.py`
  ——**文案必须说全两步**：`scripts/init_vault.py` 只建目录，**它不写 `.env`**
  （写配置一直是服务的活）。只说「跑这个脚本」会把人引到一个半截状态：
  库建好了、服务还是不知道该看哪儿
- 服务端点：返回 409 + 同样的意思，界面去引导卡
- `settings_context`（`router.py:74-100`）：未初始化时那一栏显示空值 + 提示，不能崩

这是本设计里**唯一一处会碰到 `core/` 与 `llm/` 之外大量调用点**的改动，也是风险最高的一步，
计划里单独排一个任务、先做。

## 四、一条龙初始化

### 4.1 它放在哪

**设置窗的「知识库」分组里**，不是另开一个向导窗。理由：用户的原话是
「初始化后以后就显示已初始化，要改就去对应的设置改」——
初始化**就是**那个分组的未初始化态，做完之后同一个位置换成已初始化态。
一屏两态，跟 `first-run.html` 那张 mockup 一致。

首屏引导卡上的按钮 `onclick` 打开设置窗、直接 `showGroup` 到「知识库」
（`base.html:197` 的 `showGroup` 就能干这个），滚到那条龙。**不是两套界面。**

### 4.2 三段

```
① 模型配置    模型名 / API 地址 / API Key          [测试连接]
② 知识库目录  [ 输入框：填绝对路径 ]                 [检查]
③ 初始领域    九个复选框，至少勾一个
                                          [初始化]  ← 一个按钮收尾
```

**② 就是一个文本框，用户自己填绝对路径**（需求第十条的原话是「知识库路径要能填」）。
不做什么目录选择器——路径是他自己电脑上的，他打得出来。旁边的 `[检查]` 是可选的
顺手验一下（存在吗、可写吗、里面是不是已经有个库），失败也不拦着初始化。

- **一条龙不共用设置窗那个 form，也**不是**自己另开一个 `<form>`——它是个 `<div>`。**
  两条理由，第二条是硬约束：
  - 复用 `id="settings-form"` 不行：它走 `saveSettings()`（`base.html:222`），
    那套 `data-init` 过滤、只提交改过字段的逻辑是为「改配置」设计的——
    而一条龙每次都要把三段全交上去。所以新写一个 submit handler。
  - 另开 `<form>` **更不行**：一条龙整块住在 `#settings-form` 里面，
    再嵌一层 `<form>` 是非法嵌套。解析器碰到「表单指针非 null」时的
    `<form>` 开始标签会**直接忽略**，而且一声不响。叠加上 `name` 还会跟
    外层通用字段循环撞车（`Object.fromEntries(new FormData(form))` 只取到
    最后一个）。做法见 `_vault_pane.html`：**不给 `name`**（沿用本文件
    「只读字段不给 name」那条约定），`runInit` 按 id 逐个收。
  共用 `.pane` 那套样式。
- **① 复用现成的 `/settings/test` 端点**（`router.py:420-475`）：它拿表单里的值试一次调用、
  **不落盘**——正是「先测再存」要的。
- **③ 清单来自代码常量**，不落 `.env`（见 4.3）。

底部那句提示要写清楚：**初始化会建目录、写 `.gitignore`、初始化 git 仓库；幂等**。
「幂等」两个字很重要——用户在一个已有东西的目录上点它，得知道不会被毁。

### 4.3 领域清单为什么不进 `.env`

**领域的唯一真源始终是磁盘**（`vault.py:35` 的注释、`list_domains` 直接读目录）。
初始化时勾的那几个，作用只是**建出对应的目录**；建完之后它就不再被读第二次。
所以：

- `.env` 里**没有**「领域」这个键，不需要新增配置项
- 设置窗里**没有**「领域」这一栏，要加一个领域 = 在资源管理器里建个文件夹，
  服务下次就认（这正是「名称不能随便起」能成立的原因：勾选保证起点干净，
  人工建目录留着当后路）
- 语义上「改领域」= 改目录，不是改配置——跟模型的「改参数」不是一类东西

**⚠️ 这是一处已知的粗糙**：别人想在界面里加个领域，现在得离开界面去建文件夹。
本设计**不做**「在界面上增删领域」，理由是增删领域要处理「目录里还有笔记怎么办」，
那是另一个尺度的功能（搬迁 + 合并分类），跟巡检（Q89）是一类。**记在「不在本次范围」**。

### 4.4 初始化做了什么

```
1. settings.validate + write_env      写 KB_VAULT_PATH 与模型三件套（保留注释与顺序）
2. reload_config → 灌回 state         复用 apply_settings 那套（http.py:303-347）
3. init_vault(vault_path, domains)    建目录、写 .gitignore、git init、首次提交
4. 返回本次实际做的动作清单            直接展示给用户（「建了 8 个目录、初始化了 git 仓库」）
```

第 3 步的函数**现在住在 `scripts/init_vault.py`，要被服务调用，得挪地方**——见第八节。

## 五、迁移

### 5.1 前置检查

| 检查 | 不过怎么办 |
|---|---|
| 目标路径**不存在，或存在但是空的** | **通过**——这正是要的那两种目标 |
| 目标路径已存在**且有任何一个条目** | 拒绝。报「目标非空（有 N 个条目）」，让用户另选一个 |
| 当前不 busy | 拒绝。报「正在整理，等它跑完」 |
| 源库存在且是库 | 拒绝。报「当前库不在了」——这本身是异常状态 |
| 目标不是源自己 / 不是源的子目录 | 拒绝。`D:\a` 搬到 `D:\a\b` 会把库搬进自己肚子里 |

**「非空」的判据是「有任何一个条目」**，不区分是不是库——连一个空文件夹都不算非空，
但一个 `.DS_Store` 就算。理由：迁移做完就把目标**当成新库**了，
里面原有的任何东西都会混进笔记树。

### 5.2 搬家过程

```
1. 置 busy = "migrate"                    ← 挡住半路投递/整理
2. copytree(源 → 目标)                     逐文件拷贝
3. 校验：文件数 + 总字节数两边一致          ← 不一致就回滚
4. rmtree(源)
5. 写 .env 新路径 + reload_config          ← 复用 apply_settings
6. 清 busy
```

**第 3 步的校验只比文件数和总字节数**，不逐文件哈希。理由：这库按几千条设计（Q95），
727K 时哈希是零成本，但真到几千条、带附件时逐文件哈希会明显变慢，而**拷贝被截断
几乎必然改变文件数和字节数**。要在计划里写明这个取舍，别让人以为漏了。

**失败时回滚目标目录，源库一根汗毛不动。** 这条是铁律：
数据有两份的时候，永远让**旧的那份先活着**，新的可以再造。

### 5.3 半路迁移为什么必须挡

用户问过「整理完再迁移」和「半路迁移」哪个风险大，答案是**半路大得多**，因为
失败的样子是「看起来一切正常」：

`organize_selected`（`organize.py:325-369`）一轮整理里会**多次**读 vault——
每条草稿规划时 `list_domains` + `find_candidates`，落盘时 `write_note`。
迁移插在中间，一次整理就被劈成两半：

| 劈在哪 | 后果 |
|---|---|
| 前一半落进旧库、后一半落进新库 | 最后那个 `commit_changes`（`organize.py:449`）只在新库里提交，**旧库那半永远不进 git**，但它们躺在旧库磁盘上，看起来正常 |
| `append_results` 写日志时库已经换了 | 整理日志只记了后半截，前半截的笔记**在日志里不存在** |
| `write_note` 自己的 `mkdir(parents=True)` 落旧路径 | 旧库那边**长出半个骨架**——`_收件箱` 有、领域空，正是第三节那个坑 |

挡住它的机制很便宜：`state["busy"]`，投递/整理端点开头查一次。

### 5.4 迁移之后 `data/` 不用动

**已核实**：`data/logs/flow/*.jsonl` 里记的路径**全是 vault 相对路径**（0 条绝对路径），
`data/state.json` 只有巡检状态。所以换库不影响 `data/`，不用搬。

## 六、移除

### 6.1 删什么、不删什么

| 删 | 为什么 |
|---|---|
| vault 目录整棵 | 笔记本体 |
| `data/chats/*.json` | `save_chat` 把**整段 messages** 存盘（`chat_store.py:61-75`），对话里引用过的笔记正文**在里头** |
| `data/logs/` | 运行日志与流程日志里有笔记路径、标题。**今天那两个正被服务打开的文件删不掉，跳过**，见 9.4 |
| `data/state.json` | 巡检状态 |
| `.env` 里的 `KB_VAULT_PATH` | 解绑。**这一步是直接写空，不走 `settings.validate`**——它是一次「移除」，不是一次「设置保存」；9.2 那条拦空值的校验只管设置窗那条路 |

| 不删 | 为什么 |
|---|---|
| **`data/runtime/service.json`** | **删了就是「停不掉的孤儿进程」**——那份文件是 `kb stop` 唯一的线索，探活失败时 `stop_service` 还会顺手把它清掉（见 `docs/04_踩坑与经验.md` 第 21 条、`03_问题记录.md` 待解决第 5 条）。服务自己正在跑，删自己的身份文件是纯粹的坏主意 |
| `data/cache/` | pytest / ruff 的缓存，不是知识 |
| 模型配置（`.env` 里的三个键） | 用户明说保留 |
| `.env` 其余键（端口、皮肤、日志级别……） | 跟库无关 |

### 6.2 怎么删得干净

`shutil.rmtree` 在 Windows 上会被占用中的文件挡住（Obsidian 开着、资源管理器停在库里、
杀毒软件正在扫）。**先改名再删**：

```
1. os.rename(vault, vault 同盘的 ".<名字>.deleting-<时间戳>")
2. rmtree(那个改好的名字)
3. 失败的话把名字改回去，报「有文件被占用，先关掉 Obsidian / 资源管理器再试」
```

改名在同盘内是原子的、瞬间完成，所以**「删了一半」这个窗口从一开始就不存在**——
要么库还在原地，要么它整个变成了一个待删的目录。第 3 步的改名回去保证失败可逆。

`data/chats` / `data/logs` 同理，但它们小、且不被别的进程占，直接 rmtree + 有错就报。

### 6.3 确认界面

用现成的 `.modal.notice`（`style.css:993-1000`，`base.html:159-167` 那个
「服务已停」通知就是它），内容换成：

- 标题：**移除知识库**
- **将要删掉的具体清单，带数量**：`34 篇笔记 · 2 条草稿 · 7 段会话 · 全部整理日志`
- 一句：**这一步不能撤销，也不进回收站**
- 一个「我知道，删了找不回来」的勾选框（没勾时「移除」按钮不可点）
- `[取消]` `[移除]`（红）

**为什么先给数量而不是先给警告**：数量让人**看一眼就知道删的是不是他以为的那个库**。
一句「确定要删除吗」在删 3 篇和删 3000 篇时长得一模一样。

**不用浏览器原生 `confirm()`**（`quitService` 那个做法，`base.html:316`）：
原生 confirm 不能放清单、不能放勾选框，而且和其余界面的样式是两套。

### 6.4 移除之后

- 状态回到「未初始化」，首屏那张引导卡回来（`first-run.html` 左半张）
- **模型配置还在**，重新初始化时不用再填一次
- 「移除之后再回来」那张 mockup（`wizard.html` 下半张）**只取它的文案，
  那张卡本身不做。** 定稿见 4.1：未初始化态**就是**那条龙本身，首屏引导卡
  的按钮 `showGroupByName('知识库')` 直接滚到它，**不是两套界面**。
  卡片 → 卡片 → 龙 是三层，跟 4.1 冲突——照 mockup 再建一张卡就是把它加回来。
  那段文案的落点在 4.2 那条龙的第①段。

## 七、路由与接口

设置窗相关的一律放 `src/kb/web/router.py` 的 `build_router`（现有 `/settings`、
`/settings/test`、`/quit` 都在那儿）。**注意注册顺序：`include_router` 早于
`http.py` 的 app 级路由，同名路径放 app 级会变成死代码**（`http.py:546-549` 有注释）。

| 路由 | 方法 | 作用 |
|---|---|---|
| `/setup/state` | GET | `{initialized, vault_path, domains, counts:{notes,drafts,chats}, busy}` |
| `/setup/init` | POST | body：模型三件套 + `vault_path` + `domains[]` → `{actions, vault_path, domains}` |
| `/setup/migrate` | POST | body：`{target}` → `{moved:{files,bytes,notes}, vault_path}` |
| `/setup/remove` | POST | → `{removed, failed, notes, vault_removed}` |
| `/setup/check` | GET | 可选：`?path=<绝对路径>` → `{exists, writable, looks_like_vault, entries}` |

**后三个的返回比这张表原来写的宽**（2026-09-22 施工后补齐）：多出来的字段不是
顺手加的，是界面要用的——`init` 的 `vault_path`/`domains` 让那条龙建完就能显示
「建在哪儿、有哪些领域」；`migrate` 的 `vault_path` 让界面上报搬到哪去了；
`remove` 的 `failed`/`notes` 是**必须**的，因为移除做不到「全部成功」
（今天正在写的日志文件删不掉），界面得如实说哪几项留下了、为什么。
原来的表只写 `{actions:[...]}` / `{removed:[...]}`，照着实现对不上界面。

`moved` 里那个 `notes` 是 2026-09-22 修缺陷时补的，理由值得单记：迁移的最后一步
是删掉旧库，而**这一步失败时新库已经是唯一完整的一份**——所以不能回滚（回滚会把
好的那份也毁掉），只能「保住新库、如实说旧库没删干净」。没有 `notes` 这个出口，
那条路就只能抛异常，而抛异常会把一件**已经成功**的事报成失败。

**busy 标志**：一个带锁的小对象，在 `create_app` 里造、同时给 `http.py` 的 app 级路由和
`build_router` 用。`build_router(...)` 要加一个参数。

```python
class Busy:
    """谁在动 vault。同一时刻只允许一件事。"""
    def acquire(self, what: str) -> bool: ...   # 拿不到返回 False，不等待
    def release(self) -> None: ...
    @property
    def what(self) -> str | None: ...
```

**`/organize`、`/push`（带整理的那个）、`/setup/migrate`、`/setup/remove` 四个入口开头
都先 `acquire`**，拿不到就 409 + `{"detail": "正在整理，等它跑完再试"}`。

**`/setup/init` 单独一条规矩**：只在「未初始化」时才允许（已初始化时 400，
文案指向「要改去对应设置，要搬用迁移」）。它**不加 busy 锁**——那个状态下没有
别的事在跑，加了反而是空转。

**未初始化时，投递与整理端点也要挡住**（409 + 指向初始化的提示）。
前端的置灰只是界面礼貌，**端点必须自己拦**——`kb.bat push` 走的是 CLI、
接入指南里的会话层 AI 走的是 `/push`，它们都绕过界面。

### 为什么要搬 `init_vault`

`scripts/` 与 `src/kb/` 之间**现在没有桥**：`src/` 下没有任何文件 import `scripts`，
`pyproject.toml` 的 `pythonpath` 只有 `src`（`scripts` 能被测试 import 是因为
`tests/__init__.py` 让 pytest 把仓库根插进了 `sys.path`）。

服务进程**恰好**能 import 它——`spawn_service` 用 `-m kb.api.http` 且 `cwd=PROJECT_ROOT`
（`runtime.py:122-142`），`python -m` 把 cwd 放进 `sys.path[0]`。**这是巧合，不是设计**：
换个人从别的 cwd 起服务就断。而且「vault 结构的唯一真源」放在一个服务读不到的地方，
本来就不该。

所以把逻辑**下沉到 `src/kb/core/vault_setup.py`**，`scripts/init_vault.py` 留成薄壳。
README 那句「这个脚本是 vault 结构的唯一真源」改成指向 `vault_setup.py`。

## 九、边界与错误处理

### 9.1 初始化

| 情况 | 处理 |
|---|---|
| 路径不存在 | **允许**，`init_vault` 会建（`mkdir(parents=True)`） |
| 路径存在、里面有东西 | **允许**，幂等，已有的不碰。但要提示「这个目录里已有 N 个条目，只会新建缺的部分」 |
| 路径存在、已经是另一个库 | 允许，幂等。但它会成为当前库 |
| 一个领域都没勾 | 前端挡住（按钮不可点）+ 后端 400。**理由要说清**：一个都没有的话投进来的每条都会掉进「待归类」 |
| 模型配置填错 | 允许保存，但「测试连接」会失败。**不强制先测**——用户可能就想先建库 |
| 路径不可写（只读盘、没权限） | 建目录时 `PermissionError` → 400，文案指向具体路径 |

### 9.2 改路径（已初始化之后）

路径框**保持可编辑**（用户 mockup 里就是这样）。保存时后端校验：

| 目标 | 结果 |
|---|---|
| 是个已初始化的库（含 `.git`） | 通过。换指向——**这是「换机器后路径变了」那条路** |
| 不存在 / 存在但没有 `.git` | **400**，文案：`那儿还没有知识库。想搬过去用「迁移到别处」，想从零建先「移除知识库」` |
| 空 | **400**，文案：`要解绑请用「移除知识库」，它会把痕迹一起清掉` |

**为什么不给「留空 = 解绑」**：那会留下笔记、会话、日志在原地，
而界面上显示成「还没有知识库」——**痕迹还在，界面说没了**，正是本设计要消灭的那种状态。

### 9.3 迁移

| 情况 | 处理 |
|---|---|
| 目标非空 | 拒绝，带条目数（见 5.1） |
| 目标是源自己 / 源的子目录 | 拒绝 |
| 目标是源所在盘之外 | 允许（`copytree` 天然跨盘） |
| 拷贝中途失败 | 回滚目标目录，源不动，报错 |
| 校验不一致 | 同上，并报出「拷了 N 个文件，源有 M 个」 |
| 搬家时服务被 `/quit` | 迁移是同步的，退出排在它后面。**不额外处理** |

### 9.4 移除

| 情况 | 处理 |
|---|---|
| vault 目录被别人占着 | 改名失败 → 报「先关掉 Obsidian / 资源管理器」 |
| vault 目录已经不在了 | 照删其余部分，最后报「笔记目录本来就不在了」 |
| `data/chats` 不存在 | 跳过，不算错 |
| 删到一半出错 | `data/chats` / `data/logs` 是逐个删的，报出「这几项删掉了、这几项没删掉」 |
| **今天的日志文件正被服务自己占用** | **跳过它**，在结果里说明「有 N 个日志文件正被服务打开，重启后可以再清一次」。见下 |

**日志文件那条值得单独说**：`data/logs/kb/2026-09-22.log` 是服务**当前正在写**的文件
（`logging_setup.py:86`），`data/logs/flow/2026-09-22.jsonl` 同理。
Windows 上正被打开的文件删不掉，所以**移除不可能做到字面意义上的「一点不留」——
今天那一份一定留着**。

这不是设计妥协，是操作系统的边界，**要在界面上说实话**：清单里写
「全部日志」时，底下的结果得说「今天那两个日志文件服务还开着，下次重启后可以再清」。
不写这一句，用户下次在 `data/logs/` 里看见文件会以为移除没生效。
