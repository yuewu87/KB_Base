**KN_Base —— 人机共用的知识库系统。**

工程代码在 `E:\Study_Projects\KN_Base`，知识数据在 `E:\KB_Library`。两者物理分离，各自独立版本管理。

> **状态：2026-09-17。** 架构已定案，**主体已实现**——逐条进度见第十三节的实现步骤表，还缺什么见第十四节。逐条的理由与由来见 [`03_问题记录.md`](03_问题记录.md)，那才是设计状态的唯一真源——**本文只写「是什么」，不写「为什么」**。

### 每块是干什么的

| 块 | 干什么 | 和谁说话 |
|---|---|---|
| **会话层** | 你在 Claude Code 里说的话，它挑值得记的投递出去。**只投递、发请求、接收**，不背任何整理规则 | → 服务（发请求） |
| **服务** | 收下内容、判断放哪、写进库、把结果返回。整理规则全在这里，改一处全生效 | ↔ vault（读写） |
| **vault** | 就是一堆 markdown 文件加目录。**没有数据库、没有隐藏格式**，用记事本也能打开 | ← Obsidian 打开 |
| **Obsidian** | 你看的地方。查看、检索、随手改 | 你 |
| **Web UI** | 不开会话也能随手记、看日志、跟 AI 对话。六个入口：记一条 / ai对话 / 整理日志 / 工作日志 / 运行日志 / 巡检 | 服务 + 你 |

### 三条要点

1. **整理不是会话行为，是服务行为。** 任何会话只管投递，规则收拢在服务一处——换个会话、换个工具，行为完全一样。
2. **数据是纯 markdown。** 没有锁定，Obsidian 只是它的一个视图，卸载了文件还在。
3. **检索不靠文件夹，靠标签。** 文件夹决定「物理放哪」，标签决定「属于哪些主题」——所以文件夹放错了也不影响找得到。

## 一、定位

**人机共用，但偏 AI。**

- **人这一侧**：只用 Obsidian 做三件事——查看、检索、随手改
- **AI 这一侧**：主要使用者。会话里的 AI 直接查

**核心是知识的关联性和检索能力**，不是「放对位置」。放错位置可以接受。

---

## 二、数据本体

是 `E:\KB_Library` 里的 **markdown 文件 + 目录结构 + frontmatter 字段**，不是 Obsidian。

Obsidian 只是这些文件的一个视图——随时卸载，文件仍在，git 历史仍在。选本地 markdown 而非数据库，是因为 **AI 友好、对人可读、无锁定**。

## 三、两层

| | 是谁 | 干什么 |
|---|---|---|
| **第一层** | 会话 AI（Claude Code / DeepSeek Harness 等） | **只**投递、发请求、接收。不背整理规则 |
| **第二层** | 知识库服务 | 处理请求、分发、检索、返回 |

**第二层的形态：LLM 链式工作流，agent 之间无交流。**

确定性流水线，LLM 只在固定调用点上工作（规划、审核判断、标题提炼）。**没有管理 agent，没有 agent 之间的对话。** 审核是链上的一步，不是独立进程。

## 四、目录结构

```
E:\KB_Library\
├── 计算机/                    ← 领域（知识）
├── 艺术/
├── 文学/
├── _收件箱/                   ← 机器目录
│   └── 待归类/
├── _索引/
│   └── 整理日志/
└── _附件/
```

**领域是「知识」，`_` 开头的是「机器目录」**——混在同一层，靠下划线前缀区分。

### 领域

**一级目录即领域。** 领域是知识分类的顶层，人建、固定。

**起手三个：**

| 领域 | 装什么 |
|---|---|
| `计算机` | 代码、工程实践、工具链，以及跨领域的方法论 |
| `艺术` | 绘画、设计 |
| `文学` | 小说、写作 |

**怎么划出来的：** 借现成分类体系的思路（杜威十进分类法 DDC），**用日常词命名**。不照搬——个人知识库照搬图书馆分类会背离「简易清晰」；但也不自己发明，因为「按一套公认规则来就不会乱」。

**划领域的标准：** 互斥（一条内容只有一个地方说得通）· 自成一个实践圈 · 粒度均匀。**「其他」「杂项」这类兜底领域不允许存在**——注定变垃圾桶。

**新增领域由人处理**（上报 → 确认）。**领域内分类由 AI 自建**，见下。

### 领域内分类

**领域内部的子分类由 LLM 自己建，边用边长。**

| 层 | 谁管 | 怎么管 |
|---|---|---|
| 领域（一级） | 人 | 新增要上报确认 |
| 领域内分类 | LLM 自建 | 由**审核**管 |

**整条路径的目录最多 4 层**（领域算第一层，文件名不算），`validate_plan` 强制（Q94）。

**新建时的规则：与前缀重叠就归旧，不新建。**

> **⚠️ 放开时机未定。** 审核是后续阶段才有的，「放开自由分类」排在审核之后。在此之前，领域下先平铺。

### 机器目录

| 目录 | 干什么 |
|---|---|
| `_收件箱/` | 所有未定稿内容的统一入口。**空的才是健康状态** |
| `_收件箱/待归类/` | 归不了类的暂存，不阻塞流程 |
| `_索引/` | 索引页（Dataview 查询，服务自动生成） |
| `_索引/整理日志/` | 按天聚合，每次整理往当天那篇追加一节 |
| `_附件/` | 图片等小文件 |

**索引页按现有目录分**（一个目录一个），由知识库定时整理时顺手更新。

### vault 是纯数据

**vault 里不含任何规则或说明文件**——没有 `CLAUDE.md`，没有使用说明，没有模板。规则全在服务侧（代码里）。

理由是两份约定会漂移：vault 一份、服务代码一份，改了一边忘了另一边，就会留下**一份没人读又会说错话的文档**。

**边界：数据在 vault，规则全在服务侧。** 换库、重建库都不牵动规则。

## 五、笔记

### frontmatter

```markdown
---
类型: 概念 | 踩坑 | 决策 | 经验 | 清单 | 日志 | 索引
主题: [计算机, git]        # 标签，可多个 —— 检索主力
项目: KN_Base              # 可选。项目已降为字段，不是目录
来源: 会话 | 书籍 | 网页 | 论文
创建: 2026-09-16
更新: 2026-09-16
---

# 一句话结论

## 展开

## 相关
- [[某篇已有笔记]]
```

**这三个字段里，只有 `类型` 是模型判断的。** `主题` 与 `项目` 由服务算出来，模型填了也会被覆盖（Q101）：

| 字段 | 归谁 | 为什么 |
|---|---|---|
| `类型` | **模型** | 判断题——这条算概念还是踩坑 |
| `主题` | **服务** | 路径派生 + 模型补语义标签，再由服务合并去重（见第六节） |
| `项目` | **服务** | 从草稿**原样搬**——一个字的判断都没有 |

**fold 追加的新章节插在 `## 相关` 之前。** 上面骨架里 `## 相关` 是收尾节，
原先是直接把新内容拼在文件末尾，把它挤到文章中间、后面还挂着新章节（Q101）。
找不到 `## 相关` 的笔记（用户自己改过）照旧追加到末尾——不猜他想放哪。

**文件名统一用内容标题。** 没有「项目笔记」这个类别，所以也没有 `<项目名>-<类型>.md` 那种可推导路径——**所有笔记一视同仁，找笔记靠检索**。

**标题清洗规则：**

1. 去掉文件系统非法字符：`\ / : * ? " < > |`
2. 去掉首尾空白和结尾的点
3. 长度上限 **60 个字符**，超出截断
4. 保留中文，不做大小写转换

**草稿文件名用 id 而非标题：** `_收件箱/<YYYYMMDD>-<4 位十六进制>.md`（如 `20260916-a3f2.md`）。

用 id 是因为它是对外接口（`kb organize <id>`），文件名与之一致最不容易出错；草稿生命周期短，可读性由 Obsidian 的看板提供。

**修改请求用文件名定位：**

会话层给出目标**文件名**（不含路径、不含 `.md`），服务全库搜同名文件：

| 搜索结果 | 处理 |
|---|---|
| 唯一命中 | 定位成功 |
| 零命中 | 进 `_收件箱/待归类/`，报告里列出 |
| 多个命中 | 同上——**不猜是哪一个** |

用文件名而非路径，是因为 Obsidian 本身就是按文件名链接的，与它一致；而且**会话层不需要知道目录结构**。

### 三条硬约束

**① 不允许孤儿笔记。** 每条正式笔记至少链到一处已有笔记或索引页。孤儿是检索不精准的根因。

> 空库第一天没有任何笔记可链，所以**索引页必须自动生成**——这样第一条笔记就有东西可链，约束从第一天起成立。

**② 链接要说得出「这两篇的共性是什么」（Q100）。** 只剩个 `[[X]]` 不算——正文里链的，
让那句话把共性说清楚；列在 `## 相关` 一节里的，**链接后面用 `——` 写一句**。
**说不出来就别链。**

> **为什么加这条**：2026-09-18 实测——116 条链接里 **99 条（85%）挤在 `## 相关` 一节**，
> 而其中 **85% 光秃秃不给理由**。根因是「模板有个叫『相关』的空章节」+「硬规则要求至少
> 一个链接」的组合：**模型最省力的做法就是往里丢链接，不用说为什么**。入链冠军有 11 条入链，
> 只有 2 条写了理由；它自己的 `## 相关` 里就一行 `- [[计算机]]`，索引页凑数。
>
> 方向没走偏（没有大面积链索引页凑数，剔掉领域标签后 82% 的连接两边仍有共同标签），
> 缺的是**「凭什么算相关」没有变成要求**。见 [`03_问题记录.md`](03_问题记录.md) Q100。

**③ 而且共性要具体到能被检验。** 同一个工具、同一层机制、同一类失败模式。
「都是坑」「都要显式写」「同属知识管理」这种说了等于没说的不算。

> **上面那句「说不出来就别链」不足以独立成立**：它和「不允许孤儿笔记」（①）打架——
> 一篇笔记真跟谁都不像时，模型会**编一个理由**而不是放弃链接。2026-09-18 的对照实测里，
> 真有共性的草稿 3 条链接全带具体理由，跟谁都不像的那篇就编出了
> 「同属知识库工具的使用经验，都是想要的行为必须显式写出来」——这话换任何两篇工具笔记
> 都成立。手法同规则 1 的「『编码』和『字符集』不算重复」：**给反例比给正例管用**。
>
> **① 没松动**：孤儿是孤岛，代价比一条牵强的链接大；而且理由现在写在明面上，
> 读到牵强的一眼能看出来——**从「看不见质量」变成「质量可见」本身就是收益**。

## 六、标签

**`主题` 标签是检索主力，不是文件夹。**

文件夹决定「物理放哪」，标签决定「属于哪些主题」。**一篇笔记能挂多个标签，不能放多个文件夹**——这正是标签比文件夹灵活的地方。

**标签来源：两者都要。**

- **路径派生**：领域 + 领域内分类，保证标签与物理位置基本一致
- **AI 另提**：不管路径，按内容另给语义标签，用来表达跨领域的归属（如「用代码生成艺术」同时挂 `计算机` 和 `艺术`）

**具体规则：**

> ⚠️ **只有 ② 是模型做的，①③④⑤ 全部由代码执行**（`planning.derive_tags`）。
> **路径在手边、大小写是字符串操作、数量是个数字——没有一条需要判断。**
> 2026-09-18 之前这几条全都只写在提示词里、代码一行没兜，于是「`主题` 会不会空」
> 全看模型记不记得填；而提示词里让它填的那个 `target_tags` 字段，
> `OrganizePlan` 根本没有对应属性，模型算完直接被丢掉。见 Q101。

**① 路径派生。** 笔记落在哪条路径上，`主题` 就自动带上这条路径的**各级目录名**。

```
计算机/git/暂存区是全有或全无.md   →   主题: [计算机, git]
```

**② AI 另提。** LLM 读完内容，再补 **0–3 个语义标签**，只用来表达「还属于哪些别的领域/主题」。这部分与路径无关——正是它让标签比文件夹灵活。

```
计算机/git/暂存区是全有或全无.md   →   主题: [计算机, git, 版本控制]
```

**③ 合并去重。** 两组拼起来去重。**领域名永远排在最前**，其余按出现顺序。

**④ 写法规范：**

| | |
|---|---|
| 大小写 | 英文标签一律小写（`git`，不是 `Git`） |
| 分隔符 | 中间空白折成 `-`（`版本 控制` → `版本-控制`） |
| 长度 | 单个标签不超过 20 字符 |
| **不造近义** | 已有 `版本控制` 就用它，不新建 `版本管理`——**这是标签去重的实质** |

**⑤ 数量：** 路径派生部分不设上限（路径深就多）；**AI 另提的最多 3 个**——标签一多就失去区分力。

**检索不依赖文件夹，这是容错的前提**——领域内分类由 AI 自建、会自己长，放错了只影响人翻目录，不影响检索。

## 七、写入流程

```
会话中随手记
     │  kb push --content "..." --project "KN_Base"
     ▼
_收件箱/                ← 异步落草稿，立刻返回，不阻塞会话
     │                    （留反悔窗口：`kb drop` 可删；编辑与合并靠重投）
     │  会话 AI 判断时机，或用户主动说
     ▼
整理三段式
     ├─ ① 规划（只读）  调 LLM 产出变更计划，不碰文件
     ├─ ② 校验（只读）  纯静态检查：枚举合法？引用存在？路径冲突？
     └─ ③ 落盘（写入）  纯文件操作，不调 LLM
     ▼
<领域>/                ← 正式笔记
     ▼
git commit（一次整理 = 一个 commit）+ 事后报告
```

### 投递接口

```bash
kb push --content "..." --project "KN_Base" --source 会话
echo "..." | kb push            # 长内容走 stdin
```

- **一次投递 = 一条草稿**，多条就调多次。CLI 越简单，agent 越不容易用错
- **agent 只交正文**，不填 `类型` / `主题` / 分类——那等于把整理判断泄漏到每个会话
- `--project` 可选。项目名默认取 **git 仓库根**的目录名（不是 cwd，避免 agent 停在子目录时取错）

**默认值是猜的，所以要有退路。** 在临时目录里投，`--project` 就会取到那个临时目录名；投重复、投错内容也一样。草稿进了收件箱不等于定案。

### 撤回草稿

```bash
kb drop 20260918-9e4f                    # 一条
kb drop 20260918-9654 20260918-9e4f      # 多条
```

- **也只走服务**——手改 vault 会把「写入只此一路」的规矩开口子，绕过它就没有串行化、没有校验
- **不留记录、不打 commit**：删等于「当没发生过」，流程日志上不该多一笔，也不该为它单打一个提交。**这不是审计场景**
- 找不到的 id 报出来、**退出码 1**，但**其余几条照删**——批量删的时候一条对不上不该把别的废掉
- **只删草稿**，碰不到笔记

> 「投错了能撤」是 2026-09-18 补的（[Q99](03_问题记录.md)）。此前收件箱只有「进」没有「出」，投错一条就只能让它烂在库里。

### 三段式为什么这样切

**把 LLM 的不确定性和文件写入彻底分开。**

LLM 只参与第一段（只读，可无限重试）。校验段不靠 LLM 自我保证，用机器检查——这一步拦掉绝大多数幻觉类错误，且 vault 一个字节没动。落盘段不调模型，所以是确定性的、快的、失败率极低的。

### 审核

**是链上的一步，不是独立进程。** 位置在「规划」之后、「落盘」之前。

**审什么——只审规则，不审内容：**

| 检查项 | 具体判什么 |
|---|---|
| **路径合法** | 落在某个领域下吗？层级超过上限了吗？ |
| **类型合法** | `类型` 在固定枚举里吗？ |
| **分类不重复** | 要新建的分类，和同层已有的近义吗？**近义就归旧，不新建** |
| **链接存在** | `[[...]]` 指向的笔记真的存在吗？ |
| **文件名合规** | 标题清洗规则走了吗？ |

**不审什么：** 「内容该不该这么归类」——那是规划的活。**审核只判断「名字和路径合不合规则」。**

**为什么必须独立：** 如果它还兼着规划，就是自己审自己。它必须**只对规则负责**。

**为什么能交给 AI 审：** 因为审的是**规则**不是**内容**——规则可以逐条写下来，判断就变成了对照检查。这跟「这条内容该归哪」那种主观判断是两回事。

**分类不重复怎么判：** 分类数量少（一个领域下撑死几十个），**把同层已有的分类全列给 LLM 看**即可，不需要预筛机制。规则一句话：**能用已有的就用已有的。**

### 谁触发整理

**由会话 AI 判断时机**（项目暂停时、半天未整理等），用户也可主动发起。

**前置条件只有一个：发请求前先确认没有需要推翻的结论。**

### 整理范围

- **投递 → 整理**：处理的是**新草稿**。`kb organize` 整理全部，`kb organize <id>` 只整理某条
- **定时整理**：巡检的是**已有笔记**——它们不会自己变，但标签会长乱、索引会过期。见下

## 八、修改已有的笔记

**走 `--revise <文件名>`：**

```bash
kb push --content "这条结论要改……" --revise "并发写锁"
```

会话层**显式指明**「这条取代那条」。

**为什么不写 frontmatter 让模型填：** `--revise` 是明确说出来的；写 frontmatter 等于让 LLM 自己填一个判断字段，和「agent 只交正文」相冲。

**失效而非覆盖：** 旧内容**不删**，打失效标记保留，**默认排除出检索结果**（点时间查仍可得历史）。

**失效必须由会话层显式指定，不由服务靠相似度猜。** 调研查到 Graphiti（Zep）的双时态失效在生产上出过事故——**被自动失效的事实里 70% 其实还是真的**，因为它挑候选时用语义相似度、不要求候选与新事实共享同一个实体，一次 LLM 调用返回裸索引，系统照时间戳算术直接落。结果只是用词相近的两条互相误伤。

## 九、知识库定时整理（巡检）

**收拾的是标签和目录，正文一个字不动。**

**与「投递 → 整理」的区别：** 那条链处理一条**新草稿**；这条巡检**已有笔记**。「边用边长」的另一半——长出来的东西要有人收拾。

### 什么时候跑

| 触发 | 条件 |
|---|---|
| **自动** | **服务启动时**检查，距上次超过 **6 天**就跑 |
| **手动** | 网页侧栏「巡检一次」按钮，或 `kb sweep`。**不受 6 天限制**——是你主动要跑的 |

自动那次**起后台线程**，不挡你正在做的事；先把「上次巡检」推到现在再跑，免得服务重启重复跑。

### 整理内容

| 做什么 | 动什么 |
|---|---|
| **标签去重** —— 近义标签合并 | frontmatter 的 `主题` |
| **分类合并** —— 近义词目录合并 | 文件位置 + `主题` |
| **更新索引页** | `_索引/` |

**只合并，不新建**：目标必须是**已有**的目录。模型想新建分类，得落在某个领域下（见第七节）。

### 怎么做的

**一次 LLM 调用。** 输入是「全库的标签清单 + 目录树」——**不含任何正文**，所以很小。输出直接是变更计划，不先出「人话建议」再翻译一遍。

```
扫描（只读）→ 规划（LLM，只读）→ 校验（静态）→ 落盘（移动 + 改标签）→ commit → 报告
```

**和整理草稿是同一条链**，只是输入换成了整个库。

**只出建议不出建议的区别：** 巡检**自己就改了**，改完给你一份报告。

**报告下面没有「调整」入口**（2026-09-17 删掉了一版）。原来有个「还需调整」：弹输入框、把你写的话注进提示词、重跑一次。删掉的理由是**后端能力与用户预期对不上**——巡检**只会合并**（`validate` 要求合并目标必须是已有名字，不许新建；`apply_plan` 只 `rmdir` 不建目录），而且**刻意不看笔记正文**，所以「拆开某个分类」这类要求它在结构上**根本表达不了**。与其留一个做一半的入口，不如整条去掉。

### 报告

服务侧存一份**未读**报告；网页的**巡检页**（`/sweep`，Q93）把它显示出来，下面配一个按钮：

```
这次巡检收拾了这些：
  标签：命令行 → shell
  目录：计算机/命令行 → 计算机/Shell

[ 我知道了 ]
```

**「我知道了」只做一件事：把报告标成已读**（不再高亮）。它**不是审批**，也不触发任何动作。

## 十、日志

**按「是不是知识」分成两类，这是唯一的分界。**

| 分类 | 含 | 进 vault 吗 |
|---|---|---|
| **整理日志** | 整理了什么 + 汇报总结 | **进**（`_索引/整理日志/`）——它是知识，可被检索 |
| **技术日志** | 流程日志（每一个流转）+ 运行日志（Python logging） | **不进** |

**技术日志绝不能进 vault**——一旦进去就成了笔记，会被检索、被 RAG 切片、被 AI 当作知识。技术日志是噪音，属于垃圾进垃圾出。

- **整理日志**：按天聚合，每次整理往当天那篇追加一节。**失败也记**——只记成功的话，回头看会不知道当时为什么有东西卡在收件箱
- **流程日志**：记每一个流转——谁发了什么命令、分给谁、谁做了什么、怎么返回
- **运行日志**：`data/logs/`，标准 Python logging，按大小轮转

**报告与整理日志同源**：服务产生一份「整理结果」结构，两个出口——渲染成文本给会话，渲染成 markdown 进 vault。**不写两套逻辑**，否则会出现报告说「新建 3 篇」而日志写 4 篇这种对不上的情况。

## 十一、接口与工程

### 三层接口，共用一份逻辑

| 层 | 谁用 | 通用性 |
|---|---|---|
| **CLI** | 任何能跑 shell 的 harness | **最通用**——「能跑 shell」几乎是所有 agent harness 的底线能力 |
| **HTTP REST** | 任何能发请求的工具 | 底层，另两层都调它 |
| **MCP server** | 支持 MCP 的工具 | 体验最好，覆盖有限 |

三层都是**薄包装**，不含判断逻辑。

### 会话层怎么用

**每个 harness 一份说明书**，放 [`docs/接入指南/`](接入指南/README.md)——告诉会话里的 AI：**记什么、什么时候请求整理、怎么改已有笔记**。

| harness | 形态 | 状态 |
|---|---|---|
| Claude Code | skill | ✅ [`kn-record`](接入指南/kn-record/SKILL.md)，装在用户级 `~/.claude/skills/` |
| Codex | `AGENTS.md` | ⬜ 等这边跑稳了照着改 |
| 其他 | 通用说明 | ⬜ 同上 |

**装用户级而不是项目级**：用法是「在别的项目里干活时，把东西记到这个库」——项目级只有待在 `KN_Base` 目录下才生效，那就本末倒置了。

**触发条件写在这里，不写在本文里**——本文是给人看的，那份指南才是**会话层 AI 读得到的**（[Q30②](03_问题记录.md) / [Q97](03_问题记录.md)）。

**设置（2026-09-17）：** `GET /settings` 返回模态窗的片段、`POST /settings` 保存并
**当场重载**、`POST /settings/test` 拿表单里的值试连一次、`POST /quit` 停服务。

**保存即生效**——模型三件套重建客户端、日志级别当场调。

**有两类要等下次启动服务**：巡检间隔与日志保留（服务启动那一刻才判/才清），
以及 vault 路径与端口（路径是一切的前提、端口就是地址本身）。后两个在界面上
是**只读**的，要改得动 `.env`。

### 写入一致性

**所有写入必须经过服务进程。** CLI 和 MCP 都走 HTTP，不直接碰文件。服务没启动时 CLI 报错并提示，而不是自己偷偷写。这样写入天然**串行化**。

服务**按需自动拉起**：启动后把端口写进 `data/runtime/service.json`，CLI 读它去探测——通就投递，不通就后台拉起。

### 端口：自动寻找 vs 固定

**这两件事要分开想，别用一个策略套两种用户。**

| 谁 | 要什么 | 怎么做 |
|---|---|---|
| **CLI / agent** | 不用关心服务开没开 | 自动寻找端口 + `service.json` 自动发现 |
| **人（Web UI）** | 一个**能收藏、不会变**的地址 | **在 `.env` 里把 `KB_PORT` 钉死** |

**默认配置里 `KB_PORT` 是空值 = 每次重启换端口。** CLI 那边完全无感，但人这边书签就废了——2026-09-16 就是这么踩到的：改了代码让服务重启，端口从 56294 换成 54852 再换成 52447，而给用户报的还是旧地址。

**所以部署时应当设 `KB_PORT`。** 它是给人用的那一个入口。

### 工程结构

```
KN_Base/
│
├─ 代码与工程 ───────────────────── 进 git
│  ├── src/kb/
│  │   ├── core/       ← 领域逻辑，不 import web/api
│  │   ├── llm/        ← LLM 抽象层，换供应商不改上层
│  │   ├── api/        ← 对外接口（薄层）
│  │   ├── web/        ← 管理界面
│  │   └── config.py   ← 读工程根目录 .env
│  ├── tests/          ← 测试
│  ├── scripts/        ← 建 vault 骨架等
│  ├── templates/
│  │   ├── 笔记/        ← 笔记骨架 —— **机器读**，套进笔记
│  │   └── 投递/        ← 随手记脚手架 —— **人读**，帮他把话说清
│  ├── docs/           ← 本目录
│  ├── .env.example    ← 配置项清单（.env 本身不入库）
│  └── pyproject.toml · requirements.txt · CLAUDE.md · README.md · kb.bat
│
└─ data/ ────────────────────────── **不进 git**
    ├── logs/           ← 运行日志
    ├── runtime/        ← service.json
    ├── chats/          ← 会话历史
    └── cache/          ← pytest 与 ruff 的缓存
```

### 为什么这样分

**第一刀按「进不进 git」切，第二刀按「谁读」切。**

- **进不进 git 是最硬的一条线**——代码仓库是 **public** 的，运行数据进去就是**公开发布**。所以 `data/` **整棵排除**，`.gitignore` 一行搞定，那条线一眼看得见。
- **`templates/` 分两层是因为它们服务的人不同**：`笔记/` 是**给机器看的 schema**（服务套进笔记），`投递/` 是**给人看的脚手架**（写东西时帮他把话说清）。混在一个平铺目录里看不出区别。

**不按「文件类型」切**——`log` 和 `模板` 看着都是文本，但一个绝不能进 git、一个必须进。放一起就把红线糊了。

**`.env` 留在根上**：它是**配置**不是运行数据，而且是启动时的约定位置。

**代价**：换机器时 `data/` 不跟着 git 走，要手动拷——里面的日志和会话本身也未必需要带走。

### git 提交策略

**一次整理 = 一个 commit。** 这直接支撑「报告是事后通知」——收到报告后不满意，回退这一个 commit，整次整理干净撤销。

- 服务只 `git add` 自己动过的文件，**禁止 `git add -A`**（否则会把用户正在编辑的笔记一起裹进「AI 整理」的 commit）
- 服务使用独立 git author（`kb-service`），`git log --author=kb-service` 一眼分出「AI 写的」和「我写的」
- 回滚必须精确，**不能用 `git checkout .`**

### 配置

全部走工程根目录的 `.env`（扁平键值）。**配置集中在本文件夹，不散到用户目录。**

`.env` 不入库，`.env.example` 入库——换机器时照着填一份就够。

### 一条硬约束

**`core/` 不许依赖 `web/` 或 `api/`。** 整理是这套系统最容易出错的部分，必须能脱离界面单独跑测试。
