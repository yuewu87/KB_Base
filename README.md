# KN_Base

**一个给 AI 用的个人知识库。** 你在任何会话里随口说一句值得记的话，它自己判断放哪、写成什么、打什么标签；你要查的时候，让会话里的 AI 代你查，或打开网页直接问。

知识存在 `E:\KB_Library`（一个 Obsidian vault），代码在本仓库。两者物理分离，各自独立版本管理。

> **当前状态：核心链路全部打通**，400 个测试全绿，真实 LLM 端到端验过。
> 详细设计见 [`docs/`](docs/)，**那份才是准的**；本文只是入口。

---

## 一、背景：为什么不是「一个文件夹 + 手动分类」

**问题不在存不下，在找不到。**

文件夹的物理位置只能有一个，但一条知识天然属于多个上下文。「IE 缩放导致点击坐标算歪」这一条，属于浏览器自动化、属于坐标换算、属于 RPA 项目——放哪个文件夹都能说得通，放哪个都会在别的场景里想不起来。

所以这个库的三个前提是：

| | |
|---|---|
| **人机共用，但偏 AI** | 你只用 Obsidian 做三件事：看、查、手写「用户的判断」。主要的读和写都是会话里的 AI |
| **本体是纯 markdown** | 没有数据库、没有隐藏格式，记事本能打开。Obsidian 只是它的一个视图，卸载了文件还在，git 历史还在 |
| **检索不靠文件夹，靠标签** | 文件夹决定「物理放哪」，标签决定「属于哪些主题」。**一篇能挂多个标签，不能放多个文件夹** |

最后一条是关键：**文件夹放错了也不影响找得到**。所以「AI 偶尔分错类」不再是致命问题，也就不需要逼人逐条审核。

## 二、架构

### 有哪几块

```
   ┌────────────────┐              ┌────────────────┐
   │    会话层       │              │    Web UI      │
   │ Claude Code 等  │              │  随手记 / 看日志 │
   │                │              │                │
   │  只投递、发请求  │              └───────┬────────┘
   └───────┬────────┘                      │
           │  kb push / kb organize         │
           └──────────────┬─────────────────┘
                          ▼
          ┌──────────────────────────────────┐
          │        知识库服务（本地进程）      │
          │                                  │
          │   收下 → 判断放哪 → 写进库         │
          │   自带 LLM，不占你的会话额度       │
          └──────────────┬───────────────────┘
                         │ 读写 markdown 文件
                         ▼
          ┌──────────────────────────────────┐
          │      vault（E:\KB_Library）       │
          │   计算机/  艺术/  文学/            │
          │   _收件箱/  _索引/  _附件/         │
          └──────────────┬───────────────────┘
                         │ Obsidian 打开它
                         ▼
                   你（查看 / 检索 / 写判断）
```

**会话层和 Web UI 是平级的两个入口**——能力完全一样，只是走 shell 还是走浏览器。以后接 QQ bot 就是再加一个入口，内核不动。

### 一次投递走过的路

```
你说了句值得记的话
    │  kb push
    ▼
_收件箱/                        ← 先落草稿
    │
    ▼
知识库服务整理
    ├─ ① 规划    LLM 决定放哪、写成什么     （不碰文件）
    ├─ ② 校验    机器检查这个决定合不合法    （不碰文件）
    ├─ ③ 审核    新建的分类跟已有的重不重     （只在这一步才调 LLM）
    └─ ④ 落盘    按决定写文件               （不调 LLM）
    ▼
计算机/…/xxx.md                  ← 正式笔记
    │
    ▼
一趟 git commit + 一份报告
```

**为什么切这么细：** 把 LLM 的不确定性和文件写入彻底分开。前三段一个字节都不写，校验不过就打回重来；落盘段不调模型，所以是确定性的、快的、几乎不会失败的。

`审核` 只在模型**要新建分类**时才跑——没新建就不调，不做无谓的往返。

### vault 长什么样

```
E:\KB_Library\
├── 计算机/                  ← 领域（知识）
├── 艺术/
├── 文学/
├── _收件箱/                 ← 机器目录
│   └── 待归类/
├── _索引/
│   └── 整理日志/
└── _附件/
```

**领域是一级目录，人建、固定。** 领域**内部**的分类由 AI 自己长（`计算机/Windows/`、`计算机/RPA/`……），边用边长。

**`_` 开头的是机器目录**，跟知识混在一层，靠前缀区分。

**项目不是一个目录，是一个字段。** 一条笔记可以属于某个项目，也可以不属于——`项目: 04_RPA_restart` 只是 frontmatter 里的一项，不影响它物理上放在哪。这样项目改名不牵动任何链接。

### 一条笔记长什么样

```markdown
---
类型: 踩坑                    # 固定枚举，不许自由发挥
主题: [计算机, windows, 自动化]  # 标签，可多个 —— 检索主力
项目: 04_RPA_restart          # 可选
来源: 会话
创建: 2026-09-17
更新: 2026-09-17
---

# IE 缩放不是 100% 导致点击坐标算歪

## 现象
…
## 原因
…
## 解决
…

## 用户的判断        ← 只由你亲手写。服务落盘时会机械清空这一节

## 相关
- [[窗口置前要请求前台，不要摆弄窗口]]
```

**「用户的判断」那一节，AI 写了也会被丢掉。** 不是靠提示词劝它别写——是靠服务在落盘前**机械清空**。代填等于伪造你的观点，将来回看时分不清哪句是自己想的。

### 三层日志

| | 记什么 | 住在哪 |
|---|---|---|
| **整理日志** | 整理了哪些笔记 | **vault 里**（`_索引/整理日志/`）——它是知识，可被检索 |
| **工作日志**（流程日志） | 从投递到落库，每一步干了什么，一条一句大白话 | 服务侧（`data/logs/flow.jsonl`） |
| **运行日志** | Python logging，技术排查用 | 服务侧（`data/logs/kb.log`） |

**后两个绝不进 vault**——一旦进去就成了笔记，会被检索、被当知识。技术日志是噪音。

## 三、使用方式

### 装环境

```bash
conda create -n kn_base python=3.11 -y
conda activate kn_base
pip install -r requirements.txt
```

配置放在工程根目录的 `.env`（不入库）。照 `.env.example` 填一份：

```
KB_LLM_API_KEY=...
KB_LLM_BASE_URL=...
KB_LLM_MODEL=...
KB_VAULT_PATH=E:\KB_Library        # 可选，默认就是这个
KB_PORT=51823                      # 建议钉死，见下
```

> **`KB_PORT` 建议设。** 留空的话每次重启换端口——CLI 那边无感（它自己会找），但**你收藏的网页地址就废了**。

### 起服务

**不用手动起。** 第一次调 `kb` 命令时它自己会拉起来，之后一直待在后台。

```bash
./kb.bat status     # 看它在不在、在哪个端口
./kb.bat stop       # 改了代码之后要停，否则服务还跑旧逻辑
```

> **改了 `src/` 下的代码，一定 `kb stop`。** 服务是常驻进程，不停的话它仍执行旧逻辑，而且看起来一切正常。

### 投递：让会话 AI 记一条

```bash
kb push --content "并发写入会锁表，最后用队列串行化解决" --source 会话
echo "长内容走 stdin" | kb push
```

**只交正文。** 类型、标签、放哪、叫什么名字——一概不填，那是整理阶段的事。

一次投递 = 一条草稿。多条就调多次。

### 整理

```bash
kb organize           # 整理全部待整理
kb organize <id>      # 只整理某一条
```

**谁决定什么时候整理：** 会话 AI 判断（项目暂停时、半天没整理过），或者你说一句「可以整理了」。**发请求前它必须先确认没有需要推翻的结论。**

### 改一条已有的笔记

```bash
kb push --content "这条结论要改……" --revise "队列串行化"
```

旧内容**不删**，打失效标记保留，**默认不再出现在检索结果里**（点时间查仍能翻到历史）。这样能看出结论是怎么演变的。

### 查

```bash
kb search "缩放"
```

### 网页

```
http://127.0.0.1:51823
```

| 页面 | 干什么 |
|---|---|
| **＋ 记一条** | 选个脚手架帮自己把话说清，写完点投递——**直接归位**，不用等 |
| **ai对话** | 说一句就行：「记一下…」「…是怎么说的」 |
| **整理日志** | 整理了哪些笔记，淡蓝卡片 |
| **工作日志** | 每一步干了什么，旁边一条竖着的流程链 |
| **运行日志** | 技术输出，终端样式 |

**网页投的和 CLI 投的有个区别**：网页是你亲手写的，写完就想看到结果，所以**投完直接走完整理**；CLI 那条是 agent 干活时投的，攒着，由会话 AI 挑时机。

## 四、工程结构

```
KN_Base/
│
├─ 代码与工程 ───────────────────── 进 git
│  ├── src/kb/
│  │   ├── core/       ← 领域逻辑，不 import web/api
│  │   ├── llm/        ← LLM 抽象层，换供应商不改上层
│  │   ├── api/        ← 对外接口（薄层）
│  │   ├── web/        ← 管理界面
│  │   └── config.py   ← 读工程根目录 .env
│  ├── tests/          ← 测试（LLM 全 mock）
│  ├── scripts/        ← 建 vault 骨架等
│  ├── templates/
│  │   ├── 笔记/        ← 笔记骨架 —— 机器读，套进笔记
│  │   └── 投递/        ← 随手记脚手架 —— 人读，帮他把话说清
│  ├── docs/           ← 设计文档，见下
│  └── .env.example · pyproject.toml · requirements.txt · kb.bat
│
└─ data/ ────────────────────────── **不进 git**
    ├── logs/           ← 运行日志 + 流程日志
    ├── runtime/        ← service.json（端口与 pid）
    ├── chats/          ← 会话历史
    └── cache/          ← pytest 与 ruff 的缓存
```

**为什么这样分：** 第一刀按「进不进 git」切——本仓库是 public 的，运行数据进去就是**公开发布**，所以 `data/` 整棵排除。第二刀按「谁读」切——`templates/笔记/` 是给机器看的 schema，`templates/投递/` 是给人看的脚手架，混一起看不出区别。

**代价**：换机器时 `data/` 不跟着 git 走，要手动拷。

### 跑测试

```bash
"D:/Conda_base/envs/kn_base/python.exe" -m pytest -v
"D:/Conda_base/envs/kn_base/python.exe" -m ruff check src tests scripts
```

（本机 `conda run` 会报内部错误，别用；默认的 `python` 没装 pytest，得用绝对路径。）

## 五、文档

| 文档 | 作用 |
|---|---|
| [`docs/01_架构.md`](docs/01_架构.md) | **目标架构**——做成什么样。只写「是什么」 |
| [`docs/02_需求.md`](docs/02_需求.md) | **要什么** |
| [`docs/03_问题记录.md`](docs/03_问题记录.md) | **全部设计决策与理由**——设计状态的唯一真源，只写「为什么」 |
| [`docs/04_踩坑与经验.md`](docs/04_踩坑与经验.md) | **踩过什么、学到了什么**——动手前扫一眼，多半能少踩一次 |
| [`docs/superpowers/plans/`](docs/superpowers/plans/) | 实施计划 |

**最有用的那条结论**（从踩过的坑里总结出来的）：

> **机械约束**（文件名格式、字段非空）→ **代码必须管**
> **判断题**（这条可不可复用、该归哪类）→ **才交给模型**

同一个坑踩了三次才总结出来。写规则之前先问一句：**这条能不能落成一行 `if`？**
