# KN_Base

**一个给 AI 用的个人知识库。** 你在任何会话里随口说一句值得记的话，它自己判断放哪、写成什么、打什么标签；你要查的时候，让会话里的 AI 代你查，或打开网页直接问。

知识存在 `E:\KB_Library`（一个 Obsidian vault），代码在本仓库。两者物理分离，各自独立版本管理。

> **状态：核心链路全部打通**，测试全绿，真实 LLM 端到端验过。
> **细节以 [`docs/`](docs/) 为准**——本文只当入口，不重复那边的设计。

## 一、为什么不是「一个文件夹 + 手动分类」

**问题不在存不下，在找不到。**

文件夹的物理位置只能有一个，但一条知识天然属于多个上下文。「IE 缩放导致点击坐标算歪」这一条，属于浏览器自动化、属于坐标换算、属于 RPA 项目——放哪个文件夹都能说得通，放哪个都会在别的场景里想不起来。

所以这个库有三个前提：

| | |
|---|---|
| **人机共用，但偏 AI** | 你只用 Obsidian 做三件事：看、查、手写「用户的判断」。主要的读和写都是会话里的 AI |
| **本体是纯 markdown** | 没有数据库、没有隐藏格式，记事本能打开。Obsidian 只是它的一个视图，卸载了文件还在，git 历史还在 |
| **检索不靠文件夹，靠标签** | 文件夹决定「物理放哪」，标签决定「属于哪些主题」。**一篇能挂多个标签，不能放多个文件夹** |

最后一条是关键：**文件夹放错了也不影响找得到**。所以「AI 偶尔分错类」不再是致命问题，也就不需要逼人逐条审核。

## 二、有哪几块

```
   ┌────────────────┐              ┌────────────────┐
   │    会话层       │              │    Web UI      │
   │ Claude Code 等  │              │  随手记 / 看日志 │
   │  只投递、发请求  │              └───────┬────────┘
   └───────┬────────┘                      │
           │  kb push / kb organize         │
           └──────────────┬─────────────────┘
                          ▼
          ┌──────────────────────────────────┐
          │        知识库服务（本地进程）      │
          │   收下 → 判断放哪 → 写进库         │
          │   自带 LLM，不占你的会话额度       │
          └──────────────┬───────────────────┘
                         │ 读写 markdown 文件
                         ▼
          ┌──────────────────────────────────┐
          │      vault（E:\KB_Library）       │
          │   计算机/  艺术/  文学/            │
          │   _收件箱/  _索引/  _附件/         │
          └──────────────┬───────────────────┘
                         │ Obsidian 打开它
                         ▼
                   你（查看 / 检索 / 写判断）
```

**会话层和 Web UI 是平级的两个入口**——能力完全一样，只是走 shell 还是走浏览器。以后接 QQ bot 就是再加一个入口，内核不动。

**整理切成四段：** 规划（LLM，不碰文件）→ 校验（机器，不碰文件）→ 审核（只在**新建分类**时才调 LLM）→ 落盘（不调 LLM）。

切这么细是为了**把 LLM 的不确定性和文件写入彻底分开**——前三段一个字节都不写，校验不过就打回重来；落盘段不调模型，所以是确定性的、快的、几乎不会失败的。

> 完整设计（目录结构、笔记格式、标签规则、日志分层……）见 [`docs/01_架构.md`](docs/01_架构.md)。

## 三、怎么用

### 装环境

```bash
conda create -n kn_base python=3.11 -y
conda activate kn_base
pip install -r requirements.txt
```

配置放工程根目录的 `.env`（不入库），照 `.env.example` 填一份。

> **`KB_PORT` 建议钉死。** 留空的话每次重启换端口——CLI 那边无感（它自己会找），但**你收藏的网页地址就废了**。

### 起服务 / 开网页

**不用手动起。** 第一次调 `kb` 命令时它自己会拉起来，之后一直待在后台。

**双击 `web.bat`** 就能用——它确保服务在跑，然后把浏览器打开。**双击 `stop.bat`** 停掉它。

```bash
./kb.bat status     # 看它在不在、在哪个端口
./kb.bat stop       # 改了代码之后要停
./kb.bat web        # 服务没跑就拉起来，然后把网页打开
```

网页侧栏底部也有一个红色的**退出**按钮，效果同 `stop`。

> ⚠️ **改了 `src/` 下的代码，一定先 `kb stop`。** 服务是常驻进程，不停的话它仍执行旧逻辑——**而且看起来一切正常**。

### 日常四条

```bash
kb push --content "并发写入会锁表，最后用队列串行化解决" --source 会话
kb push --content "这条结论要改……" --revise "队列串行化"
kb organize
kb search "缩放"
```

**投递只交正文。** 类型、标签、放哪、叫什么名字——一概不填，那是整理阶段的事。一次投递 = 一条草稿，多条就调多次。

**谁决定什么时候整理：** 会话 AI 判断。规则写在 [`docs/接入指南/`](docs/接入指南/)——**那是会话层 AI 能读到的地方**（一份 skill），不是给它看的说明文档。

**改已有的笔记不会覆盖**：旧内容打失效标记保留、默认不再出现在检索结果里，这样能看出结论是怎么演变的。

### 网页

双击 **`web.bat`**，或直接开 `http://127.0.0.1:51823`（端口由 `.env` 的 `KB_PORT` 决定）。

| 页面 | 干什么 |
|---|---|
| **＋ 记一条** | 选个脚手架帮自己把话说清，写完点投递——**直接归位**，不用等 |
| **ai对话** | 说一句就行：「记一下…」「…是怎么说的」 |
| **整理日志** | 按天的**箱子**，右侧栏「报告 / 历史」两个竖排页签 |
| **工作日志** | 每一步干了什么，页签是「流程图 / 历史」 |
| **运行日志** | 技术输出，终端样式，只有箱子没有页签 |
| **巡检** | 定期收拾标签和目录的建议与报告；「巡检一次」也在这儿 |

侧栏最下面有 **设置**（改模型、日志级别、巡检间隔，**保存即生效**）和 **退出**（停服务）。

**网页投的和 CLI 投的有个区别**：网页是你亲手写的，写完就想看到结果，所以**投完直接走完整理**；CLI 那条是 agent 干活时投的，攒着，由会话 AI 挑时机。

## 四、工程结构

```
KN_Base/
│
├─ 代码与工程 ───────────────────── 进 git
│  ├── src/kb/
│  │   ├── core/       ← 领域逻辑，不 import web/api
│  │   ├── llm/        ← LLM 抽象层，换供应商不改上层
│  │   ├── api/        ← 对外接口（薄层）
│  │   ├── web/        ← 管理界面
│  │   └── config.py   ← 读工程根目录 .env
│  ├── tests/          ← 测试（LLM 全 mock）
│  ├── scripts/        ← 建 vault 骨架、一次性迁移脚本
│  ├── templates/
│  │   ├── 笔记/        ← 笔记骨架 —— 机器读，套进笔记
│  │   └── 投递/        ← 随手记脚手架 —— 人读，帮他把话说清
│  ├── docs/           ← 设计文档，见下
│  └── .env.example · pyproject.toml · requirements.txt
│      kb.bat（命令行）· web.bat（双击开网页）· stop.bat（双击停服务）
│
└─ data/ ────────────────────────── **不进 git**
    ├── logs/
    │   ├── flow/       ← 流程日志，一天一个 jsonl
    │   └── kb/         ← 运行日志，一天一个 log
    ├── runtime/        ← service.json（端口与 pid）
    ├── chats/          ← 会话历史
    └── cache/          ← pytest 与 ruff 的缓存
```

**为什么这样分：** 第一刀按「进不进 git」切——本仓库是 public 的，运行数据进去就是**公开发布**，所以 `data/` 整棵排除。第二刀按「谁读」切——`templates/笔记/` 是给机器看的 schema，`templates/投递/` 是给人看的脚手架。

**代价**：换机器时 `data/` 不跟着 git 走，要手动拷。

### 跑测试

```bash
"D:/Conda_base/envs/kn_base/python.exe" -m pytest -v
"D:/Conda_base/envs/kn_base/python.exe" -m ruff check src tests scripts
```
