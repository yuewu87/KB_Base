# KN_Base

**人机共用的知识库系统。**

工程代码在本仓库（`E:\Study_Projects\KN_Base`），知识数据在 `E:\KB_Library`（独立的 Obsidian vault）。两者物理分离，各自独立版本管理。

> **当前状态：最小闭环已实现并端到端验证通过（真实 LLM 跑过）。正在做架构扩张（多 agent、检索、Web UI）。**
> 全部设计决策与理由见 [`docs/问题记录.md`](docs/问题记录.md)，路线图见 [`docs/规划总纲.md`](docs/规划总纲.md)。本文档描述系统的最终形态。

---

## 一、定位

**人机共用**——不是纯 AI 检索库。

- **人这一侧**：Obsidian 承担阅读、编辑、双向链接、搜索。人的判断（`用户的判断` 字段）是库里 AI 检索不出来的、最不可替代的部分。
- **AI 这一侧**：本地服务 + 自带 LLM 负责整理——归类、查重、补链接、更新索引。

**核心设计：把「整理」从会话行为变成服务行为。**

各会话的 agent 只负责**投递**内容，完全不背整理规则；规则收拢在服务里一处维护。这样你在任何项目里随口记一条，不需要那个会话懂目录约定、模板和查重逻辑。

### 数据本体是什么

是 `E:\KB_Library` 里的 **markdown 文件 + 目录结构 + frontmatter 字段**，不是 Obsidian。Obsidian 只是这些文件的一个视图——随时卸载，文件仍在，git 历史仍在。

这也是选本地 markdown 而非数据库的原因：**AI 友好、对人可读、无锁定**。

## 二、系统组成

```
① 任意项目的会话 agent（Claude Code / Codex / DeepSeek harness …）
        │  调用 CLI 投递，只投递，不整理
        ▼
② 知识库服务（Python）
        ├─ 领域逻辑：归类、查重、补链接、落盘
        ├─ LLM 层：自带 API key，专职整理，不占会话额度
        └─ 对外接口：HTTP / MCP / CLI
        │  读写 + 写整理日志
        ▼
③ E:\KB_Library（Obsidian vault，独立 git）
        └─ 人在这里读、写、查、改

④ 管理 Web UI（由 ② 提供，bat 启动）
        └─ 配置、工作记录、运行状态
```

**②的领域逻辑完全不依赖 ④ 和接口层**——换 UI、换协议，整理逻辑一行不动。

### 接口：三层，共用一份逻辑

接入市面上的大多数工具靠**三层**，不是选一种：

| 层 | 谁用 | 通用性 |
|---|---|---|
| **CLI** | 任何能跑 shell 的 harness | **最通用**——「能跑 shell」几乎是所有 agent harness 的底线能力 |
| **HTTP REST** | 任何能发请求的工具、脚本、自动化 | 底层，另两层都调它 |
| **MCP server** | 支持 MCP 的工具（Claude Code、Codex CLI） | 体验最好，但覆盖有限 |

三层都是**薄包装**，不允许含判断逻辑——最终都打到同一个 HTTP 服务。

### 写入一致性

**所有写入必须经过服务进程。** CLI 和 MCP 都走 HTTP，不直接碰文件；服务没启动时 CLI 报错并提示，而不是自己偷偷写。这样写入天然**串行化**，不会出现两份逻辑打架。

服务**按需自动拉起**：服务启动后把端口写入 `runtime/service.json`，CLI 读这个文件去探测——通就直接投递，不通就后台拉起服务、等它就绪、再投递。你无需关心服务开没开，也不用开机常驻。

## 三、数据流

```
会话中随手记
     │  kb push --content "..." --project "电商后台"
     ▼
00_收件箱/          ← 异步落草稿，立刻返回，不阻塞会话
     │                （此处留反悔窗口：可编辑、可删除、可合并）
     │  用户确认「这条可以整理了」
     ▼
整理三段式
     ├─ ① 规划（只读）  调 LLM 产出变更计划，不碰文件
     ├─ ② 校验（只读）  纯静态检查：枚举合法？引用存在？路径冲突？计划自相矛盾？
     └─ ③ 落盘（写入）  纯文件操作，不调 LLM
     ▼
10_项目/ 或 20_知识/   ← 正式笔记
     ▼
git commit（一次整理 = 一个 commit）+ 事后报告
```

### 三段式为什么这样切

**把 LLM 的不确定性和文件写入彻底分开。**

LLM 只参与第一段（只读，可无限重试），产出计划后，写入是确定性的、快的、可回滚的。「LLM 调到一半留下半成品」不会发生——**因为调用 LLM 的阶段根本不写文件**。

校验段不靠 LLM 自我保证，用机器检查。这一步拦掉绝大多数幻觉类错误，且 vault 一个字节都没动。

### 谁触发整理

**只能由用户触发。** 用户在会话中明确说「这条可以整理了」，agent 才调工具。

**硬约束：agent 不得自行判断某条总结「已经稳定了」就触发整理。** 否则与「用户决定」矛盾，异步缓冲也失去意义。

整理粒度单条与批量都支持：`kb organize` 整理全部，`kb organize <id>` 只整理某条。

### 报告与工作日志同源

服务产生一份「整理结果」结构，然后**两个出口**：

- 渲染成文本 → **报告**，给会话/终端。即时，看完即走
- 渲染成 markdown → **工作日志**，写进 vault 的 `40_索引/整理日志/`。持久，可检索

不写两套逻辑——否则会出现报告说「新建 3 篇」而日志写 4 篇这种对不上的情况。

**失败也记入工作日志。** 日志是审计记录，只记成功的话，回头看会不知道当时为什么有东西卡在收件箱。

### 两种日志，不要混

| | **工作日志** | **运行日志** |
|---|---|---|
| 是什么 | 「什么时候整理了什么」，审计记录 | debug / info / error，技术排查用 |
| 谁看 | 你 | 排查故障时 |
| 是不是知识 | 是，可被检索、阶段二可被 RAG 召回 | 不是 |
| 住哪 | vault 内（`40_索引/整理日志/`） | vault 外（`KN_Base/logs/`），轮转保留 |
| 保留 | 长期 | 轮转，保留 N 份 |

**运行日志绝不能进 vault**——一旦进去就成了笔记，会被检索、被 RAG 切片、被 AI 当作知识。技术日志是噪音，属于垃圾进垃圾出。

## 四、vault 目录结构

```
KB_Library/                  ← Obsidian vault 根，独立 git 仓库
├── .obsidian/               ← Obsidian 配置（部分入库，见下）
├── 00_收件箱/               ← 所有未定稿内容的统一入口
│   └── 待归类/              ← 归不了类的内容暂存于此，不阻塞流程
├── 10_项目/
│   └── <项目名>/            ← <项目名>-架构.md、<项目名>-决策.md、<项目名>-踩坑.md
├── 20_知识/                 ← 跨项目可复用知识
│   ├── 后端/ 前端/ 工具链/ 方法论/
│   └── （先建这几个，边用边长）
├── 30_素材/                 ← 创作素材（小说、绘画参考等）
│                              注意：课程知识不在这，归 20_知识/
├── 40_索引/                 ← 索引页与看板
│   ├── <主题>.md            ← 主题索引页，**服务自动生成**（Dataview 查询，零维护）
│   └── 整理日志/            ← 按天聚合，每次整理往当天那篇追加一节
└── 90_附件/                 ← 图片等小文件
```

### `.obsidian/` 部分入库

- **入库**：`app.json`、`community-plugins.json`、插件配置等——换机器时设置基本能跟着走
- **忽略**：`workspace.json`、`cache` 等频繁变动的文件

`workspace.json` 记录「哪个面板开在哪」，每次开关 Obsidian 都变。全部入库会让 git 历史被这种噪音淹没，真正的内容变更反而难找。

### vault 是纯数据

**vault 里不含任何规则或说明文件**——没有 CLAUDE.md，没有使用说明。规则全在服务侧（代码与 `templates/`）。

理由是两条约定会漂移：vault 里一份、服务代码里一份，改了一边忘了另一边，就会留下**一份没人读又会说错话的文档**。规则收拢在服务一处维护，数据与规则的边界才清晰——换库、重建库都不牵动规则。

### 三条结构规则

**① 项目档案与可复用知识分家。**
项目文件夹只放项目专属的东西（架构、决策、踩坑）。从中提炼的**通用**知识抽到 `20_知识/`，两边用双向链接互指。

理由：文件夹的物理位置只能有一个，但知识天然属于多个上下文。留在项目文件夹里会被项目边界锁死——下个项目启动时你根本想不到去翻。

**② 项目内笔记文件名必须带项目前缀**（如 `<项目名>-踩坑.md`）。
每个项目文件夹下都会有 `踩坑.md`，一旦出现同名文件，`[[踩坑]]` 双向链接就产生歧义。

**③ 课程知识归 `20_知识/`，不归 `30_素材/`。**
课程学到的东西就是典型的可复用知识，应与项目经验一起被检索到。「其他分类」这种目录注定变垃圾桶，所以 `30_素材/` 的语义被限定为「创作素材」。

### 收件箱

**所有未定稿内容的统一入口**——agent 投递的和人手写的共用同一个，不分开。本质状态一致，分开只会让你每次纠结「这个该放哪」。

**收件箱空的才是健康状态。**

## 五、笔记字段

```markdown
---
类型: 概念 | 踩坑 | 决策 | 经验 | 清单 | 日志 | 索引
主题: [后端, 数据库]        # 标签，可多个 —— 检索主力
项目: 电商后台               # 只有项目笔记有
来源: 会话 | 书籍 | 网页 | 论文
创建: 2026-09-15
更新: 2026-09-15
---

# 一句话结论

## 展开

## 用户的判断

## 相关
- [[某篇已有笔记]]
- [[40_索引/后端]]
```

**`主题` 标签是检索主力，不是文件夹。** 文件夹决定「物理放哪」，标签决定「属于哪些主题」——一篇笔记能挂多个标签，不能放多个文件夹。阶段一靠 Obsidian 搜索（`tag:#数据库`），阶段二作为 RAG 切片聚合的依据。

**`用户的判断` 必须是你自己的观点。** 内容来自对话中你说过的话；**你没表达观点时该节留空，AI 不许代填**。代填等于伪造你的观点——将来回看时分不清哪句是自己想的。

**`类型` 固定枚举。** 字段一旦失控（`类型: 学习笔记`、`类型: 知识点` 各写各的），Dataview 查询和后续自动化全部失效。

## 六、最小闭环范围

**本期目标：把「投递 → 整理 → 落盘」跑通。**

- vault 骨架（目录、git、模板、索引页）
- 服务核心（领域逻辑 + LLM 层）

- 异步整理 + 三段式

**排在其后：** Web UI 完整功能、MCP 接口、收件箱撤回界面。

理由：整理质量是成败点，得先能跑起来看到真实效果，再包界面。

├── .env.example           ← 配置项清单（**入库**）：密钥留空待填，其余给出可用默认值
├── logs/                  ← 运行日志，轮转保留（**不入库**）

### 配置

**配置集中在本文件夹，不散到用户目录。** 全部走工程根目录的 `.env`（扁平键值）：

| 键 | 必填 | 说明 |
|---|---|---|
| `KB_LLM_API_KEY` | 是 | LLM 的 API key |
| `KB_LLM_BASE_URL` | 是 | API 地址 |
| `KB_LLM_MODEL` | 是 | 模型名（deepseek-flash 起步） |
| `KB_VAULT_PATH` | 否 | vault 路径，默认 `E:\KB_Library` |
| `KB_PORT` | 否 | 指定端口；留空则自动寻找 |

`.env` 不入库，`.env.example` 入库——**换机器时照着 example 填一份就够**，不用翻代码找配置项。

### 技术栈

| 用途 | 选型 | 依据 |
|---|---|---|
| 语言 | Python 3.11 | Q2 |
| Web 框架 | FastAPI | 轻量、自带交互文档、异步原生 |
| 模板引擎 | Jinja2 | Q41 —— 不引入前端构建链 |
| LLM 调用 | `openai` SDK + 兼容端点 | Q54 —— 换供应商只改 `base_url` |
| 测试 | pytest，**LLM 全 mock** | Q52 |
| 配置 | 工程根目录 `.env` | Q32 |
| 日志 | 标准库 `logging`，按大小轮转 | Q51 |

### 测试策略

**LLM 调用全部 mock**，替换为返回固定变更计划的假实现；在此基础上对校验层、落盘层写真实测试。

这样测试快、免费、稳定，可随时跑。真实 LLM 的效果靠手动端到端验证。

**整理逻辑的正确性不该依赖具体模型的输出**——这正是把 `llm/` 做成抽象层的原因。

### 模块化三条规则

**① `core/` 不许 import `web/` 或 `api/`。**
硬约束。整理是最容易出错的部分，必须能脱离界面单独跑测试。

**② `llm/` 是抽象层。**
换模型、换供应商、甚至本地模型，只改 `providers/`。整理逻辑的正确性不该依赖某个具体模型的输出。

**③ `api/` 和 `web/` 都是薄层。**
只做「协议 ↔ 领域调用」的转换，不含判断逻辑。加一个接口是几十行的事。

`scripts/init_vault.py` 是**知识库结构的唯一真源**——实际目录是它的产物。写成脚本而非手动建，是为了幂等（调结构重跑即可）、可重建、有版本记录。

## 八、关键约束

这些是硬规则，不是建议：

| 约束 | 原因 |
|---|---|
| **API key 绝不进 vault** | vault 是 git 仓库，写进配置会被提交进历史，删掉也还在。配置放 `KN_Base/.env`，且 `.env` 不入库 |
| **所有写入经服务进程** | 两个进程同时写会冲突。写入天然串行化 |
| **不允许孤儿笔记** | 每条正式笔记至少链到一处已有笔记或 MOC。孤儿是检索不精准的根因 |
| **AI 不得自行发明分类** | 遇到放不进的分类，只能报告。否则半年后分类体系就烂了 |
| **AI 不得自动新建项目文件夹** | 项目名匹配不到就进待归类，不猜 |
| **agent 不得自行触发整理** | 只能用户触发，否则异步缓冲失去意义 |
| **`用户的判断` 不许 AI 代填** | 代填等于伪造用户观点 |
| **失败回滚必须精确** | 不能用 `git checkout .`——会还原掉用户未提交的改动 |
| **服务禁止 `git add -A`** | 只 add 自己动过的文件，否则会把用户未提交的编辑裹进「AI 整理」的 commit |
| **一次整理 = 一个 commit** | 支撑「事后通知」——不满意可整体回退 |
| **运行日志不进 vault** | 一旦进去就成了笔记，会被检索、被 RAG 切片。技术日志是噪音，会污染知识 |

### 整理失败的兜底

| 失败类型 | 处理 |
|---|---|
| LLM 超时/限流/网络 | 指数退避重试 3 次 |
| 返回格式不合规 | 把错误信息喂回去让它自己修，重试 2 次 |
| 仍失败 | **按条隔离**——该条留在收件箱原样不动，其余条正常整理 |

按条隔离：10 条草稿里 1 条判不了，不该拖垮另外 9 条。失败条目**什么也不写**，所以下次重试天然幂等。

**崩溃残留**：服务启动时检查 vault 工作区，若发现上次操作清单残留，**报告给用户决定**回滚还是保留——不自动处理，因为你可能有未提交的改动。

### git 提交

服务使用独立 author（`kb-service`），`git log --author=kb-service` 能一眼分出「AI 写的」和「我写的」。

```
整理草稿 3 条

- 新建 20_知识/后端/并发写锁.md
- 合并入 10_项目/XXX/XXX-踩坑.md
- 更新 40_索引/后端.md
```

## 九、环境与运行

```bash
conda create -n kn_base python=3.11 -y
conda activate kn_base
pip install -r requirements.txt

cp .env.example .env      # 然后填入 API key
```

**环境内一律用 pip**，不混用 `conda install`（避免依赖冲突）。

本地代理 `http://127.0.0.1:5408` 已配置到 pip 与 git 全局，`pip install` 和 `git clone` 会自动走代理——详见 [`CLAUDE.md`](CLAUDE.md)。

## 十、接口速览

```bash
# 投递一条草稿（异步，立刻返回）
kb push --content "并发写入会锁表，最后用队列串行化解决" \
        --project "电商后台" --source 会话

# 长内容走 stdin
echo "..." | kb push --project "电商后台"

# 整理
kb organize           # 整理全部待整理
kb organize <id>      # 只整理某条

# 查看
kb inbox              # 收件箱
kb status             # 服务状态
kb stop               # 停掉服务（改了代码之后用）
```

### ⚠️ 改了代码要重启服务

服务是长驻进程，**Python 不会热重载**。改了 `src/kb/` 下的代码后，在跑的服务仍执行旧逻辑，而 CLI 探测端口只看到「活着」，于是继续用它——**改动看起来没生效**。

`kb status` 会检测到这种情况并告警，跑 `kb stop` 停掉即可（下次调用自动用当前代码拉起）。

`templates/*.md` 是每次整理现读的，**不受影响**。

**agent 只交正文，其余服务推断。** 必填只有正文，`--project` / `--source` 可选。

**禁止让 agent 填 `类型` / `主题` / 建议分类**——那等于把整理判断泄漏到每个会话，与服务收拢规则的设计相悖。

### 项目名映射

agent 报项目名，**默认取 git 仓库根的目录名**（不是 cwd 的 basename——避免停在子目录时取到 `core`）。非 git 仓库回退到 cwd basename。

- **允许没有项目**：留空则走 `20_知识/`
- **匹配前规范化**：统一转小写、`-` 与 `_` 视为等价（避免 `KN_Base` / `kn_base` 被当成两个项目）
- 服务在 `10_项目/` 下搜唯一匹配：匹配到就挂上；找不到或找到多个 → 进 `待归类/` 并报告
